**一句话版本：** 前沿部署工程师(FDE)是企业 AI 里增长最快的岗位——据报道招聘量同比增长约 1000%,OpenAI 更在 2026 年 5 月为专门的部署公司投入 40 亿美元。真正被验证有效的打法是 Palantir 那套：**本体优先**——先为客户业务建模,再交付任何 AI 应用。但这套打法留了一个没解决的结尾。每个项目都以交接收场,而今天,本体通常被锁在客户要永远租用的平台里。我们认为下一波 FDE 的定义性问题是我们所称的**本体交接（the ontology handover）**：客户的本体离开项目时,是变成*他们自己*仓库里的类型化开放文件——还是变成别人手里的续约筹码?

## 吃掉企业 AI 的岗位

今年公开报道的数字：FDE 职位发布量在 2025 年 1–9 月增长超过 800%,2026 年初同比突破 1000%（[Perspective AI](https://getperspective.ai/blog/2026-fde-hiring-trends-what-1000-job-posts-reveal)、[TechTarget](https://www.techtarget.com/searchenterpriseai/feature/The-rise-of-the-AI-forward-deployed-engineer)）。2026 年 5 月,OpenAI 宣布成立部署公司,**注资 40 亿美元**、约 150 名 FDE。原因是结构性的：模型已经够好,瓶颈从建模转移到了部署——每家企业的数据、流程、合规约束都是独特的,必须有人坐进去,让 AI 真正落地。

## 有效的打法是本体优先

早在这个词流行之前,Palantir 就把它制度化了：他们的 AI FDE **在交付任何基于 LLM 的应用之前,先构建客户专属的本体**,并把每周 30–40% 的时间花在业务发现上（[Palantir AI FDE 指南](https://www.palantir.com/docs/foundry/ai-fde/overview)）。这个洞察经得起时间：通用模型给通用答案。企业价值必须落在客户自己的名词和动词上——对象、关系、权限、审批路径。这是工程,不是提示词。

这些如今已无争议。很少被讨论的,是项目结束时发生的事。

## 没解决的部分：交接

每个前沿部署项目都会结束。FDE 撤场,而他们构建的本体——整个项目最有价值的产物,这家企业实际运转方式的编码知识——会落在两种地方之一：

- **供应商的平台里。** 客户能用,但只能通过平台用,按席位计费,改动只能靠平台培训的专家。本体变成了续约筹码。
- **客户的仓库里。** 类型化、有版本、开放的文件,客户自己的团队——以及客户自己的 AI 智能体——不需要任何人许可就能读懂、运行、持续修改。

今天默认是第一种结局,这正是企业客户学会害怕"成功试点"的原因：本体越好,锁定越深。第二种结局,只有当定义层本身是开放格式时才可能。

## 开放的 FDE 技术栈长什么样

这正是 [ObjectStack](https://github.com/objectstack-ai/objectstack)（Apache-2.0）为之设计的工作流。发现笔记变成类型化元数据——你的编码智能体来写,校验门拒绝一切会静默失败的东西：

```ts
export const Ticket = ObjectSchema.create({
  name: 'support_ticket',
  label: 'Ticket',
  sharingModel: 'private',        // 默认从严——校验门强制要求
  fields: {
    subject:  Field.text({ label: 'Subject', required: true }),
    status:   Field.select({ label: 'Status', options: [/* 客户真实的状态 */] }),
    approver: Field.lookup('sys_user'),
  },
});
```

运行时从这份定义派生数据库、REST API、管理 Console 和 MCP 工具,并对每一次调用强制执行权限与审计——包括你离场之后。整个应用始终可审：一个完整 CRM 是 **1792 行、约 16k token**——自己数一遍：

```bash
find examples/app-crm/src -name '*.ts' -not -name '*.test.ts' | xargs cat | wc -l
```

正是这个体量让交接变得诚实。客户的安全团队读的是真实的 diff,而不是信任某个平台边界;客户未来的智能体能把整个系统装进上下文,整体重构。

## 这套栈不解决什么

把边界说清楚：**超大规模数据联邦与分析管道**是 Foundry 的主场,开放的应用层不能替代它们。**组织变革管理**——让人真正用起来——依然是任何技术栈都修不了的人的工作。已经全面标准化在某个封闭平台上的客户,留在原地也可能是理性的。这个论断更窄：就前沿部署工作的应用层——为业务建模并在其上交付受治理应用——而言,本体现在可以交接,而不必扣为人质。

## FDE 检查清单

1. 先把客户的名词和动词建模成对象与流程,再谈任何界面。
2. 让整个定义保持上下文体量,智能体才能整体重构。
3. 权限默认从严;每一次权限变更都在 diff 里显式可见。
4. 交接的是仓库、编译制品和评审清单——不是你租户里的一个账号。
5. 保持 MCP 开启,让客户自己的 AI 在其权限内操作应用。

## 跑一遍这个循环

把你的编码智能体指向开源技术栈——脚手架自带 `AGENTS.md` 和技能包：

```bash
npm create objectstack@latest client-app && cd client-app
npx os dev --ui   # 应用已运行——和你的智能体一起建模下一个对象
```

如果客户希望平台被托管运营——浏览器内 AI Builder、云端或自管部署——那是 [ObjectOS](https://www.objectos.ai),运行在同一份开放定义上的商业运行时。
