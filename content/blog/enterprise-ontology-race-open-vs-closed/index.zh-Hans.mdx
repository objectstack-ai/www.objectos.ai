先讲一家公司的真实处境（细节做了脱敏，但每一步你大概都见过）。

一家制造企业，2024 年把数据底座押给了微软。Fabric 里建了一套干净的本体："客户"是什么、一个"客户"连着哪些"设备"、"设备"又挂着哪些"工单"，定义得清清楚楚。那一年它是模范案例。

2026 年，三件事几乎同时落到这家公司头上：

- 数据科学团队想用 Gemini 跑一批预测，因为在某个具体场景里它确实更准；
- 合规部门接到通知，欧盟客户的数据要留在欧盟，不能再进美国云；
- 一桩收购完成，带来了一整套跑在 Salesforce 上、好几千客户的销售组织。

于是今天，这家公司有了**三个"客户"**。Fabric 里一个，Salesforce 里一个，合规隔离的欧盟环境里还得再来一个。没有任何一个 agent 能跨着这三个回答一句"这个客户的全局风险有多高"——因为没有一层东西知道，这三个"客户"其实是同一个人。

他们没做错任何一步。每一步单看都正确。错的是一个更隐蔽的决定：**他们把"自己业务的定义"交给了平台保管，而每个平台只保管它自己那一份。**

这就是 2026 年企业本体竞赛真正的暗线。

## 所有人都在抢这一层，方向高度一致

先把背景交代清楚，因为这件事正在快速变成主战场。

一年前，"业务语义层 / Ontology"还基本是 Palantir 的专属词汇。今年，Gartner 在数据与分析峰会上把语义层和知识图谱直接定位成 agentic AI 的基础设施；企业知识图谱市场的预测，从今天的约 19 亿美元一路画到 2032 年的近 100 亿。玩家也齐了：微软推 Fabric IQ，谷歌把企业知识图谱摆上台面，Palantir 一边卖 Foundry 一边绑定 NVIDIA。

为什么是现在？因为 agent 把这个洞捅破了。过去十年的数据管道只在乎"数据流到哪"，不太在乎"这条数据是什么意思"——反正最后兜底的是人。agent 没有那个兜底的人，它面对几十张表、口径不一的"客户"字段，要么答错、要么不敢答。行业里那些扎眼的数字——88% 的 agent 试点进不了生产——很大一部分就死在这层缺失上。

所以三巨头的判断是对的，而且一致：**AI 要可靠地进企业，必须先有一层机器可读、受治理的业务定义。** 这一点不必再争。该争的是下一个问题——这一层该归谁。

## 三个对的方向，三把不同的锁

把三家方案摊开，会撞见一个尴尬的共同点。

| | 本体存放在哪 | 谁能读懂它 | 你能带走吗 |
| --- | --- | --- | --- |
| Palantir Foundry | Palantir 平台内 | 驻场工程师 + 平台工具 | 绑定平台，迁移=重做 |
| Microsoft Fabric IQ | OneLake / Fabric 内 | 365 与 Fabric 生态 | 绑定微软栈 |
| Google 企业知识图谱 | Google Cloud 内 | Vertex 与 GCP 生态 | 绑定谷歌栈 |

每一家都在帮你把业务梳理清楚，然后把这份清楚锁进自己的平台。这很合理——平台当然希望你的核心资产长在它身上。

老一辈 IT 人看到这里会条件反射地说一句：又是厂商锁定嘛，老问题了。

但锁定不是这次最该担心的。这次有个更糟的新问题。

## 旧问题是锁定，新问题是分裂

单一厂商锁定，至少你的业务定义还是**完整的一份**，只是搬不走。痛，但完整。

三家巨头同时建封闭本体，制造的是另一种东西：**分裂。** 回到开头那家公司——它的"客户"不是被锁住了，是被切成了三份，分别躺在三个互不相认的平台里。这比锁定难受得多，因为：

- **没有任何一方有动力去统一它。** 微软的本体不会去理解 Salesforce 里的"客户"，反之亦然。统一这件事，每一家都觉得不归自己管。
- **agent 时代，分裂的代价被放大了。** 人脑还能勉强在三个系统间手动对齐；agent 不能，它需要一层确定的、跨系统一致的定义才能推理。你越想让 agent 干跨域的活，分裂就越致命。
- **而企业的技术栈注定是混合的。** 多模型、多云、加上并购——没有哪家大公司能保证未来十年只用一家的东西。赌"全栈押一家"，等于赌自己永不改变。

要让分裂不发生，逻辑上只有一个出路：**业务的定义，不能属于任何一个参与竞赛的平台，它必须是一层中立的东西**——一份你自己持有、三家的工具都能去读的定义。这正是开放协议要解决的，也是封闭平台结构上给不了的：它们是竞赛的选手，没法同时当裁判。

这件事在 2026 年还多了一个旁证。agent 之间已经在用开放协议握手了——MCP 连工具、A2A 连 agent，都归了 Linux 基金会。整个 agent 生态正在把"管子"标准化成中立的。唯独管子里流动的"意义"——业务定义——还卡在三家的私有平台里。中立的工具协议之下接一个各自为政的定义层，这个组合长不了。

## 先泼一盆冷水：开放不等于自动统一

到这里要诚实地停一下，否则就成了卖膏药。

**把定义换成开放协议，并不会自动把你那三个"客户"合并成一个。** 该做的数据建模、口径对齐、脏活，一样得做——这部分没有银弹，谁吹这个都别信。

开放真正改变的，是这件苦活的**归属**：你今天花力气对齐出来的那份定义，是写在你自己仓库里的，而不是沉淀在某家平台的后台里。明年你换模型、换云、被并购，重做的是连接，不是定义本身。封闭方案里，每换一次平台，这份苦活就报废重来一次；开放方案里，它是你**留得下、带得走**的资产。

换句话说：开放不省你第一次的功夫，它省你后面每一次的功夫。对一个技术栈注定会变的企业，这才是真正值钱的地方。

## 被所有人依赖的层，最后都中立了

这个规律本身不新，一句话带过：被整个生态共同依赖的"定义层"最终都走向中立——SQL、TCP/IP、OCI 镜像格式，无一例外；而"运行层"可以封闭、可以收费，因为运行意味着持续的运维与责任。AWS 就是活教材：定义归社区，运行收钱。

新的是它这次套在谁头上。业务定义这一层，未来要被你的应用、你的 agent、你的审计系统**同时**依赖——现在还要被三家厂商的工具同时依赖。一个被这么多方依赖的层，逻辑上不可能长期归其中任何一方私有。它要么变中立，要么持续制造上面那种分裂。

## 中立的那一层，长什么样

说了这么多，看一眼实物，重点不在语法，在于它**在哪、能不能带走**。

业务对象、关系、权限，是你 Git 仓库里一份声明式的定义：

```ts
export const Opportunity = ObjectSchema.create({
  name: 'crm_opportunity',
  label: '商机',
  fields: {
    account: Field.lookup('crm_account', { label: '客户', required: true }),
    amount: Field.currency({ label: '金额', min: 0 }),
  },
});
```

它最关键的属性，不是这几行多优雅，而是它接下来能做什么——把"可带走"变成可演示的动作，而不是一句承诺：

```bash
git add crm/*.ts          # 定义进了你的版本库，可 diff、可评审、可回滚
os deploy --self-hosted   # 同一份定义，跑在你自己的基础设施上
# 然后把任意模型指向它——Claude、GPT、Gemini 都行，运行时不变
```

定义在你手里，运行时（ObjectOS）在你自己的环境里执行它、强制权限、记录审计。明年你想从一家云换到另一家、从一个模型换到另一个——重新部署，定义一行不用改。回到开头那家公司：如果它的"客户"当初是这样一份中立定义，三个系统接的就是同一份，agent 那句"全局风险"才答得出来。

这就是 ObjectStack 与 ObjectOS 的分工，也是它对这场竞赛的回答：

- **ObjectStack**——描述业务的开放协议（Apache 2.0），存在你仓库里，三家的 agent 都能读；
- **ObjectOS**——这份定义的运行时，跑在你自己的基础设施上。

定义层中立，运行层做生意。和 SQL 与数据库厂商的关系，一模一样。

## 结语

这不是一道"开放好还是封闭好"的意识形态题。它是一道更冷静的算术题：**当你的厂商组合迟早会变——而它一定会变——那一刻，谁手里攥着你业务的定义？**

三巨头用真金白银替行业证明了这一层值得做。但他们也同时把这道算术题摆到了每家企业面前。开头那家公司的三个"客户"，不是技术事故，是把定义交出去的必然结果。

被所有人依赖的层，历史上从没长期归过一家。这一次，没理由不同。

```bash
npm i -g @objectstack/cli && os start
```

定义你的第一个业务对象，然后把它 `git commit` 进自己的仓库——那一刻，业务的定义就回到了你手里，而不是某一家的后台里。
