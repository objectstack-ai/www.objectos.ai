**TL;DR:** If you are evaluating Retool for governed AI app development, its access layer passes, and you should not pretend otherwise. Retool has RBAC through permission groups, role-based control over who may use its AI builder, audit logs that record every query run, SSO, self-hosting, and (since October 2026, in public beta for Postgres) resource access policies that no query can opt out of. Since June 2026 it applies those controls to apps built in Lovable, Cursor or Claude Code too. What it does not give you is business **authority** as a declared fact. "Can this person issue a $12k refund?" still tends to live in JavaScript spread across component properties and query logic, and an AI writes those expressions faster than any pull request can review them. The gap is not basic security. It is that authority is *code*, not a rule a reviewer can read in one place.

Picture a very ordinary Retool app: a refund console. An engineer builds it in an afternoon: a table of orders, a "Refund" button, a few queries. Support uses it. It works well. This is Retool at its best.

Now it is six months later. The engineer who built it has changed teams. Security is doing an access review and asks the new owner a one-line question: **"Which roles can issue a refund over $10,000, and where exactly is that enforced?"**

Watch what the new owner has to do to answer. There is no single place to look. They open the app and start reading JavaScript.

## The Grep Test

Here is what "where is it enforced" actually looks like in a real Retool app. The authority to issue a large refund is spread across at least three independent expressions, each hand-written, each a different shape:

```js
// 1. refundButton → "Hidden" property
{{ current_user.groups.map(g => g.name).includes('admin') ||
   (current_user.groups.map(g => g.name).includes('support_lead') && refundAmount.value <= 10000) }}

// 2. refundAmount input → "disabled" property
{{ !current_user.groups.map(g => g.name).includes('support_lead') }}

// 3. issueRefund query → transformer (this is the part that actually writes)
if (refundAmount.value > 10000 && !current_user.groups.map(g => g.name).includes('finance')) {
  throw new Error('Refunds over $10k require finance');
}
```

Three places. Three subtly different conditions. The button hides itself for some users; the input disables itself for others; the query throws for a third set. They are *supposed* to add up to one coherent rule — "support leads up to $10k, finance above" — but nothing guarantees they do. Hide a button and the underlying query still runs if someone hits it another way. Add a second write path next quarter and forget the `finance` check, and you have a hole that no screen reveals.

Call this **the grep test**: to answer "who can do X," do you read *one declared rule*, or do you `grep` the app? If the answer is grep, the app is not governed at the authority layer; it is merely *coded*. Access governance, which Retool handles well, sits one layer above the thing that can actually hurt you.

For contrast, here is the same authority as a declared fact — one rule the runtime enforces on *every* path, regardless of which button or query you came through:

```yaml
action: issue_refund
  who_can_run:
    - role: SupportLead   when: amount <= 10000
    - role: Finance       when: amount  > 10000
  requires_approval:      when: amount > 10000      # a preventive gate, not a thrown error
  audit: always
```

One place to read. One place to change. One thing for a reviewer — or an AI — to reason about. The difference between three hand-maintained expressions and one declared rule is the entire difference between "the app is coded" and "the app's authority is governed."

## Retool RBAC and Audit Logs: What Each Control Actually Covers

The grep test is only fair if the controls Retool *does* have are stated exactly. Here they are, checked against Retool's own documentation in November 2026:

| Control | What it governs | Where it stops |
| --- | --- | --- |
| **Permission groups (RBAC)** | Groups "grant roles and control access to apps, resources, workflows, and agents" ([Retool permissions guides](https://docs.retool.com/permissions/guides)) | Who can open, edit or query, not what a given action may do once someone is in |
| **Assist RBAC** (Feb 2026, Business and Enterprise) | Per role: Ask and Build mode, Ask mode only, or no access to the AI builder ([changelog](https://docs.retool.com/changelog/assist-rbac)) | Who may *generate* changes, not what a generated change grants |
| **Audit logs** | User actions "such as query runs and password resets", with the exact query, parameters, IP address and response time; one year of retention on Cloud, CSV export on Business and Enterprise, Datadog or Splunk streaming on Enterprise ([audit logs](https://docs.retool.com/org-users/guides/audit-logs)) | Detective: they record what ran, after it ran |
| **`current_user` row filters** | Values "computed server-side from the authenticated session" and injected into each query ([row-level security](https://docs.retool.com/docs/user-permissions)) | Per query, by hand: "A query that omits the filter returns unfiltered data." |
| **Resource access policies** | Table, column and row access on a resource, enforced on every query from apps, the query library, raw SQL and agents ([access policies](https://docs.retool.com/data-sources/concepts/access-policies)) | PostgreSQL only, [public beta since October 2026](https://community.retool.com/t/new-public-beta-data-access-enforcement-for-postgres-resources/67615); row filters "do not validate the rows a user creates, or the values a user writes" |
| **Governance for AI-coded apps** (June 2026) | Apps built in Lovable, Replit, Cursor or Claude Code "inherit existing permissions and audit trails"; "Permissions are attached to data sources" ([Retool newsroom](https://retool.com/newsroom/retool-extends-enterprise-governance-to-vibe-coded-apps)) | Same layer: data-source permissions, not action-level business rules |

Two of those rows matter more than the rest, because they are Retool moving in exactly the direction this article argues for.

**Access policies are a declared rule, not three expressions.** A policy on the resource applies to every query, "so no query can opt out", which is the opposite of the per-query `current_user` filter. For *data* authority — which rows a support lead may read or delete — that closes most of the grep test on Postgres. The honest update to the June version of this post is that Retool now has a real answer for that layer.

**What policies do not express is the refund rule.** The access-policy documentation describes read, write and delete access to tables, columns and rows. It does not describe amount thresholds, approval gates, or conditions on the value being written; and row filters explicitly do not check what a user writes. "Support leads up to $10k, finance above, approval over the line" is a rule about an *action and its arguments*, so it still lives in the button, the input and the transformer above. Policies move data authority into one place. Business authority stays in JavaScript.

Read the table as a scorecard and Retool passes every access-governance question a security review will ask. The question it cannot answer from one place is the one at the top of this post: which roles can issue a refund over $10,000, and where is that enforced?

## Why Source Control Does Not Close This

The sharp Retool engineer's rebuttal is fair and has to be answered precisely: *"We have Git-backed source control, audit logs, and RBAC. Changes are reviewed in PRs. Access is governed. What is missing?"*

Three things, specifically.

First, a PR on a Retool app is a review of **JavaScript and bindings scattered across components** — you are code-reviewing, which means (a) it requires an engineer, and (b) there is no structured representation of *"this change altered who can issue a large refund."* The reviewer has to *notice* that a tweak to a `Hidden` expression three components over changed an authority boundary. Diffs of scattered logic hide exactly the thing you most need to see.

Second, source control reviews **code, not authority as a fact.** "Did this PR change who can refund >$10k?" is not a question a Git diff answers directly; it's a question you answer by tracing the code in your head. The declared rule above makes that diff trivial: `who_can_run` changed, or it didn't.

Third, and this is the one that matters most for where the industry is going, the whole premise of low-code is that **non-engineers and AI** change the app, often in the visual editor and often without a PR at all. The governance you are counting on, PR review, may not exist for the changes low-code is *for*. Audit logs can tell you a `Hidden` property changed after the fact, but that is detective, not preventive. No one reviewed *what authority it granted* before it shipped.

## AI Does Not Break This. It Multiplies It.

For years the grep test was survivable because a human wrote the JavaScript and another human carried the knowledge of where each rule lived. Scattered logic is navigable if a person built it and remembers it.

Point an AI at the same app and the economics invert in both directions. The AI can generate fifty bindings and a dozen transformers in a minute; it produces *authority decisions* faster than any reviewer can trace them. To review what it produced, you are back to reading JavaScript across screens, because there is still no single structured representation of authority to diff against. Retool AI and agents are real and useful, but they automate *on top of the same app substrate*: the agent can be scoped, but the **app the agent edits** may not express authority in a form an AI, or a human, can review as a fact rather than as code.

The thing AI is fastest at producing is precisely the thing Retool makes hardest to review.

## Retool vs. Lovable for Enterprise Apps

The other comparison people run is Retool against Lovable, and it is usually framed as "internal tool builder vs. AI app generator." For an enterprise app the more useful framing is: *whose users does each control govern?*

| | Retool | Lovable |
| --- | --- | --- |
| **What the AI produces** | An app on Retool's component runtime, wired to your existing resources | Full-stack project code; by default it "lives in Lovable's managed infrastructure", with GitHub, GitLab or Bitbucket sync ([Lovable for Enterprise](https://docs.lovable.dev/introduction/lovable-for-enterprise)) |
| **Roles** | Permission groups control access to the app and to the resources, workflows and agents behind it | Owner, admin, editor, viewer and external collaborator govern the *workspace* that builds the app ([same page](https://docs.lovable.dev/introduction/lovable-for-enterprise)) |
| **End-user data access** | Data-source permissions, `current_user` filters, access policies | Row-level security in the built-in backend "for per-user data", part of the generated project; a Quick scan "runs on every publish and checks database access rules" |
| **Audit** | Query-level audit log, one year on Cloud | Workspace audit log "retained for 13 weeks", with scheduled export to a SIEM or storage bucket |
| **Self-hosting** | Retool-managed or self-managed self-hosted instances ([self-hosted Retool](https://docs.retool.com/self-hosted)) | Backend and database can move to infrastructure you operate, "including self-hosted Supabase"; the builder itself stays SaaS |

The distinction in the second and third rows is the one that decides enterprise fit. Lovable's roles and audit log govern the people *building* the app; the people *using* it are protected by the access rules inside the generated project's own backend, which a scan checks on every publish. Retool governs the people using the app, because the app runs inside Retool. That is why Retool's June 2026 move is to *host* apps built in Lovable and similar tools under its own data-source permissions, rather than to compete with them on generation.

So the realistic enterprise pattern is not "Retool or Lovable" but "generate anywhere, run somewhere governed." Neither changes the grep test: a Lovable app's refund threshold lives in its generated code, a Retool app's in its bindings and transformers, and in both cases a reviewer reconstructs business authority by reading code.

## Where Retool Is the Right Call

Be honest in both directions, because a one-sided piece is worthless to someone actually deciding.

Retool's access governance is genuinely strong, and for a large set of apps the grep test never bites: an internal tool operated by trusted staff, behind SSO, maintained by the same engineers who wrote it, where "support leads can refund up to $10k" is enforced in three places that agree and rarely change. For that, and for the freedom to drop into SQL and arbitrary JavaScript whenever a requirement is unusual, Retool is excellent. We are not going to beat "wire a tool in an afternoon."

And the declared-metadata model has a real cost in the other direction: you trade raw flexibility for legibility. You cannot paste arbitrary JavaScript into a property when the model does not have a place for it; expressing genuinely unusual logic as declared rules is more constrained than `{{ }}` anywhere. For a throwaway tool, that constraint is pure overhead. The model pays for itself when "who can do what" is something you will be *asked to prove* by an auditor, a regulator, or the next owner, and when an AI, not the original author, is doing the changing.

That is the line. Below it, Retool wins on merit. Above it, the grep test is what you fail six months later in front of an auditor or security reviewer.

## ObjectStack's Position

ObjectStack keeps the thing Retool gets right, including strong access control, self-hosting, and your own infrastructure, and moves *authority* down into the same governed layer. The app's logic is **open, readable metadata**: an action like `issue_refund` carries its own `who_can_run`, its own approval gate, and its own audit requirement, declared once and enforced by the runtime on every path. An AI change is a **diff against that declared authority**. "This change lets SupportLead refund up to $25k" is a line a non-engineer can read and approve before it ships, not a `Hidden` expression you discover later by grepping.

We will not out-Retool Retool at "drop into JavaScript and ship a tool by lunch." The claim is narrower and only matters above the line: when AI is writing your internal software, *who-can-do-what* should be a fact you can read in one place and review as a diff, not an emergent property of three expressions that have to agree until the quarter they do not.
