**短い答え。** そのシステムで業務を回す部門の責任者が承認のサインをする。署名するのはコードではなく、一枚の紙だ。この紙、**承認シート**には四つのことが書かれている。誰がどのレコードを見て変更できるか、誰が何を承認できるか、何が外部に開いているか、何が記録されるか。リリース前に一枚、AI が変更するたびにもう一枚求め、変わった行だけを読む。誰も署名しなければ、これらの判断は AI が代わりに下したことになる。シートは、システムが実際に動くこと、データがきれいなこと、ロジックが正しいことは証明しない。それは人が引き続きテストする。

*ObjectStack 18.5.0（2026 年 11 月 17 日時点の最新リリース）で、同梱の CRM サンプルを使って計測した。すべてのコマンドと生の出力は[証拠](#証拠)にある。*

## 承認はコードレビューではない

AI コーディングエージェントが社内システムを作ると、二つの異なる問いが生まれ、それぞれ別の人が答える必要がある。

開発者、あるいは [AI が生成したアプリ変更のレビューチェックリスト](/en/blog/how-to-review-ai-generated-app-changes/) に沿って確認するレビュアーが答えるのは、*正しく作られているか？* だ。

業務の責任者が答えるのは、*これは私たちが許していることか？* だ。チームの誰が顧客のレコードを開けるのか、誰が商談に 35% の値引きを認められるのか、ウェブサイト上の見知らぬ人は何ができるのか、来年の監査で何を見せられるのか。誰も答えなければ、AI エージェントがこれらの問いにすべて代わりに答えてしまう。動いているシステムは、それを空欄のままにしておけないからだ。

だから責任者は、それらの判断をまとめた書面に署名する。自分の言葉で書かれ、システムそのものから生成されたものだ。その書面がシートである。

## 変更前のシート

以下は、出荷時の状態の CRM サンプルのシートだ。第 1 部と第 2 部、それに問い合わせフォームのフィールドとフィールド履歴の行は、アプリ自身の定義から読み取った。残りは、動いているシステムを実際に試して確かめた。詳しい解説記事がある部分にはリンクを付けている。

### 1. 誰がどのレコードとフィールドを見て変更できるか

この機能を有効にしたアプリは、**アクセスマトリクスのスナップショット**を保存している。各ロールが各種類のレコードに対して何ができるかを記録した表だ。ビルドのたびに表を作り直し、保存されたコピーと違えばビルドが止まる。人がその変更を受け入れるまで止まったままだ（[スナップショットが権限の静かな変更をどう捕まえるか](/ja/blog/catch-ai-silent-permission-change-access-matrix-gate/)）。ロール（プラットフォームでは「ポジション」と呼ぶ）を行にして平易な言葉に直すと、CRM のスナップショットは次のとおりだ（最後の行はプラットフォーム組み込みの管理者で、スナップショットには載っていない）。

| ロール | 見られるもの | 作成・編集できるもの | 削除できるもの | 誰のレコードか | フィールドの制限 |
|:--|:--|:--|:--|:--|:--|
| 営業担当 | 取引先、連絡先、リード、商談、商談明細、活動 | 同じ六種類 | なし | 全員のもの | なし |
| 営業マネージャー | 営業担当と同じ | 同じ | なし | 全員のもの | なし |
| 財務承認者 | 営業担当と同じ | 同じ | なし | 全員のもの | なし |
| ウェブサイトの訪問者（未ログイン） | なし | 新しいリード、問い合わせフォーム経由のみ | なし | なし | 五つのフィールド（第 3 部） |
| 管理者 | すべてのレコード、加えてシステム設定 | すべてのレコード | すべてのレコード（プラットフォームの説明による。実際に一件削除した） | 全員のもの | なし |

**署名する人が気づくべきこと：** 三つの社員ロールはまったく同じだ。営業マネージャーにできて営業担当にできないことはなく、営業担当は自分の商談だけでなく会社中の商談を編集でき、レコードを開ける人には、どのレコードのどのフィールドも隠されていない。小さなチームならそれで問題ないかもしれない。それでもこれは一つの判断であり、この表こそ、あなたがその判断を下す場所、あるいは誰かがあなた抜きで下していたことに気づく場所だ。

### 2. 誰が何を承認できるか

**承認ステップ**とは、システムが変更をいったん止め、指定されたロールが承認するか却下するかを待つ地点のことだ。

| 承認が必要なもの | 承認する人 | 備考 |
|:--|:--|:--|
| なし | — | 「財務承認者」というロールがあり、「30% を超える値引きを承認する権限を持つ」と説明されているが、承認ステップは一つも存在しない。 |

**署名する人が気づくべきこと：** システムにない統制を、説明文で約束しているロールがある。試してみた。商談の値引きを 0% から 35% に変えると保存され、誰にも確認されなかった。別のルールが 40% を超える値引きを止めてはいる。メッセージは「Discount cannot exceed 40% without an approved exception」（承認された例外がなければ値引きは 40% を超えられない）だが、その例外を得る手段もやはり存在しない。

### 3. 何が外部に開いているか

| 入口 | 使える人 | できること |
|:--|:--|:--|
| ウェブサイトの問い合わせフォーム | 誰でも、ログイン不要 | 新しいリードを一件作る。リードの 13 フィールドのうち 5 つ：氏名、会社、メール、電話、役職（[公開フォームがフィールド五つの幅にとどまる仕組み](/ja/blog/how-to-let-anonymous-visitors-submit-a-form/)） |
| データインターフェース（API）。ほかのソフトウェアがレコードを読み書きするときに使うアドレス | ログインしたユーザーのみ | そのユーザーのロールが許す範囲そのもの。ログインしていなければ拒否する |
| AI エージェント接続（MCP）。AI アシスタントがシステムにつながるための標準的な方法 | システムが発行したキーを持つ人 | キーの持ち主として、その人の権限で動く。プラットフォームのドキュメントによる（証拠に引用）。キーがなければ拒否する |
| 組み込みの AI エージェント、ほかのアドレス、他システムへの送信メッセージ | — | 宣言なし |

**署名する人が気づくべきこと：** AI エージェント接続は既定でオンになっている。そのため「誰にキーを発行したか」が、アクセス権の見直しで確認すべき問いになる。

### 4. 何が記録されるか

| 内容 | 記録されるか |
|:--|:--|
| レコードの新規作成・変更・削除のすべて。誰が、いつ、変更前後の値とともに | はい |
| ログイン | はい |
| **フィールド履歴**。レコードのページに表示される過去の変更一覧 | 取引先、連絡先、リード、商談にはある。活動と商談明細にはない |
| **レコードの閲覧**。誰がどのレコードを開いたか | いいえ。どの種類のレコードでも有効になっていない（[閲覧監査が記録するもの](/ja/blog/prove-who-opened-a-customer-record-view-auditing/)） |

**署名する人が気づくべきこと：** 変更は記録されるが、レコードを開いたことは記録されない。「誰がこの顧客の資料を見たか」が義務に含まれるなら、この行はリリース前に変えるべきで、監査人から最初に問い合わせが来てからでは遅い。

## AI による一つの変更と、二枚目のシート

では、営業部長がエージェントに打ち込みそうな依頼を一つ。*「30% を超える値引きには財務の承認が必要」*

変更は 38 行の新しいファイル一つと、ほかの場所の 3 行の修正だ。下書きはあえて最小限にした。商談に承認ステップを一つ加え、「財務承認者」ロールに回し、依頼文が触れていない点はすべてプラットフォームの既定値に任せた。結果を面白くするために何かを付け加えてはいない。プラットフォームの 68 項目の自動チェックはすべて通った。そのうち一つが、ロールを持つ人が誰もいなければ申請は管理者に回る、という注意を表示した。注意であって、拒否ではなかった。

アクセスマトリクスのスナップショットは変わらなかった。誰の権限も変わっていないので、権限チェックは何も言わなかった。下の三つの判断は承認ステップの中にあり、そのチェックの対象外だ。シートの第 1 部と第 3 部は以前と同じ。第 2 部が変わり、第 4 部に行が増えた。

| シートの行 | 変更前 | 変更後 | 署名する人が聞くこと |
|:--|:--|:--|:--|
| 承認が必要なもの | なし | **既存の**商談の値引きを 30% 超に上げること | 「最初から 35% で入力された新しい商談は？」 |
| 承認する人 | — | 「財務承認者」ロールを持つ人なら誰でも | 「今そのロールを持っているのは誰？」 |
| ロールを持つ人がいないとき | — | システム管理者が決める | 「値引きをシステム管理者が承認すべきか？」 |
| 申請した本人が承認できるか | — | できる。「財務承認者」ロールを持っていれば | 「財務は自分の値引きを自分で承認できるのか？」 |
| 承認待ちのあいだ商談を編集できるか | — | できない。ロックされる | 「財務が決めるまで商談がロックされるのは許容できるか？」 |
| 記録 | 変更とログイン | 加えて、承認申請のそれぞれ、誰が決めたか、いつか | 聞くことはない |

それぞれを、動いているシステムで試した。

| 行ったこと | システムの反応 | 業務にとっての意味 |
|:--|:--|:--|
| 値引き 35% で新しい商談を作成 | 保存された。申請はなし。 | 承認が始まるのは編集のときだけ。最初から 35% で入力した新しい商談では始まらない。 |
| 管理者が既存の商談を 35% に上げた | 承認申請が開き、管理者に割り当てられた。新しく入れたテスト環境では誰も「財務承認者」を持っていなかったからだ。商談はロックされた | 初日から、誰かにロールが割り当てられるまでは、値引きはシステム管理者が承認する。 |
| 「財務承認者」ロールを与えられた Fiona が、別の商談を 38% に上げた | Fiona が唯一の承認者となる申請が開いた（ロールを持つのは彼女だけだった）。彼女が承認し、商談は「承認済み」と表示された | 値引きを申請した本人が、自分で承認した。 |
| ロックされた商談を編集しようとした | 拒否された：「locked while an approval is in progress」（承認の進行中はロック） | 承認者が判断しているあいだ、誰も商談を変更できない。 |
| 監査ログを読んだ | 値引き変更の行、申請の行、Fiona の判断の行が一つずつ。どれも誰がいつかを含む | これらの判断はどれも記録に残り、後から見直せる。 |
| 変更後に 45% を試した | 40% の上限で引き続き拒否 | そのメッセージにある「承認された例外」は、依然として存在しない。 |

下書きは依頼文が求めたことを実現した。同時に、誰も頼んでいない三つのことも決めていた。新しい商談は対象外であること、申請者が自分の値引きを承認できること、財務ロールを持つ人がいないときは必ずシステム管理者が決めること。三つとも、コーディングの誤りではない。そして三つとも、平易な言葉でシートに現れている。

## シートが証明しないこと

シートは、システムが何を*許している*かを述べたものだ。シートには教えられないことが三つあり、リリース前に誰かがテストしなければならない。

- **実際に動くこと。** 同じ変更の前の下書きでも、シートはまったく同じだった。シートは、プラットフォームのどの部分がオンになっているかを見ないからだ。同じチェックも通った。ところが動いているシステムでは、35% の値引きがそのまま保存され、誰にも確認されなかった。承認を実行する部分がオフになっていたのだ。手がかりは、サーバーログの警告一つとエラー一つだけだった。実際に試して初めて分かった。シートに署名したら、変わった行をテスト用のコピーで一度ずつ試すこと。
- **データが正しいこと。** シートが示すのは、誰が商談を編集できるかだ。旧システムから取り込んだ商談の担当者が正しいか、重複がないか、金額が空でないかについては何も語らない。データの品質は、データを見て確かめる。
- **業務ロジックが正しいこと。** シートには「30% 超」とある。30% が自社の数字なのか、しきい値は合計に対してか製品明細ごとか、約束されているのに存在しない例外付きの 40% の固定上限を受け入れられるのか。これらは、そのプロセスを動かしている人たちへの問いだ。実際の事例でテストすること。

シートに載るのは四つの部分で、すべてのルールではない。40% の上限はシートに載っていない。試して見つけたものだ。

シートに書かれているのはロールであって、人ではない。誰がどのロールを持っているかは、アクセス権の見直しと同じ周期で確認すること。

## もっともな反論：「署名するのは IT であって、私ではない」

承認を IT に任せるべきだという主張には強い根拠がある。IT はプラットフォームを理解しているし、ほかのシステムの変更承認もすでに担っている。部門長にはほかの仕事がある。

IT が保証できるのは、システムが依頼どおりにできていることだ。依頼の内容そのものを業務が受け入れられるかどうかは保証できない。「30% を超える値引きは財務が承認する」は忠実に実装され、そこに含まれていた三つの判断は、下書きとプラットフォームの既定値から来たもので、IT の誰かが決めたものではない。自分で承認した 38% で問題ないかどうかは、値引きの方針に責任を持つ人が言わなければならない。うまくいく分担は、IT がビルドに署名し、業務の責任者がシートに署名することだ。

一枚のシートは、さっと読まれる。だからこそ短い。最初のリリースのあとは、責任者は変わった行だけを読めばよい。

## 自分のシステムのシートを手に入れるには

エージェントに作らせる。ObjectStack 18.5.0 には、このシートを出力するコマンドはない。この記事のために 51 行のスクリプトを書いたが、データインターフェース、エージェント接続、監査ログに関する行は、スクリプトではなく、動いているシステムを試して得たものだ。四つの部分はいずれも、エージェントが ObjectStack アプリ自身の定義から読み取れるものに対応している。アクセスマトリクスのスナップショット、承認ステップ、公開フォームと各種の接続、監査の設定だ。新しいプロジェクトには、誰かが最初の一枚を作るまでスナップショットはない。エージェントが毎回読む指示にこの依頼を入れておけば、変更のたびにシートが付いてくる。

```text
With every change you make to this app, produce the sign-off sheet:
1. Who can see and change which records and fields (from the access-matrix snapshot).
2. Who can approve what: for each approval step, when it starts, who approves,
   what happens if nobody holds that role, and whether the requester can approve.
3. What is open to the outside: public forms and their fields, API and agent access,
   custom endpoints, outgoing calls to other systems.
4. What is recorded: change log, field history, record-view auditing.
Then list the lines that differ from the previous sheet, in plain words.
```

[コーディングエージェントを ObjectStack に向けるためのガイド](/en/blog/how-to-point-your-agent-at-objectstack/) では、こうした指示がエージェントに届く仕組みを説明している。ObjectStack では、アプリはプラットフォームが強制する書面の記述だ。そのため、ロール、承認、外部への入口、監査の設定はコードに散らばらず、一か所で宣言される。

自分で動かすなら、ObjectStack のリポジトリが ObjectOS Community を提供している。ghcr.io/objectstack-ai/objectstack イメージ、`os start`、Console で、無料かつセルフホストだ。ObjectOS Cloud はホスト型のエディション、ObjectOS Enterprise はセルフマネージドでライセンス制のエディションである。

**シートの生成スクリプト。** シートは、`os compile` が読み書きする二つのファイルから作る。コミット済みの `access-matrix.json` と、コンパイル結果の `dist/objectstack.json` だ。承認ノードの既定値は、仕様自身の `ApprovalNodeConfigSchema` で各ノードをパースして補っている。そのためシートには、作者が書いた値だけでなく、ランタイムが実際に適用する値が出る。

`sheet.mjs`、51 行：

```js
// Prints the four-part sign-off sheet for an ObjectStack app, from its compiled
// artifact and its committed access-matrix snapshot. Run from the app directory
// after `os compile`:  node sheet.mjs
import { readFileSync } from 'node:fs';
import { createRequire } from 'node:module';
const require = createRequire(`${process.cwd()}/package.json`);
const { ApprovalNodeConfigSchema } = require('@objectstack/spec/automation');

const app = JSON.parse(readFileSync('dist/objectstack.json', 'utf8'));
const matrix = JSON.parse(readFileSync('access-matrix.json', 'utf8')).entries;
const bits = (e) => ['create', 'read', 'edit', 'delete'].filter((b) => e[b]).join(' · ') || 'nothing';

console.log('1. Who can see and change which records and fields');
for (const pos of app.positions) {
  const sets = pos.permissionSets ?? [];
  console.log(`  ${pos.label} → ${sets.join(', ')}`);
}
for (const e of matrix) {
  const set = app.permissions.find((p) => p.name === e.permissionSet);
  const fieldRules = Object.keys(set?.fields ?? {}).length;
  console.log(`  ${e.permissionSet} | ${e.object} | ${bits(e)} | view all: ${e.viewAllRecords} | modify all: ${e.modifyAllRecords} | records: ${e.sharingModel} | field rules: ${fieldRules}`);
}

console.log('2. Who can approve what');
const approvalNodes = app.flows.flatMap((f) =>
  f.nodes.filter((n) => n.type === 'approval').map((n) => ({ f, n, cfg: ApprovalNodeConfigSchema.parse(n.config) })));
if (!approvalNodes.length) console.log('  no approval step in this app');
for (const { f, n, cfg } of approvalNodes) {
```
