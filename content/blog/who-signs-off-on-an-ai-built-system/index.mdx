**The short answer.** The head of the department that runs on the system signs it off, and signs one page, not the code. That page, the **sign-off sheet**, states four things: who can see and change which records, who can approve what, what is open to the outside, and what gets recorded. Ask for it before release and after every AI change; read only the changed lines. If nobody signs, the AI has made those decisions for you. It does not prove the system runs, the data is clean or the logic is right: a person still tests those.

*Measured on ObjectStack 18.5.0, the latest release on 17 November 2026, using the CRM example that ships with it. Every command and raw output is in [The proof](#the-proof).*

## Sign-off is not a code review

When an AI coding agent builds an internal system, two different questions need two different people.

A developer, or a reviewer working through [the review checklist for AI-generated app changes](/en/blog/how-to-review-ai-generated-app-changes/), answers *is this built correctly?*

The business owner answers *is this what we allow?* Who in my team can open a customer's record, who can allow a 35% discount on a deal, what can a stranger on the website do, and what will we be able to show an auditor next year. An AI agent will answer every one of these questions for you if nobody does, because a running system cannot leave them blank.

So the owner signs a statement of those decisions, in their language, produced from the system itself. That statement is the sheet.

## The sheet, before any change

Here is the sheet for the CRM example as it ships. Parts 1 and 2 were read from the app's own definition, as were the contact form's fields and the field-history line. The rest was confirmed by trying the running system. Where a part has its own in-depth post, the part links to it.

### 1. Who can see and change which records and fields

An app that has opted in keeps an **access-matrix snapshot**: a saved table of what each role can do to each kind of record. Every build rebuilds the table and stops if it differs from the saved copy, until a person accepts the change ([how the snapshot catches a silent permission change](/en/blog/catch-ai-silent-permission-change-access-matrix-gate/)). Translated into plain words, with roles (the platform calls them positions) as rows, the CRM's snapshot says (the last row is the platform's built-in administrator, which the snapshot does not list):

| Role | Can see | Can create and edit | Can delete | Whose records | Field limits |
|:--|:--|:--|:--|:--|:--|
| Sales Representative | accounts, contacts, leads, deals, deal lines, activities | the same six | nothing | everyone's | none |
| Sales Manager | same as a representative | same | nothing | everyone's | none |
| Finance Approver | same as a representative | same | nothing | everyone's | none |
| Website visitor (not signed in) | nothing | a new lead, through the contact form only | nothing | none | five fields (part 3) |
| Administrator | every record, plus setup | every record | every record (as the platform describes it; we deleted one) | everyone's | none |

**What a signer should spot:** the three staff roles are identical. A sales manager can do nothing a representative cannot, a representative can edit every deal in the company and not only their own, and no field on any record is hidden from anyone who can open it. All of that may be fine for a small team. It is still a decision, and this table is where you either make it or notice that someone made it without you.

### 2. Who can approve what

An **approval step** is a point where the system stops a change and waits for a named role to say yes or no.

| What needs approval | Who approves | Notes |
|:--|:--|:--|
| Nothing | — | One role is called Finance Approver and described as "authorised to approve discounts above 30%", but no approval step exists. |

**What a signer should spot:** a role whose description promises a control the system does not have. We tested it: a deal's discount went from 0% to 35% and saved, and nobody was asked. A separate rule does stop discounts above 40%, with the message "Discount cannot exceed 40% without an approved exception", and there is no way to get such an exception either.

### 3. What is open to the outside world

| Door | Who can use it | What it allows |
|:--|:--|:--|
| Website contact form | anyone, no sign-in | creates one new lead, from 5 of the lead's 13 fields: name, company, email, phone, title ([how a public form stays five fields wide](/en/blog/how-to-let-anonymous-visitors-submit-a-form/)) |
| Data interface (API), the address other software uses to read and write records | signed-in users only | exactly what that user's role allows; without a sign-in it refuses |
| AI agent connection (MCP), the standard way an AI assistant plugs into a system | anyone holding a key the system issued | acts as the person the key belongs to, with that person's access, per the platform's documentation (quoted in the proof); without a key it refuses |
| Built-in AI agents, other addresses or outgoing messages to other systems | — | none declared |

**What a signer should spot:** the AI agent connection is switched on by default. That makes "who has been issued a key" a question for your access reviews.

### 4. What is recorded

| What | Recorded? |
|:--|:--|
| Every new, changed or deleted record, with who, when, and the values before and after | Yes |
| Sign-ins | Yes |
| **Field history**, the list of past changes shown on a record's own page | On accounts, contacts, leads and deals; not on activities or deal lines |
| **Record views**, who opened which record | No; not switched on for any kind of record ([what view auditing records](/en/blog/prove-who-opened-a-customer-record-view-auditing/)) |

**What a signer should spot:** changes are recorded and opening a record is not. If your obligations include "who looked at this customer's file", that is a line to change before release, not after the first request from an auditor.

## One AI change, and the second sheet

Now the request a sales director might type to the agent: *"Discounts above 30% need Finance approval."*

The change is one new file of 38 lines and three changed lines elsewhere. The draft is deliberately minimal: an approval step on deals, routed to the Finance Approver role, taking the platform's default for everything the request did not mention. We added nothing to it to make the result more interesting. It passed the platform's 68 automatic checks. One of them printed a note that if nobody holds the role, the request goes to the administrators. It was a note, not a refusal.

The access-matrix snapshot was unchanged. Nobody's access changed, so the permission check stayed silent. The three decisions below sit in the approval step, which that check does not cover. Parts 1 and 3 of the sheet are the same as before. Part 2 changed, and part 4 gained lines:

| Line on the sheet | Before | After | What a signer asks |
|:--|:--|:--|:--|
| What needs approval | nothing | raising the discount on an **existing** deal above 30% | "And a new deal entered at 35%?" |
| Who approves | — | anyone holding the Finance Approver role | "Who holds it today?" |
| If nobody holds the role | — | the system's administrators decide | "Should our system administrators approve discounts?" |
| Can the person who asked approve it? | — | yes, if they hold the Finance Approver role | "Can Finance approve their own discounts?" |
| Can the deal be edited while it waits? | — | no, it is locked | "Is a locked deal acceptable while Finance decides?" |
| Recorded | changes and sign-ins | also each approval request, who decided, and when | Nothing to ask |

We tried each one on the running system:

| What we did | What the system answered | What it means for the business |
|:--|:--|:--|
| Created a brand-new deal with a 35% discount | Saved. No request. | Only edits start an approval. A new deal entered at 35% does not. |
| The administrator raised an existing deal to 35% | An approval request opened, assigned to the administrator, because on our fresh test install nobody held Finance Approver; the deal was locked | From the first day, the system's administrators approve discounts unless someone is given the role. |
| Fiona, given the Finance Approver role, raised another deal to 38% | A request opened with Fiona as its only approver (she was the only holder); she approved it, and the deal showed "approved" | The person who asked for the discount approved it herself. |
| Tried to edit the locked deal | Refused: "locked while an approval is in progress" | Nobody can change the deal while the approver is deciding. |
| Read the audit log | One row for the discount change, one for the request, one for Fiona's decision, each with who and when | Each of these decisions leaves a record, so it can be reviewed afterwards. |
| Tried 45% after the change | Still refused at the 40% cap | The "approved exception" in that message still does not exist. |

The draft did what the sentence asked. It also decided three things nobody asked about: that new deals are exempt, that a requester can approve their own discount, and that the system's administrators decide whenever nobody holds the Finance role. None of the three is a coding error, and all three are visible on the sheet in plain words.

## What the sheet does not prove

The sheet is a statement of what the system *allows*. Three things it cannot tell you, and someone still has to test them before release.

- **That it actually runs.** An earlier draft of this same change gave the same sheet, because the sheet does not look at which parts of the platform are switched on, and it passed the same checks. On the running system a 35% discount then saved and nobody was asked: the part that runs approvals was off. The only signs were a warning and an error in the server log. Only trying it showed that. Sign the sheet, then try every changed line once on a test copy.
- **That the data is right.** The sheet says who may edit a deal. It says nothing about whether the deals you imported from the old system have the right owners, no duplicates and no empty amounts. Data quality is checked by looking at the data.
- **That the business logic is right.** The sheet shows "above 30%". Whether 30% is your company's number, whether the threshold should apply to the total or per product line, and whether a 40% fixed limit with a promised-but-missing exception is acceptable are questions for the people who run the process. Test them with real cases.

The sheet lists four parts, not every rule. The 40% cap is not on it; we found it by trying.

The sheet names roles, not people. Review who holds each role on the same schedule as your access reviews.

## The fair objection: "IT should sign this, not me"

The case for leaving sign-off to IT is strong. IT understands the platform, already runs change approval for other systems, and a department head has other work.

What IT can certify is that the system matches what was asked for. It cannot certify that what was asked for is what the business accepts. "Finance approves discounts above 30%" was implemented faithfully, and the three decisions it carried came from the draft and the platform's defaults, not from anyone in IT. Someone who owns the discount policy has to say whether a self-approved 38% is fine. The workable split is to let IT sign the build and let the business owner sign the sheet.

A one-page sheet will be read quickly. That is why it is short: after the first release the owner reads only the changed lines.

## How to get the sheet for your own system

Ask your agent for it. ObjectStack 18.5.0 has no command that prints this sheet. We wrote a 51-line script for this post, and the rows about the data interface, the agent connection and the audit log came from trying the running system, not from the script. The four parts map to things an agent can read from an ObjectStack app's own definition: the access-matrix snapshot, the approval steps, the public forms and connections, and the audit settings. A new project has no snapshot until someone creates the first one. Put the request in the instructions the agent reads every time, so the sheet comes with every change:

```text
With every change you make to this app, produce the sign-off sheet:
1. Who can see and change which records and fields (from the access-matrix snapshot).
2. Who can approve what: for each approval step, when it starts, who approves,
   what happens if nobody holds that role, and whether the requester can approve.
3. What is open to the outside: public forms and their fields, API and agent access,
   custom endpoints, outgoing calls to other systems.
4. What is recorded: change log, field history, record-view auditing.
Then list the lines that differ from the previous sheet, in plain words.
```

The [guide to pointing your coding agent at ObjectStack](/en/blog/how-to-point-your-agent-at-objectstack/) covers how such instructions reach the agent. In ObjectStack an app is a written description that the platform enforces, so roles, approvals, public doors and audit settings are declared in one place instead of scattered through code.

To run it yourself, the ObjectStack repository ships ObjectOS Community: the ghcr.io/objectstack-ai/objectstack image, `os start` and the Console, free and self-hosted. ObjectOS Cloud is the hosted edition, and ObjectOS Enterprise the self-managed, licensed one.

`sheet.mjs`, 51 lines:

```js
// Prints the four-part sign-off sheet for an ObjectStack app, from its compiled
// artifact and its committed access-matrix snapshot. Run from the app directory
// after `os compile`:  node sheet.mjs
import { readFileSync } from 'node:fs';
import { createRequire } from 'node:module';
const require = createRequire(`${process.cwd()}/package.json`);
const { ApprovalNodeConfigSchema } = require('@objectstack/spec/automation');

const app = JSON.parse(readFileSync('dist/objectstack.json', 'utf8'));
const matrix = JSON.parse(readFileSync('access-matrix.json', 'utf8')).entries;
const bits = (e) => ['create', 'read', 'edit', 'delete'].filter((b) => e[b]).join(' · ') || 'nothing';

console.log('1. Who can see and change which records and fields');
for (const pos of app.positions) {
  const sets = pos.permissionSets ?? [];
  console.log(`  ${pos.label} → ${sets.join(', ')}`);
}
for (const e of matrix) {
  const set = app.permissions.find((p) => p.name === e.permissionSet);
  const fieldRules = Object.keys(set?.fields ?? {}).length;
  console.log(`  ${e.permissionSet} | ${e.object} | ${bits(e)} | view all: ${e.viewAllRecords} | modify all: ${e.modifyAllRecords} | records: ${e.sharingModel} | field rules: ${fieldRules}`);
}

console.log('2. Who can approve what');
const approvalNodes = app.flows.flatMap((f) =>
  f.nodes.filter((n) => n.type === 'approval').map((n) => ({ f, n, cfg: ApprovalNodeConfigSchema.parse(n.config) })));
if (!approvalNodes.length) console.log('  no approval step in this app');
for (const { f, n, cfg } of approvalNodes) {
  const start = f.nodes.find((x) => x.type === 'start')?.config ?? {};
  console.log(`  ${f.label} / ${n.label} | object: ${start.objectName} | when: ${start.triggerType} if ${start.condition}`);
  console.log(`    approvers: ${cfg.approvers.map((a) => `${a.type}:${a.value ?? ''}`).join(', ')} | decides: ${cfg.behavior}`);
  console.log(`    nobody staffed → ${cfg.onEmptyApprovers} | requester removed from approvers: ${cfg.excludeSubmitter === true} | record locked while pending: ${cfg.lockRecord}`);
}
const routed = new Set(approvalNodes.flatMap(({ cfg }) => cfg.approvers.filter((a) => a.type === 'position').map((a) => a.value)));
for (const pos of app.positions) {
  if (/approv/i.test(`${pos.label} ${pos.description ?? ''}`) && !routed.has(pos.name))
    console.log(`  position "${pos.label}" says: "${pos.description}" — no approval step routes to it`);
}

console.log('3. What is exposed to the outside');
for (const v of app.views) for (const [name, fv] of Object.entries(v.formViews ?? {})) {
  if (fv.sharing?.allowAnonymous) {
    const fields = fv.sections.flatMap((s) => s.fields.map((x) => x.field));
    console.log(`  public form ${fv.sharing.publicLink} | creates: ${fv.data.object} | ${fields.length} fields: ${fields.join(', ')}`);
  }
}
for (const k of ['agents', 'apis', 'webhooks', 'connectors', 'portals']) console.log(`  ${k} declared: ${(app[k] ?? []).length}`);

console.log('4. What is recorded');
for (const o of app.objects) console.log(`  ${o.name} | field history on record page: ${o.enable?.trackHistory === true}`);
console.log(`  plugins configured in the app (record-view audit lives here): ${(app.plugins ?? []).length}`);
```

The trigger follows the platform's own worked approval example in `examples/app-showcase`, which also starts on `record-after-update`. The `requires` line took two drafts. Without `'triggers'`, `os validate` refused the app:

```text
✗ flow 'crm_discount_approval' declares a 'record_change' trigger but `requires` does not include 'triggers' — no 'record_change' trigger would be registered, so the flow would never auto-launch.
```

With `'triggers'` but without `'approvals'`, `os validate` passed and so did the sheet. On the running app the 35% edit saved with `approval_status` still `null`, `/api/v1/approvals/requests` stayed empty, and the server log carried:

```text
WARN [Automation] 1 flow(s) reference node types no installed plugin provides (approval) — install/enable the plugin that contributes them (e.g. 'approval' ⇐ @objectstack/plugin-approvals).
```
