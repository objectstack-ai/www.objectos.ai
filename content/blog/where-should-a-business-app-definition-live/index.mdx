If AI agents are going to change your business software, keep the authoritative definition of that software (its records, fields, permissions and approval rules) as files in a repository your company controls, and build the running system from those files. The payoff is accountability: every change arrives as a dated, attributed before-and-after with a written reason, so "who let sales do that, and why?" takes a minute to answer, not a meeting. The price is maturity. The established metadata platforms bring years of production use, packaged apps and partners; a repository-first platform asks you to build more yourself.

*Measured on ObjectStack 18.5.0, the version `npm create objectstack@latest` installs today: the git history of its open-source CRM example at the release tag, and the published 18.5.0 command-line tool run against that example. Every command is in [The proof](#the-proof).*

## Configuration or definition: which copy wins?

Both kinds of platform do the same visible job. You describe your business (customers, deals, who may edit what) and the platform turns that description into database tables, screens and an API. ObjectStack's own comparison page calls the platforms that work this way ["the closest relatives"](https://github.com/objectstack-ai/objectstack/blob/b914e7247f692a79804f9b7eba278add46d57625/content/docs/concepts/compare.mdx#L58-L73): "Salesforce's metadata is the ancestor; open-source cousins include Frappe Framework with ERPNext, Odoo, NocoBase, Payload and Twenty." It names the difference in one sentence:

> Where the definition lives, and who it is written for. In most of these platforms metadata is configuration stored in the platform's database and edited through its UI; where it is code, as with the Payload Config or Odoo's modules, it is framework code.

The useful question for a buyer is narrower than "metadata or code". It is: **which copy is authoritative?** The authoritative copy is the one that wins when the running system and any other copy disagree.

- **Configuration.** The running system's database holds the authoritative copy. You change the system by changing it, usually through an admin screen, and any file you keep is a copy of what is running.
- **Definition.** A set of files in your repository holds the authoritative copy, and the running system is built from them. You change the system by changing a file, and the change takes effect when it is built and deployed.

A repository is a version-controlled folder, usually hosted on GitHub or GitLab, that keeps every change as a before-and-after with an author, a date and a message. A pull request is a proposed change shown that way, which someone merges. Both kinds of platform can keep history; this post makes no claim about any vendor's own change tracking, so check it for the platform you are weighing. What the choice decides is where "what is true right now, and since when?" gets answered, and whether a change can be read and approved before it takes effect.

That matters more now that an AI agent writes many of the changes. In the example below, an AI coding agent is recorded as co-author on every one of the seven changes to the sales roles' permission file.

## One permission change, traced

ObjectStack's repository ships an open-source CRM example, a demonstration app rather than a customer system. In August 2026 its sales role could open deals but could not add product lines to them: the platform refused every non-admin user who tried. The fix added one line to the permission file. We put to that file's history the questions an auditor or a finance lead would ask, then undid the fix on today's release to see what would stop it.

| What we asked | What the repository or the build answered | What it means for the owner |
|:--|:--|:--|
| How often has the sales roles' permission file changed? | 7 times, from its creation on 9 July 2026 to a rename on 6 November. Each change has a date, an author, a numbered pull request and a written reason. | The audit question is answered from the file's own history, not from anyone's memory. |
| Who wrote those changes? | An AI coding agent is recorded as co-author on all 7. Across the whole CRM definition, it co-wrote 49 of the 50 changes since 1 July. | AI is already writing the definition, and the record says so. |
| Who approved them? | Each was merged by a named account. One of the 7 pull requests has a formal review recorded; the other six were merged without one. | A repository does not create review. It makes a missing review visible. |
| Why can sales add product lines to a deal? | One added permission line, with a comment explaining it, on 12 August 2026, in pull request 8228. Its message says sales users were refused on deals they otherwise fully owned. | The answer is one line, with its reason attached. |
| What did that do to who-can-do-what? | One entry added to the app's committed access table: sales may create, read and edit product lines, not delete them. | The reviewer signs a row in a table, not a block of code. |
| What if someone quietly removes that line today? | The definition check still passes, with a warning that non-admin users will be refused. The build stops and names the loss (below). | A permission change cannot ship unnoticed, but the check does not decide whether the change is right. |
| What if we accept the removal on purpose? | Regenerating the table produces, byte for byte, the table from before the August fix. | Who-could-do-what is reproducible from the definition at any point in its history. |

The build's refusal reads like this:

```text
✗ Access matrix drift (1 change) — capability changes must be reviewed
• 'crm_sales_user' loses ALL access to 'crm_opportunity_line_item' (entry removed)
If intended, re-run with --update-access-matrix and commit the snapshot — its diff IS the review artifact.
```

The "access matrix" is that committed table: one row per role and record type, listing what the role can create, read, edit and delete. The build works the table out again from the definition every time and refuses to finish when the two differ, until a person regenerates the table and commits it. The diff of that table is what a reviewer approves. The mechanism, line by line, is in [How do you catch an AI's silent permission change before it ships?](/en/blog/catch-ai-silent-permission-change-access-matrix-gate/)

## What the metadata platforms do better

The case for the established platforms is strong, and ObjectStack's documentation makes it in its own words. What they are good at: ["building business applications quickly on a proven runtime, with packaged apps, modules and integrations to start from."](https://github.com/objectstack-ai/objectstack/blob/b914e7247f692a79804f9b7eba278add46d57625/content/docs/concepts/compare.mdx#L65-L66) Where they start ahead:

> Salesforce, Odoo and ERPNext bring years of production use, packaged applications, app marketplaces and implementation partners. ObjectStack is younger; expect to build more of it yourself.
> — [ObjectStack docs, "Where the others are stronger"](https://github.com/objectstack-ai/objectstack/blob/b914e7247f692a79804f9b7eba278add46d57625/content/docs/concepts/compare.mdx#L115-L117)

Three more points belong on their side of the ledger:

- **Agents can reach them too.** The same page says ["several of them now offer MCP servers, so agents can reach them too."](https://github.com/objectstack-ai/objectstack/blob/b914e7247f692a79804f9b7eba278add46d57625/content/docs/concepts/compare.mdx#L62-L63) MCP is the open standard through which AI agents call a system's tools.
- **Storing logic as data is the normal shape, not a flaw.** ObjectStack keeps its own small pieces of business logic as data, and its docs say plainly whose choice that copies: ["the same trade-off ServiceNow made (Business Rules), Salesforce made (Formulas + Apex Triggers stored as metadata), Retool made (transformer JS strings), and Airtable made (Scripting blocks). It's the standard low-code shape."](https://github.com/objectstack-ai/objectstack/blob/b914e7247f692a79804f9b7eba278add46d57625/content/docs/automation/hook-bodies.mdx#L61) So the difference is not whether a platform uses metadata. ObjectStack is a metadata platform. The difference is where the authoritative copy is versioned.
- **An admin screen needs no repository.** On a configuration platform, a business administrator can add a field at lunchtime without a pull request, a build or a deployment. For many teams that is the point.

If you already run on one of these platforms, its gravity is a real reason to stay, and our posts on [Power Platform and Dataverse](/en/blog/power-platform-lock-in-dataverse-self-host/) and on [Retool](/en/blog/retool-vs-ai-native-app-platform/) weigh specific products. The [comparison page](/en/compare/) covers this category in one paragraph; this post is the long version.

## How to choose

**Start from a configuration platform** when you need packaged apps, a marketplace and implementation partners this quarter; when the people changing the system are administrators working in its screens; and when your auditors accept the platform's own change records.

**Keep the definition in a repository** when AI agents will write most of the changes and a person has to answer for each one; when a permission change must come with a reason and a readable before-and-after; and when you want the definition of your business to be files your company holds, not rows in someone else's system. The README puts that last point this way: ["The definition lives in your repository as ordinary TypeScript, versioned in your VCS and reviewable as a diff — not a graph held inside a vendor's system."](https://github.com/objectstack-ai/objectstack/blob/b914e7247f692a79804f9b7eba278add46d57625/README.md#L197-L199)

Whichever you pick, ask the vendor three questions:

1. Which copy is authoritative: the running system or a file?
2. Can I get every permission change as a readable before-and-after, with an author and a reason, before it takes effect?
3. When the running system and the file disagree, which one wins, and who finds out?

## What a repository does not solve

- **It does not decide whether a change is right.** When we removed the August fix, the definition check passed with a warning. Only the access table stopped the build, and only because this app has one: the table is opt-in per app, and an app without it would have built. A person still has to decide that sales should or should not touch product lines.
- **It does not create review.** Six of the seven pull requests above were merged with no formal review recorded. The repository shows that gap; closing it takes a rule in the repository's settings that requires an approval before merging.
- **ObjectStack keeps some configuration too.** Views, dashboards, reports, translations and email templates can be edited in a running environment's console. Those edits are stored in that environment's database and [take precedence over the repository's version](https://github.com/objectstack-ai/objectstack/blob/b914e7247f692a79804f9b7eba278add46d57625/content/docs/concepts/metadata-lifecycle.mdx#L43), with their own history table. Most item types, permission sets included, can also be [created at runtime through the API](https://github.com/objectstack-ai/objectstack/blob/b914e7247f692a79804f9b7eba278add46d57625/packages/spec/src/kernel/metadata-plugin.zod.ts#L348). Those are configuration in exactly this post's sense, so which changes must go through the repository is a policy you set.
- **Someone has to work the repository.** In practice that is your agent plus one reviewer who reads diffs, but it is still a skill a configuration platform does not ask for.

## Point your agent at the definition

If the authoritative copy should be files, the agent writing your software needs a target that is files: a typed definition it can generate, that a person can review as a small diff, and that a runtime enforces. That is the job ObjectStack is built for; [point your agent at ObjectStack](/en/blog/how-to-point-your-agent-at-objectstack/) to try it on your own process. For the vocabulary, see the [definition layer](/en/glossary/definition-layer/), [application definition versus runtime](/en/glossary/application-definition-vs-runtime/), and [what "the ontology is the software" means](/en/blog/what-does-the-ontology-is-the-software-mean/).

### 5. Undo it on 18.5.0

$ npm install
$ npx os --version

$ npx os compile; echo $?
