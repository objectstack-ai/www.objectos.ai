**짧은 답.** AI가 만든 구매 승인 흐름을 믿기 전에 사본에서 세 가지를 시험해 보세요. 각 요청을 누가 승인했고 시스템이 다른 사람이었다면 거부했을지, 승인자가 부재중이거나 금액이 한도를 넘으면 어떻게 되는지, 그리고 나중에 경로를 다시 구성할 수 있는지입니다. 승인 기능이 내장된 플랫폼은 첫째를 강제하고 셋째를 기록합니다. 둘째는 정책이고, 승인 후 무엇을 바꿀 수 있는지까지 포함해 여전히 당신이 정할 일입니다. 우리 테스트에서는 승인된 2,400 요청이 24,000으로 수정되었는데도 승인 상태로 남았고, 승인된 금액을 확정하는 규칙 하나를 더한 뒤에야 막혔습니다.

*ObjectStack 18.6.0(2026년 11월 27일 실행 당시 최신 릴리스)에서 공식 스타터로 만든 새 프로젝트로 측정했습니다. 모든 명령과 원본 출력은 [증거](#증거)에 있습니다.*

## 믿기 전에 던질 세 가지 질문

구매 승인은 운영 책임자라면 누구나 아는 흐름입니다. 누군가 무언가를 사겠다고 요청하고, 상사가 승인하거나 반려하며, 일정 금액을 넘으면 재무팀도 동의해야 합니다. AI 코딩 에이전트는 이 흐름을 한 문장으로 작성할 수 있습니다. 알아야 할 것은 작성할 수 있느냐가 아니라, 정작 중요한 날에 그 결과가 무엇을 하느냐입니다.

질문 세 가지면 충분합니다.

1. **누가 승인했고, 그럴 자격이 있었나?** "누구 이름이 적혀 있나"가 아니라, 다른 사람이었다면 시스템이 거부했을지입니다.
2. **승인자가 부재중이거나 금액이 기준을 넘으면 어떻게 되나?** 휴가 간 사람을 2주 동안 기다리는 요청은, 아무도 잘못하지 않았더라도 실패한 승인입니다.
3. **한 달 뒤에 전체 경로를 증명할 수 있나?** 누가 요청했고, 각 단계를 누가 결정했고, 누가 누구를 대신했으며, 정확히 무엇이 승인되었는지.

이 글은 흐름을 운영하는 이야기입니다. 흐름 자체를 가동할지, 누가 그것을 승인할지는 다른 결정이며 [AI가 만든 시스템은 누가 승인하는가](/ko/blog/who-signs-off-on-an-ai-built-system/)에서 다룹니다.

## 우리가 만든 흐름, 쉬운 말로

우리가 요청한 것은 대부분의 작은 회사가 처음 쓰는 규칙입니다. *모든 구매 요청은 요청자의 상사에게 간다. 10,000을 넘으면 재무팀에도 간다.* 새 ObjectStack 프로젝트에서 이것은 하나의 레코드 유형(무엇을, 공급업체, 금액, 사유가 담긴 구매 요청), 하나의 **승인 흐름**(시스템이 각 단계에서 멈추고 지정된 사람이 승인하거나 반려하기를 기다리는 일련의 단계), 그리고 두 개의 **역할**(요청을 올릴 수 있는 직원, 재무 승인자)이 되었습니다.

두 가지 선택은 플랫폼이 아니라 우리가 했습니다. 두 단계 모두에서 요청을 제출한 사람은 승인할 수 없도록 지정했습니다. 플랫폼은 켜지 않는 한 이 옵션을 꺼 둡니다([자체 설명](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/packages/spec/src/automation/approval.zod.ts#L1118-L1123)에 "Off by default"라고 되어 있습니다). 다만 이번 실행에서는 이 설정이 작동할 일이 없었습니다. Alice가 자기 요청의 승인자가 된 적이 없었기 때문입니다. 그리고 첫 단계는 "요청자의 상사"에게 보냈는데, 플랫폼은 관리자가 각 사람에게 설정하는 상사 연결에서 이 사람을 읽어 옵니다.

그런 다음 네 사람(요청하는 Alice, 그녀의 상사 Mark, 재무팀 Fiona, 대신할 수 있는 동료 Dana)을 넣고 돌려 보았습니다.

| Alice가 18,000어치 소프트웨어 라이선스를 요청했다. Mark가 승인한 뒤 재무 단계까지 승인하려 했다. | Mark의 승인으로 Fiona를 위한 두 번째 단계가 열렸다. 재무 단계에 대한 Mark의 시도: 존재하지 않는 것처럼 응답했다. Fiona가 사유를 달아 반려했고 요청은 "반려됨"이 되었다. | 10,000을 넘으면 상사의 승인만으로는 부족하고, 상사가 재무팀의 몫을 대신할 수도 없다. |
| Mark가 12월 2일까지 부재를 등록하고 Dana를 대리인으로 지정했다. Alice가 3,000어치 콘퍼런스 티켓을 요청했다. | 요청은 곧바로 Dana에게 갔고, 기록에는 인계와 Mark가 적은 사유 "Annual leave"가 남았다. Mark는 처리할 수 없었고 Dana가 승인했다. | 상사가 자리를 비운 동안에도 상사 승인은 계속 진행되고, 인계도 기록에 남는다. |

| 관리자가 사유를 적고 12월 2일까지 Dana에게 재무 역할을 주었다. Alice가 15,000어치 의자를 요청했다. | 재무 단계는 Fiona와 Dana 모두에게 갔고 Dana가 승인했다. 이미 대기 중이던 노트북 요청은 Fiona에게 남았다. | 역할 대행은 작동하지만, 준비한 뒤에 열린 요청에만 적용된다. |

두 행은 다시 볼 만합니다.

### 승인 후 수정

이렇게 부르는 이유는 승인은 한순간에 일어나고, 레코드는 그 뒤로도 계속 살아 있기 때문입니다. 우리 흐름은 AI 코딩 에이전트가 그 한 문장으로 작성했고, 한 번만 시작됩니다. 요청이 생성될 때입니다. 나중에 요청을 수정해도 다시 시작되지 않습니다. 그 문장에는 승인된 요청에서 무엇을 아직 바꿀 수 있는지가 없었기에, 플랫폼은 우리가 선언한 대로만 정확히 움직였습니다. 감사 로그가 변경을 잡았으니 나중에 증명은 할 수 있지만, 막은 것은 아무것도 없었습니다. 승인된 금액을 확정할지, 공급업체가 바뀌면 요청을 다시 열지, 5% 미만 변경은 허용할지 모두 당신의 결정입니다. 적어 두고, 그 규칙을 에이전트에게 건네세요. 우리는 하나를 건넸습니다. 승인된 금액은 확정이다. 다음 시도는 거부되었습니다.

### 재무 승인자의 부재

대리 승인, 즉 플랫폼의 부재 시 인계는 "사람"을 따라갑니다. 우리 재무 단계는 역할을 가리켰으므로 Fiona의 부재로는 아무것도 옮겨지지 않았습니다. 플랫폼 문서는 [그렇게 밝히고](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/content/docs/automation/approvals.mdx#L1187-L1194) 다른 길도 알려 줍니다. 기간을 정해 다른 사람을 그 역할에 두는 것입니다. 그렇게 하자 다음 요청은 두 사람 모두에게 갔습니다. 우리가 시험하지 않은 길이 두 가지 더 있습니다. 승인자는 대기 중인 요청 하나를 다른 사람에게 넘길 수 있고, 관리자는 막힌 요청을 결정하거나 재배정할 수 있습니다([문서는 여기](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/content/docs/automation/approvals.mdx#L975-L990)).

설정 단계 하나가 우리를 놀라게 했습니다. 첫 실행에서 Mark는 부재를 아예 등록할 수 없었습니다. 직원에게 부재 레코드 권한을 줄 때까지 플랫폼이 그를 거부했습니다. 문서는 이 기능을 셀프서비스라고 부릅니다. 권한을 주고 나면 그렇지만, 그 권한 자체가 누가 자기 승인을 다른 사람에게 넘길 수 있는지에 대한 또 하나의 결정입니다.

## 한 달 뒤에 경로를 증명하기

플랫폼이 무엇을, 어디에 남겼나:

- **각 결정**이 별도의 기록으로: 단계, 동작(제출, 승인, 반려, 인계), 수행자 이름, 코멘트, 시각. 인계 기록에는 두 사람과 제시된 사유가 적힙니다.
- **무엇이 승인되었나**: 각 요청은 제출 당시 구매 내용의 사본을 가지고 있어서, Fiona의 반려는 오늘 레코드에 무엇이 적혀 있든 18,000에 묶여 있습니다.
- **각 요청이 거친 경로**: 재시작 후 읽은 흐름 실행 기록을 보면 2,400과 3,000은 재무를 건너뛰었고 18,000과 12,500은 재무에 도달했습니다. 플랫폼 문서는 [이 기록을 영구 보관된다고 설명하며](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/content/docs/automation/flows.mdx#L1811-L1820), 우리가 본 것도 그랬습니다. 15,000 요청은 이 조회 뒤에 올렸고, 그 결정 기록에는 두 단계가 모두 나옵니다.
- **구매 레코드 자체의 모든 변경**이, 승인 후 수정까지 포함해 감사 로그에.
- **누가 승인할 수 있었나**: 요청이 결론 나면 요청 자체에는 더 이상 승인자가 나오지 않습니다. 그 목록은 감사 로그의 행으로 남습니다. 감사인이 "다른 누군가도 승인할 수 있었나?"라고 물으면 답은 거기에 있습니다.

잘못 읽기 쉬운 점이 하나 있습니다. Mark가 18,000 요청을 승인했을 때 상태가 잠깐 "승인됨"으로 보였다가 재무 단계가 다시 "대기"로 돌렸습니다. 그래서 나중에 Fiona가 반려한 요청의 상태 이력에는 "승인됨"이라는 말이 들어 있습니다. 상태 이력이 아니라 결정 기록을 읽으세요.

재시작은 한 달이 아닙니다. 우리가 증명한 것은 기록이 저장되고 재시작 후에도 남아 있다는 것입니다. 얼마나 오래 보관되고 누가 지울 수 있는지는 보존 설정과 데이터베이스 백업에 달렸으며, 이번에 측정한 범위가 아닙니다.

## 스프레드시트와 이메일, 또는 구매 전용 제품을 위한 변론

한 달에 구매 요청이 몇 건뿐인 팀이라면 공유 스프레드시트와 상사에게 보내는 이메일은 진지한 답입니다. 설정이 필요 없고, 모두 쓸 줄 알며, 이메일 스레드는 그럴듯한 기록이 됩니다. 할 수 없는 것은 거부입니다. 누구나 셀에 "승인"이라고 쓸 수 있고, 이메일은 곁에 있는 누구에게나 전달될 수 있으며, 승인 후 바뀐 숫자는 누군가 버전을 보관하지 않는 한 흔적을 남기지 않습니다. 회사에서 그런 점을 확인하려는 사람이 없다면 스프레드시트가 더 저렴합니다.

구매 전용 제품은 반대편 끝에 있습니다. 공급업체 카탈로그, 예산, 발주서, 송장 대조에 더해, 구매팀이 오랜 세월 다듬어 온 승인 한도와 대리 규칙을 갖추고 있습니다. 구매가 회사 업무의 큰 부분이라면 그 깊이는 돈을 낼 가치가 있고, 범용 플랫폼 위의 승인 흐름으로는 대신할 수 없습니다.

AI가 만든 흐름이 맞는 곳은 그 중간입니다. 자기 시스템에 속하고 자기 레코드에 묶인 승인으로, 별도 제품을 설정하는 대신 에이전트에게 요청하고 작은 변경을 검토하는 방식으로 바꾸고 싶은 경우입니다.

## ObjectStack이 대신 결정해 주지 않는 것

- **대리 정책.** 플랫폼은 각자가 자기 대리인만 지정할 수 있도록 강제합니다. 누가 대리인이 될 수 있는지, 얼마나 오래, 얼마까지인지는 정하지 않습니다. 우리는 Dana가 Mark 대신 승인할 수 있는 범위에 한도를 두지 않았고, 플랫폼도 요구하지 않았습니다. 시험한 것은 3,000 요청 한 건입니다. 플랫폼 자체 메모는 [대리 거버넌스와 직무 분리](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/packages/plugins/plugin-approvals/src/sys-approval-delegation.object.ts#L28-L32), [승인 매트릭스 거버넌스](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/content/docs/automation/approvals.mdx#L215)를 엔터프라이즈 영역으로 두며, 우리가 시험한 범위에 들지 않습니다. 엔터프라이즈 에디션이 무엇을 제공하는지는 확인하지 않았습니다.
- **결재 한도.** 10,000 기준은 우리가 흐름에 써 넣은 분기입니다. Mark는 5,000까지, 그의 이사는 50,000까지 승인할 수 있다면 그 표는 당신이 써야 합니다.
- **"승인됨"이 무엇을 고정하는지.** 승인 후 수정을 보세요.
- **회사 달력을 따르는 기한.** 단계는 정해진 시간이 지나면 에스컬레이션될 수 있지만, 그것은 [실제 시계 시간](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/content/docs/automation/approvals.mdx#L1125-L1143)입니다. 밤과 주말도 셈에 들고, 업무 시간 달력은 제공되지 않습니다. 에스컬레이션은 실행하지 않았습니다.
- **알림.** 플랫폼은 설치한 메시징 서비스를 통해 승인자에게 알립니다. 전달은 시험하지 않았습니다.
- **구매 그 자체.** 직접 만들지 않는 한 발주도, 공급업체 관리도, 예산 확인도 하지 않습니다.

## 에이전트에게 세 가지 질문을 건네세요

에이전트가 승인 흐름을 만들거나 바꾼다면, 질문을 상시 지침으로 건네세요. 그러면 빈틈 찾기를 당신에게 맡기는 대신, 변경할 때마다 답이 함께 돌아옵니다.

```text
승인 흐름을 추가하거나 바꿀 때마다 쉬운 말로 답할 것:
1. 각 단계는 누가 승인하고, 누가 거부되는가(요청자 본인 포함)?
2. 승인자가 부재중이면 어떻게 되는가: 사람에게 가는 단계와
   역할에게 가는 단계 각각에 대해. 각 금액 기준을 넘으면 어떻게 되는가?
3. 승인 후에도 바꿀 수 있는 필드는 무엇이며, 바꾸면 승인이 다시 열리는가?
그다음 각 결정이 어디에 기록되는지 나열하고, 테스트 사본에서
승인 요청 하나와 반려 요청 하나를 시험할 것.
```

[코딩 에이전트를 ObjectStack에 맞추는 가이드](/en/blog/how-to-point-your-agent-at-objectstack/)는 이런 지침이 에이전트에 닿는 방식을, [오래 걸리는 승인이 버텨야 하는 것](/en/blog/automation-pause-resume-approvals/)은 흐름이 며칠 동안 결정을 기다려도 제자리를 잃지 않는 이유를 다룹니다. ObjectStack에서 승인 흐름은 플랫폼이 강제하는 짧은 서술이므로, 위의 답은 코드에서 짜 맞추는 대신 파일 하나에서 읽어 낼 수 있습니다.

```ts

// Every purchase request goes to the requester's manager.

export const PurchaseApprovalFlow = defineFlow({

  label: 'Purchase Request Approval',

  type: 'autolaunched',
  status: 'active',

    {
      id: 'start',
      type: 'start',
      label: 'On New Request',
      config: {
        objectName: 'purchasing_request',
        triggerType: 'record-after-create',
        condition: 'amount != null && amount > 0',
      },
    },
    {
      id: 'manager_review',
      type: 'approval',
      label: 'Manager Review',
      config: {
        approvers: [{ type: 'manager' }],
        excludeSubmitter: true,
        approvalStatusField: 'approval_status',
      },
    },
    { id: 'over_threshold', type: 'decision', label: 'Above 10,000?' },
    {
      id: 'finance_review',
      type: 'approval',
      label: 'Finance Review',
      config: {
        approvers: [{ type: 'position', value: 'purchasing_finance' }],
        excludeSubmitter: true,
        approvalStatusField: 'approval_status',
      },
    },
    { id: 'approved', type: 'end', label: 'Approved' },
    { id: 'rejected', type: 'end', label: 'Rejected' },
  ],
  edges: [
    { id: 'e1', source: 'start', target: 'manager_review' },
    { id: 'e2', source: 'manager_review', target: 'over_threshold', label: 'approve' },
    { id: 'e3', source: 'manager_review', target: 'rejected', label: 'reject' },
    { id: 'e4', source: 'over_threshold', target: 'finance_review', label: 'true', condition: 'amount > 10000' },
    { id: 'e5', source: 'over_threshold', target: 'approved', label: 'false', condition: 'amount <= 10000' },
```
