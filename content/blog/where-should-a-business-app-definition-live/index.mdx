If AI agents change your business software, keep the master copy of its rules as files in a repository you control, and build the running system from them. Every change arrives as a dated, signed before-and-after with a written reason, so "who let sales do that, and why?" is answered from the record, not memory. The price is twofold. Established platforms like Salesforce and Odoo bring years of production use, packaged apps and partners; repository-first means building more yourself. And every change has to be proposed and accepted in the repository, a step an admin screen does not ask for.

*Measured on ObjectStack 18.6.0, the version a new install gets today: the git history of its open-source CRM example at the release tag, and the published 18.6.0 command-line tool run against that example. Every command is in [The proof](#the-proof).*

## Configuration or definition: which copy wins?

Both kinds of platform do the same visible job. You describe your business (customers, deals, who may edit what) and the platform turns that description into database tables, screens and a programming interface (an API). A platform that works this way is called a metadata platform: the description it runs from is metadata, data about your data. ObjectStack's own [comparison page](/en/compare/) calls these platforms ["the closest relatives"](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/content/docs/concepts/compare.mdx#L58-L73): "Salesforce's metadata is the ancestor; open-source cousins include Frappe Framework with ERPNext, Odoo, NocoBase, Payload and Twenty." It names the difference in one sentence:

> Where the definition lives, and who it is written for. In most of these platforms metadata is configuration stored in the platform's database and edited through its UI; where it is code, as with the Payload Config or Odoo's modules, it is framework code.

Framework code here means code written for that one platform. The useful question for a buyer is narrower than "metadata or code". It is: **which copy is authoritative?** The authoritative copy is the one that wins when the running system and any other copy disagree.

- **Configuration.** The running system's database holds the authoritative copy. You change the system by changing it, usually through an admin screen, and a file, if you keep one, describes what is running.
- **Definition.** A set of files in your repository holds the authoritative copy, and the running system is built from them. You change the system by changing a file, and the change takes effect after the build, the step that turns the files into the running system.

These are two ways of working, not two lists of vendors. Several of the platforms named above can also be run from files; ask each vendor which way its customers actually work. ObjectStack, which publishes this post, is the repository-first kind.

![Two ways to keep a business app's rules. On the left, a definition: the files in your repository are the authoritative copy, and every change to them is a diff with a name and a written reason; the build checks the files and turns them into the running system, which is rebuilt from them at each deploy. On the right, configuration: an administrator changes settings in an admin screen, the running system and its database are the authoritative copy, and a file, if you keep one, describes what is running](./two-copies-en.svg)

A repository is a version-controlled folder, usually hosted on GitHub or GitLab, that keeps every change as a before-and-after with an author, a date and a message. That before-and-after is called a diff. A pull request is a proposed change shown that way, which someone accepts into the main copy. Both kinds of platform can keep history; this post makes no claim about any vendor's own change tracking, so check it for the platform you are weighing. What the choice decides is where "what is true right now, and since when?" gets answered, and where a change is read before it takes effect: in a file's history, or in the platform's own records and tools.

That matters more now that an AI agent writes many of the changes. In the example below, an AI coding agent is recorded as co-author on every one of the seven changes to the sales roles' permission file.

## One permission change, traced

ObjectStack's repository ships an open-source CRM example, a demonstration app rather than a customer system. In August 2026 its sales role could open deals but could not add product lines to them: the platform refused every user who was not an administrator. The fix added one permission line, and one row to the app's access table: a list, saved in the repository, of what each role may create, read, edit and delete. We put to the permission file's history the questions an auditor or a finance lead would ask, then undid the fix on today's release to see what would stop it.

| What we asked | What the record answered | What it means for you |
|:--|:--|:--|
| How often has the sales roles' permission file changed? | 7 times since it took its current name on 9 July 2026, most recently on 6 November. Each change has a date, an author, a numbered pull request and a written reason. | The audit question is answered from the file's own history, not from anyone's memory. |
| Who wrote those changes? | An AI coding agent is recorded as co-author on all 7. Across the CRM example's source files, 49 of the 50 changes since 1 July 2026 carry the same co-author line (71 of 218 over the example's whole history, which starts in February 2026). | AI is already writing the definition, and the record says so. |
| Who approved them? | GitHub's review record shows an approval on 1 of the 7 pull requests. The other 6 have no review record. Three were opened and merged by the same person's account, two were opened and merged by the project's automation account, and one was opened by an AI agent's account and merged by a person's account. | A repository does not create review. It shows, change by change, whether one was recorded, and here it shows that ours mostly was not. |
| Why can sales add product lines to a deal? | One permission line and one new row in the access table, 12 August 2026, [pull request 8228](https://github.com/objectstack-ai/objectstack/pull/8228), with the reason written down: sales users were refused on deals they otherwise fully owned. | The answer is one line and one table row, with its reason attached. The reviewer signs a row in a table, not a block of code. |
| What if someone quietly removes that line today? | The platform's first check, which reads the files for mistakes, still passes, with a warning that every user who is not an administrator will be refused. The build stops and names the loss (below). | In an app that keeps this table, removing a role's access to a record type stops the build until a person regenerates the table. The check does not decide whether the change is right. |
| What if we accept the removal on purpose? | Regenerating the table produces the table from before the August fix, exactly, character for character. | Who-could-do-what is reproducible from the definition at any point in its history. |

A formal review here means a review record on the pull request in GitHub: an approval, a request for changes, or a review comment.

The build's refusal reads like this:

```text
✗ Access matrix drift (1 change) — capability changes must be reviewed
• 'crm_sales_user' loses ALL access to 'crm_opportunity_line_item' (entry removed)
If intended, re-run with --update-access-matrix and commit the snapshot — its diff IS the review artifact.
```

In plain words: the sales role would lose all access to deal product lines, and the build will not finish until a person accepts that on purpose. The "access matrix" is the access table saved in the repository, one row per role and record type. The mechanism, line by line, is in [How do you catch an AI's silent permission change before it ships?](/en/blog/catch-ai-silent-permission-change-access-matrix-gate/)

## What the metadata platforms do better

The case for the established platforms is strong, and ObjectStack's documentation makes it in its own words. What they are good at: ["building business applications quickly on a proven runtime, with packaged apps, modules and integrations to start from."](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/content/docs/concepts/compare.mdx#L65-L66) Where they start ahead:

> Salesforce, Odoo and ERPNext bring years of production use, packaged applications, app marketplaces and implementation partners. ObjectStack is younger; expect to build more of it yourself.
> — [ObjectStack docs, "Where the others are stronger"](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/content/docs/concepts/compare.mdx#L115-L117)

Three more points count in their favour:

- **Agents can reach them too.** The same page says ["several of them now offer MCP servers, so agents can reach them too."](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/content/docs/concepts/compare.mdx#L62-L63) MCP is the open standard through which AI agents call a system's tools.
- **Storing logic as data is the normal shape, not a flaw.** ["This is the same trade-off ServiceNow made (Business Rules), Salesforce made (Formulas + Apex Triggers stored as metadata), Retool made (transformer JS strings), and Airtable made (Scripting blocks). It's the standard low-code shape."](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/content/docs/automation/hook-bodies.mdx#L61) That is ObjectStack's own documentation, on its choice to keep small pieces of business logic as data. So the difference is not whether a platform uses metadata. ObjectStack is a metadata platform. The difference is where the authoritative copy is versioned.
- **An admin screen needs no repository.** On a configuration platform, a business administrator can add a field in a few minutes without a pull request, a build or a deployment. For many teams that is the point.

If you already run on one of these platforms, what you have already built there is a real reason to stay, and our posts on [Power Platform and Dataverse](/en/blog/power-platform-lock-in-dataverse-self-host/) and on [Retool](/en/blog/retool-vs-ai-native-app-platform/) weigh specific products.

## How to choose

**Start from a configuration platform** when you need packaged apps, a marketplace and implementation partners this quarter; when the people changing the system are administrators working in its screens; and when your auditors accept the platform's own change records.

**Keep the definition in a repository** when AI agents will write most of the changes and a person has to answer for each one; when a permission change must come with a reason and a readable before-and-after; and when you want the definition of your business to be files your company holds, not rows in a running system's database. ObjectStack's README puts that last point this way: ["The definition lives in your repository as ordinary TypeScript, versioned in your VCS and reviewable as a diff — not a graph held inside a vendor's system."](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/README.md#L197-L199) VCS is version control; TypeScript is the language the files are written in.

Whichever you pick, ask the vendor three questions:

1. Which copy is authoritative: the running system or a file?
2. Can I get every permission change as a readable before-and-after, with an author and a reason, before it takes effect?
3. When the running system and the file disagree, which one wins, and who finds out?

## What a repository does not solve

- **It does not decide whether a change is right.** When we removed the August fix, the platform's first check passed with a warning. Only the access table stopped the build, and only because this app has one: each app has to switch the table on, and an app without it would have built. A person still has to decide that sales should or should not touch product lines.
- **It does not create review.** Six of the seven pull requests above have no review recorded on GitHub, ours included in that count: this is ObjectStack's own repository. No record does not prove nobody read the change; it means nobody can show that someone did. The repository makes that gap countable. Closing it takes a setting that requires an approval before merging.
- **ObjectStack keeps some configuration too.** Views, dashboards, reports, translations and email templates can be edited in the admin screen of a running environment. Those edits are stored in that environment's database and [take precedence over the repository's version](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/content/docs/concepts/metadata-lifecycle.mdx#L43), with their own change log. Most kinds of definition, bundles of permissions included, can also be [created at runtime through the programming interface](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/packages/spec/src/kernel/metadata-plugin.zod.ts#L348). Those are configuration in exactly this post's sense, so which changes must go through the repository is a policy you set.

## Point your agent at the definition

A definition an agent can generate, with a fixed, checkable shape, that a person can review as a small diff and that the running system enforces: ObjectStack is one such target; [point your agent at ObjectStack](/en/blog/how-to-point-your-agent-at-objectstack/) to try it on your own process.
