**요약:** 포워드 디플로이드 엔지니어(FDE)는 엔터프라이즈 AI에서 가장 빠르게 성장하는 직군입니다 — 보도에 따르면 채용은 전년 대비 약 1,000% 성장했고, OpenAI는 2026년 5월 전담 배포 회사에 40억 달러를 약정했습니다. 실제로 통하는 플레이북은 Palantir의 방식, 즉 **온톨로지 우선**입니다 — AI 애플리케이션을 내놓기 전에 고객의 비즈니스부터 모델링하는 것. 이 플레이북이 풀지 못한 것은 결말입니다. 모든 프로젝트는 인계로 끝나는데, 오늘날 온톨로지는 대개 고객이 영원히 임대해야 하는 플랫폼 안에 갇힙니다. 다음 세대 FDE를 정의할 질문은 우리가 **온톨로지 인계(the ontology handover)**라 부르는 것입니다: 고객의 온톨로지는 *고객 자신의* 저장소에 있는 타입 있는 오픈 파일로 인계되는가 — 아니면 누군가의 갱신 협상 카드가 되는가?

## 엔터프라이즈 AI를 삼킨 직군

올해 보도된 숫자들: FDE 채용 공고는 2025년 1–9월에 800% 이상 늘었고 2026년 초 전년 대비 1,000%를 넘었습니다([Perspective AI](https://getperspective.ai/blog/2026-fde-hiring-trends-what-1000-job-posts-reveal), [TechTarget](https://www.techtarget.com/searchenterpriseai/feature/The-rise-of-the-AI-forward-deployed-engineer)). 2026년 5월 OpenAI는 **40억 달러 약정 자본**과 약 150명의 FDE를 갖춘 배포 회사를 발표했습니다. 이유는 구조적입니다: 모델이 충분히 좋아지면서 병목이 모델링에서 배포로 옮겨갔습니다 — 모든 기업의 데이터, 워크플로, 컴플라이언스 제약은 저마다 고유하고, 누군가 그 안에 들어가 AI를 맞춰 넣어야 합니다.

## 통하는 플레이북은 온톨로지 우선

이 말이 유행하기 훨씬 전에 Palantir는 그것을 제도화했습니다: 그들의 AI FDE는 **LLM 기반 애플리케이션을 내놓기 전에 고객 전용 온톨로지를 먼저 구축**하고, 주당 30–40%를 디스커버리에 씁니다([Palantir AI FDE 가이드](https://www.palantir.com/docs/foundry/ai-fde/overview)). 이 통찰은 오래갑니다: 범용 모델은 범용 답만 내놓습니다. 엔터프라이즈 가치는 고객 자신의 명사와 동사 — 객체, 관계, 권한, 승인 경로 — 에 접지되어야 합니다. 그것은 엔지니어링이지 프롬프팅이 아닙니다.

여기까지는 더 이상 논쟁거리가 아닙니다. 거의 이야기되지 않는 것은 끝에서 벌어지는 일입니다.

## 풀리지 않은 부분: 인계

모든 포워드 디플로이드 프로젝트는 끝납니다. FDE는 철수하고, 그들이 구축한 온톨로지 — 프로젝트 전체에서 가장 가치 있는 산출물, 이 비즈니스가 실제로 돌아가는 방식을 부호화한 지식 — 는 둘 중 한 곳에 남습니다:

- **벤더의 플랫폼 안.** 고객은 쓸 수 있지만 플랫폼을 통해서만, 좌석당 과금으로, 변경은 플랫폼 교육을 받은 전문가에게 의존합니다. 온톨로지는 갱신 협상 카드가 되어 버렸습니다.
- **고객의 저장소 안.** 타입이 있고 버전 관리되는 오픈 파일. 고객 자신의 팀과 — 고객 자신의 AI 에이전트가 — 누구의 허락도 없이 읽고, 실행하고, 계속 고칠 수 있습니다.

오늘의 기본값은 전자이고, 그래서 기업 고객들은 '성공한 파일럿'을 두려워하게 되었습니다: 온톨로지가 좋을수록 락인은 깊어집니다. 후자의 결말은 정의 계층 자체가 오픈 포맷일 때만 가능합니다.

## 오픈 FDE 스택의 모습

이것이 [ObjectStack](https://github.com/objectstack-ai/objectstack)(Apache-2.0)이 설계된 워크플로입니다. 디스커버리 노트가 타입 메타데이터가 됩니다 — 코딩 에이전트가 쓰고, 검증 게이트가 조용히 실패할 것들을 거부합니다:

```ts
export const Ticket = ObjectSchema.create({
  name: 'support_ticket',
  label: 'Ticket',
  sharingModel: 'private',        // 기본은 보수적으로 — 게이트가 요구
  fields: {
    subject:  Field.text({ label: 'Subject', required: true }),
    status:   Field.select({ label: 'Status', options: [/* 고객의 실제 상태들 */] }),
    approver: Field.lookup('sys_user'),
  },
});
```

이 정의에서 런타임이 데이터베이스, REST API, 관리 Console, MCP 도구를 유도하고, 모든 호출에 권한과 감사를 강제합니다 — 당신이 떠난 뒤에도. 앱 전체는 검토 가능한 크기를 유지합니다: 완전한 CRM이 **1,792줄, 약 16k 토큰** — 직접 세어 보세요:

```bash
find examples/app-crm/src -name '*.ts' -not -name '*.test.ts' | xargs cat | wc -l
```

이 크기가 인계를 정직하게 만듭니다. 고객의 보안팀은 플랫폼 경계를 신뢰하는 대신 실제 diff를 읽고, 고객의 미래 에이전트는 시스템 전체를 컨텍스트에 담아 통째로 리팩터링합니다.

## 이 스택이 해결하지 못하는 것

경계를 분명히 해 둡니다: **초대규모 데이터 페더레이션과 분석 파이프라인**은 Foundry의 홈그라운드이며, 오픈 애플리케이션 계층이 그것을 대체하지 않습니다. **조직 변화 관리** — 사람들이 실제로 쓰게 만드는 일 — 는 어떤 스택도 고쳐 주지 않는 사람의 일입니다. 이미 닫힌 플랫폼에 전면 표준화한 고객이라면 남는 것이 합리적일 수도 있습니다. 주장은 더 좁습니다: 포워드 디플로이드 업무의 애플리케이션 계층 — 비즈니스를 모델링하고 그 위에 거버넌스된 앱을 내놓는 일 — 에서는, 이제 온톨로지를 인질로 잡는 대신 인계할 수 있다는 것입니다.

## FDE 체크리스트

1. 어떤 UI 이야기보다 먼저 고객의 명사와 동사를 객체와 플로로 모델링한다.
2. 정의 전체를 컨텍스트 크기로 유지해 에이전트가 통째로 리팩터링할 수 있게 한다.
3. 권한은 기본을 보수적으로; 모든 권한 변경은 diff에 명시한다.
4. 인계하는 것은 저장소, 컴파일된 산출물, 리뷰 체크리스트다 — 당신 테넌트의 로그인이 아니다.
5. MCP를 켜 둔 채 넘겨, 고객 자신의 AI가 그들의 권한 안에서 앱을 다루게 한다.
