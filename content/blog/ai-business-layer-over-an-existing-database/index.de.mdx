**Die Antwort.** Kopieren Sie die Datenbank nicht, und bauen Sie sie nicht neu. Binden Sie sie als Quelle an, die die Plattform liest, aber nie verändert, geben Sie jeder Tabelle einen fachlichen Namen, und legen Sie fest, wer was sehen darf. Menschen, Berichte und AI-Agents lesen die Live-Daten dann über einen einzigen kontrollierten Zugang, und die Rechte jeder Person gelten für jede Antwort, auch für die eines Agents. Der Preis: Jeder Lesezugriff läuft auf Ihrer Quelldatenbank. Nichts wird kopiert, also veraltet nichts: Eine Änderung im Altsystem war beim nächsten Lesen sichtbar. Nichts wird zurückgeschrieben, bis Sie das Schreiben an zwei Stellen einschalten.

*Gemessen auf ObjectStack 18.5.0, dem aktuellen Release, an einem nachgestellten Bestellsystem mit 5 Kunden und 2.400 Bestellungen. Alle Mitschnitte stehen im letzten Abschnitt, Der Nachweis.*

Ich nenne das eine **Durchlese-Ontologie**: fachliche Namen, Beziehungen, Berechtigungen und AI-Werkzeuge, gelegt über Tabellen, die Ihnen nicht gehören, und jeder Lesezugriff wird an das System durchgereicht, dem sie gehören. Eine Zahl macht es greifbar: Während sie alle 2.400 Bestellungen auslieferte, hielt die eigene Datenbank von ObjectStack **0 davon**.

## Drei Wege, eine laufende Datenbank nutzbar zu machen

Die meisten Firmen, die ihre Daten „AI-fähig“ machen sollen, haben die Daten längst, in einer Datenbank, die ein anderes System schreibt. Es gibt drei ehrliche Wege, eine kontrollierte Geschäftsschicht darauf zu setzen, und jeder kostet etwas anderes.

| | Neu bauen | Kopieren | Durchlesen |
|:--|:--|:--|:--|
| Was bewegt wird | die Daten und das System | die Daten, nach Zeitplan | nichts |
| Aktualität | das neue System ist die Wahrheit | so alt wie die letzte Synchronisierung | die Quelle, zum Lesezeitpunkt |
| Wem das Schema gehört | Ihnen | Ihnen, für die Kopie | dem Quellsystem |
| Kosten am ersten Tag | ein Migrationsprojekt | eine Pipeline, die man baut und überwacht | eine Verbindungsdatei und eine Datei pro Tabelle |
| Joins über Quellen | ja | ja, der Hauptgrund für die Kopie | zwei Lesezugriffe, im Speicher verbunden |
| Last auf der Quelle | keine nach der Umstellung | eine Synchronisierung auf einmal | jeder Lesezugriff |

Das Argument für die Kopie ist echt: Eine Kopie lässt sich indizieren, mit allem verbinden, durchsuchen und auswerten, während die Quelle langsam ist oder steht, und sie legt nie die Abfragen eines Dashboards auf ein produktives Bestellsystem. Wenn Sie das brauchen, kopieren Sie. Das Argument fürs Durchlesen ist enger und dort, wo es passt, stärker: Am Tag der Verbindung ist die Geschäftsschicht aktuell, weil es keine Kopie gibt, die zurückfallen kann.

## Was ich angebunden habe und was es antwortete

Die Quelle ist eine SQLite-Datei, geschrieben von einem kurzen Python-Skript, das ein altes Bestellsystem nachstellt: eine Kundentabelle und eine Bestelltabelle, mit den kryptischen Spaltennamen alter Systeme. Drei kurze Dateien erledigten die Arbeit. Eine **Datenquelle** deklariert, wo eine Datenbank liegt und was die Plattform dort darf. Diese hier sagt, dass das Schema der Quelle gehört, ObjectStack es also nie ändert, und dass Schreiben aus ist:

```ts
export const Erp = defineDatasource({
  name: 'erp',
  label: 'Order system (SQLite)',
  driver: 'sqlite',
  schemaMode: 'external',            // ObjectStack never runs DDL here
  config: { filename: '/…/legacy/erp.db' },   // absolute path, trimmed
  external: {
    allowWrites: false,
    validation: { onMismatch: 'fail', checkOnBoot: true },
  },
});
```

Ein **Objekt** pro Tabelle ist der fachliche Datensatz, den Menschen, Berichte und Agents beim Namen abfragen; jedes bildet die alten Spalten auf klare Namen ab, so wird `cust_no` zu `id`. Die Plattform kann die Tabellen der Quelle auflisten und diese Objekte für Sie entwerfen. Ein **Berechtigungssatz** ist ein benanntes Bündel von Rechten, das Sie Personen zuweisen; dieser zeigt Lesenden die Kunden, aber nicht, was sie schulden dürfen, und nichts von den Bestellungen.

Dann habe ich der laufenden App die Fragen gestellt, die Sie vor einer Freigabe stellen würden: als Admin, als ein Mitglied namens Mia und als AI-Agent, angemeldet als Mia über **MCP**, das offene Protokoll, mit dem AI-Agents die Werkzeuge einer Anwendung aufrufen.

| Was ich tat | Was das System antwortete | Was es für Sie bedeutet |
|:--|:--|:--|
| Ein Kreditlimit direkt im Bestellsystem geändert, dann über ObjectStack gelesen | 95.000 statt 180.000 beim nächsten Lesen; keine Synchronisierung lief, und keine der 85 Tabellen in der eigenen Datenbank von ObjectStack war eine Kunden- oder Bestelltabelle | Sie lesen die Quelle, keine Kopie, die veralten kann |
| Offene Bestellungen samt ihren Kunden abgefragt | 480 Bestellungen, in der Quelle gefiltert, jede mit ihrem Kunden aus der anderen Tabelle | Filter und Beziehungen funktionieren auf Tabellen, die Ihnen nicht gehören |
| Das Bestelldatum als Datum deklariert; die Quelle speichert Text | Die App verweigerte den Start und nannte die Spalte | Die Schicht ändert nie Ihr Schema, damit es zu ihr passt |
| Als Admin angelegt, geändert und gelöscht | Alles abgelehnt, mit beiden Schreibschaltern im Text; die Quelle hielt weiter 5 Kunden und 2.400 Bestellungen | Niemand schreibt in die Quelle, bis Sie beide Schalter öffnen |
| Als Mia gelesen, vor und nach der Zuweisung des Lese-Berechtigungssatzes | Vorher: beide Tabellen abgelehnt. Nachher: zwei EU-Kunden, kein Kreditlimit; Bestellungen weiter abgelehnt | Gesperrt bis zur Freigabe; Spalten verbergen funktioniert auf einer Datenbank, die die Plattform nicht gebaut hat |
| Mia filterte, dann sortierte nach dem Kreditlimit | Beides abgelehnt: Die Antwort würde den Wert verraten | Filtern oder Sortieren nach einer verborgenen Zahl wird abgelehnt, also lässt sie sich so nicht erraten |
| Ein als Mia angemeldeter Agent listete seine Objekte, las Kunden, verlangte 51 Zeilen, versuchte zu schreiben | Kunden und das Kollegenverzeichnis, keine Bestellungen; zwei NA-Kunden, kein Kreditlimit; mehr als 50 Zeilen abgelehnt; Schreiben abgelehnt | Der Agent bekommt nicht mehr als Mias Sicht, höchstens 50 Zeilen pro Aufruf, nur lesend |
| Ein **Dataset** (ein benannter Satz von Berichtszahlen) nach Umsatz je Kundenregion gefragt | APAC 6,127,544.10, EU 11,995,588.50, NA 12,470,792.17, genau wie die eigene Abfrage des Bestellsystems, auf zwei Nachkommastellen | Berichte funktionieren über beide Tabellen (siehe Grenze 1) |

Die Quelldatenbank weiß nicht, wer Mia ist: Die Schicht setzt ihre Rechte bei jedem Lesezugriff durch, und der Agent spricht nie mit der Datenbank.

## Wo die Durchlese-Schicht aufhört

Das sind die Ränder, die ich gemessen habe, dazu zwei, die die Dokumentation für Treiber nennt, die ich nicht ausgeführt habe. Die Schreibschalter habe ich nie eingeschaltet; was ein Schreibzugriff tut, wenn beide offen sind, ist hier also nicht gemessen.

**1. Keine einzelne Abfrage verbindet zwei Datenbanken.** Der Umsatzbericht war kein einzelner Join, der an SQLite ging. Für ein föderiertes Objekt, also eines, das an eine externe Tabelle gebunden ist, läuft das Dataset laut dem Kommentar im Analytics-Compiler über „the ObjectQL FK-expand path (two reads, joined in memory)“ (den ObjectQL-Pfad der Fremdschlüssel-Auflösung: zwei Lesezugriffe, im Speicher verbunden). Dasselbe gilt zwischen der eigenen Datenbank von ObjectStack und dem Bestellsystem: Ein natives Besuchsobjekt mit einem Lookup auf Kunden löste den Kunden auf und filterte nach seiner Region, als getrennte Lesezugriffe. Was es nicht gibt, ist eine Anweisung über zwei Datenbanken; der Entwurfsbeschluss (ADR) der Runtime führt sie unter den Nicht-Zielen: „cross-datasource JOINs in one query (federated objects are queried per-datasource)“ (quellübergreifende JOINs in einer Abfrage; föderierte Objekte werden je Datenquelle abgefragt).

**2. Große Lesezugriffe sind auf Zusatz-Connectors begrenzt, nicht auf eingebauten SQL-Datenbanken.** Über den eingebauten SQLite-Treiber gibt es keine Obergrenze: 5.000 angeforderte Bestellungen lieferten alle 2.400, und eine Obergrenze auf dieser Datenquelle wird bei der Validierung als wirkungslos abgelehnt. Ein Zusatz-Connector, bei ObjectStack Plugin-Treiber genannt, wird separat installiert, OData eingeschlossen; über einen solchen setzt der Leitfaden eine Grenze: „A read that matches more rows than the datasource's row cap is refused with `422 EXTERNAL_ROW_CAP_EXCEEDED` rather than answered from a partial set“ (ein Lesezugriff, der mehr Zeilen trifft als die Obergrenze der Datenquelle, wird abgelehnt statt aus einer Teilmenge beantwortet), „The default is 1000 rows“ (Standard sind 1000 Zeilen), höchstens 10.000. Hier nicht ausgeführt.

**3. „Sichtbar, wenn der Elterndatensatz sichtbar ist“ funktioniert auf SQL und wird auf Zusatz-Connectors abgelehnt.** Elterngesteuerte Freigabe heißt: Eine Bestellung ist für alle sichtbar, die ihren Kunden sehen dürfen. Auf einem Zusatz-Connector wird ein solcher Lesezugriff laut Leitfaden abgelehnt (zitiert im Nachweis). Auf SQL habe ich das Gegenteil gemessen: Mia las Bestellungen über ihren Kunden, und als der Kunde für sie unsichtbar wurde, verschwanden die Bestellungen mit (nächster Punkt).

**4. Besitzerbezogene Freigabe braucht eine Besitzerspalte.** Setzen Sie Kunden auf privat, den Standard des entworfenen Objekts, über einer Tabelle ohne Besitzerspalte, und Mia las nichts, weder Kunden noch ihre Bestellungen, während der Admin weiter alle 5 und alle 2.400 las. Der Leitfaden warnt: „only an `owner_id` declared in `fields`, or named by an `external.columnMap` entry, counts as one. Without it a member reads no row.“ (nur ein in `fields` deklariertes oder von einem `external.columnMap`-Eintrag benanntes `owner_id` zählt als Besitzer; ohne ihn liest ein Mitglied keine Zeile.) Bilden Sie die Besitzerspalte der Quelle ab, oder geben Sie die Tabelle zum Lesen frei und schränken Sie wie oben mit Berechtigungssätzen ein.

**5. Die Leistung ist die der Quelle.** Jeder Lesezugriff läuft in diesem Moment auf dem Bestellsystem: Eine Listenseite liest die Zeilen und die Gesamtzahl, und ein Dashboard, das jemand offen lässt, ist eine Abfrage auf Ihrer Produktionsdatenbank. Die Schicht fügt keinen Index hinzu, den die Quelle nicht hat. Verkraftet die Quelle die Last nicht, richten Sie die Datenquelle auf ein Replikat, das Sie bereits betreiben, oder kopieren Sie die Daten.

## Wann eine Kopie das bessere Werkzeug ist

Der ObjectStack-Leitfaden zu virtuellen Objekten nennt die Regel in einem Satz: „Make the object virtual when a copy would be **wrong**, and real when a copy is merely **convenient**“ (machen Sie das Objekt virtuell, wenn eine Kopie falsch wäre, und real, wenn eine Kopie bloß bequem ist). Falsch ist eine Kopie, wenn die Gegenstelle die Antwort erst bei der Anfrage berechnet, wenn die Daten nicht außerhalb der Quelle gespeichert werden dürfen (Datenresidenz, Lizenz, Prüfung) oder wenn sie sich schneller ändern, als eine Synchronisierung folgen kann. Bequem ist sie für langsam veränderliche Referenzdaten und für Berichte, die viele Quellen verbinden. Die erste Sorte lesen Sie durch, die zweite kopieren Sie. Bei einem bereits abgeschalteten System bleibt nur ein Export, und [ein Import-Mapping mit Probelauf](/de/blog/how-to-import-a-spreadsheet-from-an-old-system/) ist der Weg, diese Datei ohne ihre alten Codes ins Modell zu holen.

Hineinkopieren ist der andere Weg, und sein Kern ist in 18.5.0 enthalten: Ein geplanter Job kopiert ein föderiertes Objekt in eine synchronisierte Kopie, die Mitglieder lesen, aber nicht beschreiben können. Für diesen Artikel habe ich das nicht gemessen. Die Leitlinie von ADR-0153 weist „Reports, analysis, AI question answering, joins across sources; a slow or fragile legacy system“ (Berichte, Analyse, AI-Fragen, Joins über Quellen; ein langsames oder fragiles Altsystem) dem Sync-in zu, ihrem Namen fürs Hineinkopieren, und „Live data, one table at a time; the legacy system must not be touched; data that must not land“ (Live-Daten, eine Tabelle zur Zeit; das Altsystem darf nicht angefasst werden; Daten, die nicht landen dürfen) der Föderation, ihrem Namen für diese Durchlese-Bindung. Die Seite [Connect existing systems](/en/connect-existing-systems/) stellt die drei Wege nebeneinander: live lesen, hineinkopieren oder die Quelle über eine deklarierte Aktion ändern.

## In Entwicklung: der Rest von Sync-in

Nicht in 18.5.0: das Markieren von Zeilen, die die Quelle gelöscht hat (der Job-Leitfaden: „The delete keys change nothing yet“, die Lösch-Schlüssel ändern noch nichts), das Blättern für Connector-Quellen, deren Schlüssel sich deklarieren lässt, aber „nothing reads it yet“ (noch liest ihn nichts), sowie der Sync-in-Leitfaden und die Skills. Nichts in diesem Abschnitt wurde gemessen.

## Was man im Diff liest

Schreibt ein Agent die Bindung, ist jede Entscheidung eine Zeile im Diff:

| Zeile im Diff | Was sie entscheidet |
|:--|:--|
| `schemaMode: 'external'` | ObjectStack ändert die Quelle nie; Abweichungen lassen den Start scheitern |
| `allowWrites` / `writable` | beide müssen `true` sein, damit ein Schreibzugriff die Quelle erreicht |
| `columnMap` | unter welchen fachlichen Namen die Spalten der Quelle erscheinen |
| `sharingModel` | `private` braucht eine abgebildete Besitzerspalte, sonst lesen Mitglieder nichts |
| Berechtigungssatz `fields` | welche Quellspalten ein Mitglied nie sieht und nicht zum Filtern nutzt |
| `rowCap` | nur Plugin-Treiber; auf einem eingebauten SQL-Treiber abgelehnt |

Föderation lässt die [Ontologie](/de/glossary/ontology/) eine Datenbank benennen, die Sie nicht gebaut haben, mit dem [Berechtigungsmodell](/en/glossary/permission-model/) für jeden Leser, Mensch oder Agent.

## Richten Sie Ihren Agent darauf aus

Geben Sie Ihrem Coding-Agent die Bindung als Regel, nicht diesen Artikel: eine `external`-Datenquelle, ein Objekt pro Tabelle mit `remoteName` und `columnMap`, ein ausdrücklich gesetztes `sharingModel`, beide Schreibschalter aus und ein Berechtigungssatz pro Zielgruppe. [Wie man den Coding-Agent konfiguriert](/en/blog/how-to-point-your-agent-at-objectstack/) behandelt die Regeldatei, den MCP-Endpunkt der laufenden App und die Spezifikation; der [Leitfaden zu externen Datenquellen](https://objectstack.ai/docs/data-modeling/external-datasources) ist die Referenz, die der Agent lesen sollte.

## Der Nachweis

Alles hier ist echte Ausgabe von `objectstack dev` auf 18.5.0, auf einem Gerüst aus `npm create objectstack@latest`, gekürzt nur, wo markiert. `$B` ist die Adresse des Dev-Servers, und `sql.py` ist ein dreizeiliges Python-Hilfsskript, das eine Anweisung gegen die Datei ausführt, weil die Maschine keinen `sqlite3`-Befehl hatte.

### Die Quelle und der Dialekt

Fünf Kunden und 2.400 Bestellungen, in diesem Schema:

```sql
CREATE TABLE customers (
  cust_no      TEXT PRIMARY KEY,
  cust_name    TEXT NOT NULL,
  cust_region  TEXT,
  credit_limit REAL
);
CREATE TABLE orders (
  order_no   TEXT PRIMARY KEY,
  cust_no    TEXT NOT NULL REFERENCES customers(cust_no),
  amount     REAL,
  status     TEXT,
  placed_on  TEXT
);
```

Ich habe zuerst Postgres versucht, und der Start sagte es deutlich: „The database client package `pg` is not installed, so no connection was attempted. It is an OPTIONAL install of @objectstack/driver-sql … `npm install pg` (pnpm add pg / yarn add pg)“ (das Client-Paket `pg` ist nicht installiert, also wurde keine Verbindung versucht; es ist eine optionale Installation von @objectstack/driver-sql). Der Leitfaden dokumentiert außerdem Oracle und SQL Server als reine Föderations-Dialekte („ObjectStack reads an existing Oracle schema live … but it never owns one“, ObjectStack liest ein bestehendes Oracle-Schema live, besitzt es aber nie) sowie OData-v4-Dienste wie SAP S/4HANA und Dynamics 365 über einen mitgelieferten Treiber. Keinen dieser drei habe ich hier ausgeführt.

### Die Bindung

Im Gerüst `sales` steht neben der Datenquelle oben das Kundenobjekt, das mit `external.columnMap` (entfernte Spalte → lokales Feld) aus `cust_no`, `cust_name` und `cust_region` die Felder `id`, `name` und `region` macht:

```ts
export const Customer = ObjectSchema.create({
  name: 'sales_customer',
  label: 'Customer',
  sharingModel: 'public_read',
  datasource: 'erp',
  external: {
    remoteName: 'customers',
    columnMap: { cust_no: 'id', cust_name: 'name', cust_region: 'region' },
  },
  fields: {
    name: Field.text({ label: 'Name', searchable: true }),
    region: Field.text({ label: 'Region' }),
    credit_limit: Field.currency({ label: 'Credit limit' }),
  },
});
```

`sales_order` hat dieselbe Form über `orders`, mit `cust_no` auf einen `customer`-Lookup abgebildet. Der Berechtigungssatz:

```ts
export const SalesReader = definePermissionSet({
  name: 'sales_reader',
  objects: { sales_customer: { allowRead: true } },
  fields: { 'sales_customer.credit_limit': { readable: false, editable: false } },
});
```

Die Admin-Route `GET …/datasources/erp/external/tables` antwortete mit `customers` (4 Spalten) und `orders` (5), und `POST …/external/tables/customers/draft` lieferte einen Objektentwurf für die Tabelle. Der Entwurf behält die entfernten Namen als Feldnamen und beginnt mit `sharingModel: 'private'` (Grenze 4), also habe ich über `columnMap` umbenannt und `public_read` gewählt.

`placed_on` als `date`-Feld zu deklarieren ließ den Start scheitern:

```text
✗ Object 'sales_order' does not match its remote table on datasource 'erp':
✗ type_mismatch: orders.placed_on (expected date, actual text)
```

Das ist `schemaMode: 'external'`, das wie vorgesehen arbeitet, laut Leitfaden: „A mature external DB — **DDL forbidden**; a schema mismatch **fails** boot.“ (eine reife externe DB: DDL verboten, eine Schema-Abweichung lässt den Start scheitern.) Ich habe das Feld auf `text` geändert, also auf das, was das Bestellsystem speichert.

### Kann irgendetwas hineinschreiben?

Als Plattform-Admin:

```bash
curl -s -b admin.cookies -X POST "$B/api/v1/data/sales_customer" \
  -H "content-type: application/json" -d '{"id":"C-9999","name":"Test Co","region":"EU"}'
```

```json
HTTP 403
{"error":"Write 'insert' blocked on object 'sales_customer': datasource 'erp' is external (schemaMode=external). Requires datasource.external.allowWrites=true (got false) AND object.external.writable=true (got false).","code":"EXTERNAL_WRITE_FORBIDDEN","object":"sales_customer"}
```

Ein `PATCH` auf `C-1002` und ein `DELETE` der Bestellung `SO-00001` antworteten mit demselben `403`, mit `update` und `delete` im Text. Das Bestellsystem hatte danach weiter 5 Kunden, 2.400 Bestellungen und das Kreditlimit, das es selbst gesetzt hatte. Der Leitfaden: „With either gate off, insert/update/delete on the federated object is rejected.“ (ist eines der beiden Tore zu, wird Einfügen, Ändern und Löschen am föderierten Objekt abgelehnt.) Der Entwurfsbeschluss (ADR), der den Mechanismus festlegt, nennt als Ziele „Register existing remote tables as ObjectStack objects **without touching the remote schema**“ (bestehende entfernte Tabellen als ObjectStack-Objekte registrieren, ohne das entfernte Schema anzufassen) und „Default to read-only; require **two explicit opt-ins** (datasource level + object level) to enable writes.“ (standardmäßig nur lesend; Schreiben verlangt zwei ausdrückliche Zustimmungen, auf Ebene der Datenquelle und des Objekts.)

### Was sieht ein Mitglied?

Mia ist ein Mitglied, das der Admin über `POST /api/v1/auth/admin/create-user` angelegt hat. Ohne Zuweisung antworten beide Objekte mit `403 PERMISSION_DENIED`: Ein föderiertes Objekt ist standardmäßig gesperrt wie jedes andere. Nachdem der Admin ihr `sales_reader` zugewiesen hat:

```bash
curl -s -b member.cookies "$B/api/v1/data/sales_customer?region=EU"
```

```json
HTTP 200
{"object":"sales_customer","records":[{"id":"C-1002","name":"Borealis GmbH","region":"EU"},{"id":"C-1004","name":"Delta Freight","region":"EU"}],"total":2,"hasMore":false}
```

Kein `credit_limit`; Bestellungen antworten weiter mit `403`. Über eine indirekte Frage:

```bash
curl -s -b member.cookies "$B/api/v1/data/sales_customer?credit_limit=95000"
```

```json
HTTP 403
{"error":"[Security] Access denied: query on 'sales_customer' references field(s) not readable by the caller: credit_limit. Filtering, sorting, grouping, or aggregating by a hidden field would leak its values (filter oracle) — remove these predicates or grant field read access.","code":"PERMISSION_DENIED","object":"sales_customer"}
```

Sortieren danach antwortete genauso.

### Kommt ein AI-Agent daran vorbei?

Jede ObjectStack-App ist ein MCP-Server unter `/api/v1/mcp`. Als Mia angemeldet, antwortete `list_objects` eines Agents mit `sys_user`, das 18.5.0 einem Agent öffnet, damit er für ein Personenfeld Kollegen finden kann, und `sales_customer`. Danach, gekürzt auf die Werkzeugergebnisse:

```text
query_records  sales_customer  where {"region":"NA"}  → 2 records: Aurora Labs, Ember Foods (no credit_limit)
query_records  sales_order     limit 1                → {"code":"PERMISSION_DENIED","status":403}
query_records  sales_customer  limit 51               → Too big: expected number to be <=50 at limit
create_record  sales_customer  {"id":"C-9998",…}      → {"code":"EXTERNAL_WRITE_FORBIDDEN","status":403}
```

### Funktionieren Berichte über die Tabellen hinweg?

Das Dataset gruppiert den Bestellumsatz nach einer Spalte der anderen Tabelle:

```ts
export const OrderRevenue: Dataset = {
  name: 'sales_order_revenue',
  label: 'Order revenue',
  object: 'sales_order',
```

### Die Grenzen, wie gemessen

Über Datenquellen hinweg (Grenze 1): Das native `sales_visit` mit einem Lookup auf `sales_customer` nahm `?expand=customer` und den verschachtelten Filter `{"customer":{"region":"EU"}}` an. Ein Filter mit Punktpfad wie `?customer.region=EU` und `aggregate_records`, gruppiert nach `customer.region`, antworteten auf dem nativen `sales_visit` genau wie auf `sales_order` mit `400 INVALID_FIELD`; diese beiden Ablehnungen sind also keine Grenzen der Föderation.

Zeilenobergrenze (Grenze 2): `?top=5000` auf Bestellungen lieferte alle 2.400 Zeilen. `rowCap` auf der SQLite-Datenquelle, bei der Validierung:

```text
✗ external.rowCap: `external.rowCap` caps the rows the engine reads from a plugin driver, which it holds behind its correctness floor; the 'sqlite' driver is built in, runs the whole query itself and is never capped, so the key would do nothing here. Remove `rowCap`.
```

Elterngesteuert (Grenze 3): `sales_order` auf `controlled_by_parent`, über ein `master_detail` an Kunden gehängt; Mia las Bestellungen. Der Leitfaden für einen Plugin-Treiber: „A read whose scope composes a `ReadableIds` leaf, such as an object `controlled_by_parent`, is refused“ (ein Lesezugriff, dessen Bereich ein `ReadableIds`-Blatt enthält, etwa bei einem Objekt `controlled_by_parent`, wird abgelehnt).

Besitzerspalte (Grenze 4): Mit `sales_customer` auf `private` lautete Mias Antwort `{"records":[],"total":0}` für Kunden und für die elterngesteuerten Bestellungen; der Admin las weiter alle 5 und alle 2.400.

Hineinkopieren, beim Namen genannt (in 18.5.0 enthalten, hier nicht gemessen): Ein `job`, dessen `pull` ein `mapping` mit `datasourceSource` nennt, liest ein föderiertes Objekt in Fenstern und schreibt per Upsert in ein Objekt, das als `managedBy: 'synced'` deklariert ist; Mitglieder können es lesen, ihre Schreibzugriffe lehnt die Engine mit `403` ab. Jeder Lauf hinterlässt eine Zeile in `sys_sync_run` mit dem, was er gelesen hat, und der erreichten Position, und der nächste Lauf liest von dort weiter. Die Release Notes: „A mapping's `datasourceSource` now does what it declares“ (das `datasourceSource` eines Mappings tut jetzt, was es deklariert). In einer App deklarierte Jobs laufen nur auf einem Deployment, das `OS_AUTOMATION_SCHEDULED_WORK_ENABLED` auf `true` setzt, standardmäßig ist das aus.
