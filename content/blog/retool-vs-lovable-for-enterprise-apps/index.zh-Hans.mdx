按谁来改应用来选。如果是工程师在现有数据库上做工具，选 Retool：它的 AI 不会越出你已经授予的访问权限，审计日志从 Business 套餐开始提供；但在 Free 和 Team 套餐上，它的 All Users 组可以编辑每一个应用，而要让每次改动都走拉取请求评审，需要最高套餐。如果是业务团队生成整个应用，选 Lovable：它把应用做出来并负责托管，它的 Git 同步在每个套餐上都能接入拉取请求评审，最高套餐还能把公开应用压住，等管理员或所有者批准。但数据访问规则是它的 AI 写的，而且这些规则约束不了应用的特权服务器账号。无论选哪个，都得有人为 AI 做出的东西负责。

*下文每一条关于 Retool 和 Lovable 的说法，都引自该厂商的公开文档或定价页，阅读日期为 2026 年 11 月 17 日。ObjectStack 的结果实测于 ObjectStack 18.5.0，即今天新安装得到的版本。来源和完整记录见[证据](#证据)。*

## 这场比较背后的问题

如果你搜到了这个比较，多半已经接受了一件事：应用会由 AI 来做。悬而未决的是做完之后怎么办。IT 负责人会收到三类请求，通常按这个顺序来：业务负责人要改一个地方；审计员问上一次改动是谁批准的；有人问应用在某一天对某条记录做了什么。所以有用的比较不在于哪个工具做得快，而在于这三类请求在每个工具里由谁、在哪里回答。

Retool 的文档描述的是这样一个应用构建器：“the primary development experience of apps is by prompting an AI agent with natural language”（构建应用的主要方式是用自然语言向 AI Agent 下指令），连接的是你公司已经接入 Retool 的数据库和服务。本文讲的是这个 AI 应用构建器（Retool 称之为 Apps），不是它的经典拖拽式应用。Lovable 的文档描述的是一个把整个应用（界面、服务器和数据库）都生成出来、默认还负责托管的工具。我们之前分别写过[Retool 那篇](/zh-Hans/blog/retool-vs-ai-native-app-platform/)和[Lovable 那篇](/zh-Hans/blog/is-lovable-safe-for-production/)，更多平台的对比见[对比页](/zh-Hans/compare/)。

## 七个问题，两家厂商

每一格写的都是该厂商自己的文档或定价页怎么说。粗体标签标出厂商对某项功能限定的套餐。有三个词会反复出现：**拉取请求**（pull request）是放在你的代码仓库（例如 GitHub）里的一份改动提议，有人批准后才生效；**Git 同步**是 Lovable 把应用代码双向同步到你的代码仓库的功能；**MCP** 是 AI 助手连接其他软件所用的协议。

| 你会被问到的问题 | Retool | Lovable |
|:--|:--|:--|
| **谁能改应用？** | 构建者（builder），他们也能发布；以及“internal users”（内部用户，即使用应用的员工），他们能创建应用但不能发布。**Free、Team**：固定分组，All Users 组可编辑每个应用。 | 编辑者及以上角色。工作区成员“can see, edit, and publish the workspace's projects”（可以查看、编辑和发布工作区的项目）。**Business、Enterprise**：项目可限定为仅受邀者可见。 |
| **改动在用户看到之前怎么评审？** | 改动留在一份独立的工作副本中，有自己的预览。AI 在运行任何写数据的操作之前会先询问。 | 草稿会先显示“a one-line summary of what the draft changes”（一句话概括草稿改了什么）和具体改动，再由人接受。**所有套餐**：Git 同步可以加上拉取请求评审。 |
| **谁来批准？** | 由构建者发布；内部用户做的应用需要构建者来发布。**Enterprise**：对纳入源代码管理的应用，合并拉取请求即发布，评审者可看到应用预览。 | 默认“editors and above can publish”（编辑者及以上可以发布）。**Enterprise**：策略可要求管理员或所有者批准公开应用、使用连接器的应用，或外部协作者的发布。 |
| **运行中的应用执行什么权限？** | 用户需要有某个数据源的访问权限才能对它运行查询。**Business、Enterprise**：按组控制。在开启了强制执行的 PostgreSQL 资源上，策略作用于每一条查询，“including … agents”（包括 Agent 发出的）。 | 由它的 AI 编写的数据库规则；你能查看，修改要通过对话。它们不约束应用的特权服务器账号（`service_role`）。每次发布都会运行的扫描会“checks database access rules”（检查数据库访问规则）。 |
| **审计日志记录什么？** | **Business、Enterprise**：每一次查询运行和用户在 Retool 中的操作，经 MCP 接入的客户端会被标记。Retool 云上保留一年。**Enterprise**：可推送到 Datadog 或 Splunk。 | **Enterprise**：工作区活动，包括成员、项目、提示词和发布。保留 13 周；可定期导出到你的安全监控系统。 |
| **数据和定义放在哪里？** | 应用使用你已接入的数据库和服务；应用本身存放在 Retool 中。Enterprise 套餐卡片：“Retool Cloud, self-hosted, or air-gapped”（Retool 云、自托管或物理隔离，即不接入互联网的网络）。 | 代码默认放在“Lovable's managed infrastructure”（Lovable 托管的基础设施）里；Git 同步（所有套餐）可以在你的仓库里保留一份副本。数据库：用 Lovable 的，或你自己接入的，例如 Supabase。 |
| **它的边界在哪里，怎么离开？** | 在 Retool 之外运行导出的 AI 构建器应用，被列为尚不支持（经典应用可能不同）。**Enterprise**：纳入源代码管理的应用，其源代码放在你的仓库里。 | 文档称“you are never locked in”（你永远不会被锁定）；代码和数据都能导出。接受草稿“can change your live app's backend immediately”（可能立即改动线上应用的后端）。后端日志（不同于审计日志）“do not prove who made a particular database change”（不能证明某次数据库改动是谁做的）。 |

这张表说明了三件事：

- **批准发生在不同的环节。** 在 Retool 里是发布，或者在 Enterprise 上是合并拉取请求。在 Lovable 里是先接受草稿再发布，在 Enterprise 上，策略点名的那几类发布还要管理员或所有者批准。两者的差别在于批准人看到的是什么。
- **两份审计日志回答的是不同的问题。** Retool 的日志记录用户在 Retool 中的操作，“such as query runs and password resets”（例如运行查询和重置密码）。Lovable 的日志记录工作区活动，它列出的事件包括“Prompt sent”（发送提示词）、“Project published externally”（项目对外发布）和“Database query executed”（执行数据库查询）。先写下审计员会问的问题，再看哪份日志能回答。
- **这些管控要更高的套餐。** Retool 的定价页把丰富的权限控制和审计日志列在 Business 起，Git 源代码管理只在 Enterprise；Lovable 的文档把审计日志和发布审批标为仅 Enterprise。

## 什么时候选 Retool 更合适

如果应用是基于你现有系统的内部工具，做应用的人是工程师或技术人员，就选 Retool。对 IT 负责人来说，它最有力的一点是 AI 的触及范围永远不会超过构建者本人：它的安全页面写着“the LLM cannot read or write any resource data the user is not already authorized to access”（LLM 不能读写用户本来就无权访问的任何资源数据），而且 AI 在运行任何写入、插入、更新或删除数据的操作之前，都会先问构建者。它的审计日志记录应用用户运行的每一次查询，包括具体查询语句和参数，并标记经 Retool 的 MCP 服务器接入的 AI 助手所做的操作。如果审计员问某个用户在内部工具里做了什么，这份日志能直接回答。需要知道的限制是：用它的 AI 应用构建器做出的应用，在 Retool 之外运行被列为尚不支持。如果需要按组授权和审计日志，按 Business 做预算；如果每次改动都必须在你自己的仓库里走拉取请求，按 Enterprise 做预算。

## 什么时候选 Lovable 更合适

如果业务团队需要自己把一个想法变成能用的应用，而应用可以跑在 Lovable 替你运营的服务器和数据库上，就选 Lovable。它一次性做出界面、服务器和数据库，负责托管，并让人先在草稿里试改动、再决定是否接受。它的 Git 同步在每个套餐上都可用，所以你的开发人员可以让它的改动走他们已经在用的拉取请求评审；发布应用仍是单独的一步。Lovable 从 Business 套餐起提供单点登录，而 Retool 把它列在仅 Enterprise。如果你希望应用在公开、使用连接器或由外部协作者发布之前，先由管理员或所有者批准，按 Enterprise 做预算；审计日志和定期安全扫描也都在 Enterprise。它的文档对离开有一个直白的承诺：“you are never locked in. You can export your code, migrate your data, self-host parts or all of your stack, or move to another provider at any time.”（你永远不会被锁定。你可以导出代码、迁移数据、自托管部分或全部技术栈，或随时换到其他服务商。）同一页也列出了真要离开时你要接手的事，其中包括“Implementing authentication and enforcing data isolation policies”（实现身份认证并执行数据隔离策略）。

## 我们在 ObjectStack 上测了什么

ObjectStack 是我们做的，它走第三条路：应用的定义是一组普通文件，运行中的应用执行这些文件写下的规则。我们在 ObjectStack 18.5.0 自带的开源 CRM 示例上做了这些检查。这是一个演示应用，不是客户系统。销售代表这个角色可以读取、创建和编辑商机，但不能删除。

| 我们做了什么 | 系统怎么回答 | 这对你意味着什么 |
|:--|:--|:--|
| 一个 AI Agent 用为销售代表账号创建的访问密钥，通过 MCP 尝试删除一条商机。 | 被拒绝两次：第一次因为没有人确认这是一次永久删除；带上确认后，又因为销售代表不能删除商机而被拒。 | 永久删除需要有人确认，而且即便确认了，Agent 也只拥有它所用账号的权限。 |
| 一位销售代表通过应用的 API 尝试同样的删除。 | 被拒绝。 | 这条规则对人和 Agent 一视同仁。 |
| Agent 把这条商机从“prospecting”（初步接触）推进到“qualification”（资格确认），这是销售代表可以做的。 | 一行审计记录：Agent 的账号、这条商机，以及阶段改动前后的值。被拒绝的删除没有留下任何记录。 | 你能拿出证据说明 Agent 改了什么、什么时候改的。被拒绝的尝试只出现在服务器日志里。 |
| 这位销售代表请求读取审计日志。 | 被拒绝。 | 销售代表看不到谁做了什么；要读日志，得有授予该权限的角色。 |
| 一个 AI Agent 修改应用文件，让销售角色可以删除商机。 | 平台对文件的第一道检查通过了。构建停下，用一行字点出这次改动，并一直停着，直到有人运行了接受命令（在我们这次运行中，就是同一个 Agent；见下文的局限）。 | 这次改动不可能悄无声息地生效，但仍需要一个人去评审接受之后产生的那一行改动。 |

最后一项检查背后的机制，在[业务应用该放在数据库里，还是放在代码仓库里？](/zh-Hans/blog/where-should-a-business-app-definition-live/)和[怎样在上线前抓住 AI 悄悄改掉的权限？](/zh-Hans/blog/catch-ai-silent-permission-change-access-matrix-gate/)里有完整解释。打开一条记录如何被审计、这份记录的局限在哪里，见[能证明是谁打开了一条客户记录吗——包括 AI Agent？](/zh-Hans/blog/prove-who-opened-a-customer-record-view-auditing/)

## ObjectStack 不做什么

- **它不判断一次改动对不对。** 平台的第一道检查对这条删除权限一言不发就放行了。构建之所以停下，只是因为这个示例应用保留了一张访问表。新应用在你开启之前没有这张表，而新项目自带的自动检查运行的是第一道检查，不是构建。
- **它不阻止 Agent 接受自己的改动。** 接受只是一条命令，任何能访问这些文件的人或程序都能运行。只有当那一行改动经过你的拉取请求流程、由一个人批准时，它才成为一次评审。
- **它不把被拒绝的尝试写进审计日志。** 两次被拒的删除只出现在服务器日志里，那是审计日志之外的另一个地方。
- **它分不清 Agent 和人。** 审计记录写的是 Agent 的访问密钥所属的账号，记录里没有任何地方写着“AI”。给每个 Agent 一个专属账号，否则日志会把 Agent 做的事记在某个人名下。
- **它不把每一次改动都留在文件里。** 运行中的环境也可以保存在管理界面里或通过 API 做的编辑，这些编辑优先于文件。哪些改动必须经过文件，是你来定的规则。
- **它比两家厂商都年轻。** ObjectStack 自己的对比页写道：“ObjectStack is younger; expect to build more of it yourself.”（ObjectStack 更年轻，要做好更多东西得自己搭的准备。）

## 怎么选

Retool 和 Lovable 各自适合上面描述的情形。如果为应用负责的人必须把“谁能做什么”当成一张简短的表来读，而不是当成代码来读，并且必须在每一次改动生效之前看到它，那就看看第三种选择。这正是 ObjectStack 要解决的情形，局限见上文；想在你自己的流程上试一试，可以[把你的 Agent 指向 ObjectStack](/en/blog/how-to-point-your-agent-at-objectstack/)。

无论选哪个，都向厂商问这三个问题，并把答案留存下来：

1. 当 AI 改动了谁能看到或做什么时，批准人在用户拿到之前到底看到了什么？
2. 批准的人能不能是改动者以外的另一个人？
3. 哪份日志能回答“这个用户或这个 Agent 对那条记录做了什么”，保留多久？

### 应用

ObjectStack 仓库中标签 `@objectstack/cli@18.5.0` 处的 `examples/app-crm`，依赖固定为已发布的 18.5.0 包。它的安全文件把 `crm_sales_user` 权限集授予 `crm_sales_rep` 岗位，该权限集可以读取、创建和编辑 `crm_opportunity`（商机），但不能删除。这个应用开启了访问矩阵检查：`objectstack.config.ts` 旁边放着一份 `access-matrix.json`。

```text
$ npx os --version
@objectstack/cli/18.5.0 linux-x64 node-v22.22.0
```

### 1. AI 的改动、构建的拒绝、评审的 diff

改动位于 `src/security/sales-positions.ts` 第 50 行：

```diff
-    crm_opportunity: { allowRead: true, allowCreate: true, allowEdit: true, allowDelete: false },
+    crm_opportunity: { allowRead: true, allowCreate: true, allowEdit: true, allowDelete: true },
```

`npx os validate` 输出 `✓ Validation passed` 和四条无关的字段警告，退出码 0。`npx os compile` 运行同样的 68 条编写期规则，然后：

```text
  → Checking access-matrix snapshot (ADR-0090 D6)...
  ✗ Access matrix drift (1 change) — capability changes must be reviewed
  • 'crm_sales_user' gains delete on 'crm_opportunity'
  If intended, re-run with --update-access-matrix and commit the snapshot — its diff IS the review artifact.
compile exit 1
```

接受它，即运行 `npx os compile --update-access-matrix`，退出码 0，输出 `Access matrix snapshot written to access-matrix.json (ADR-0090 D6) — review the diff.` 快照的 diff：

```diff
@@ -51,7 +51,7 @@
       "create": true,
       "read": true,
       "edit": true,
-      "delete": false,
+      "delete": true,
       "viewAllRecords": false,
```

随后撤销了这次改动，所以下面运行的应用用的是原来的权限集。

### 2. 被拒绝的删除

### 4. 新项目没有访问表

`npm create objectstack@latest` 今天运行的 `create-objectstack@18.5.0` 包，其模板里没有 `access-matrix.json`，模板的 CI 工作流运行的是 `pnpm validate`，而不是构建。在新项目里第一次运行 `os compile --update-access-matrix`，就是开启这项检查。
