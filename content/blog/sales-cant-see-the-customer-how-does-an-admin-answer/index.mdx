When sales says they can't see a customer, don't rebuild the answer from screens of settings. Ask the system that refused them. An access explain report runs the same checks the platform enforces, for that one person and that one action, and names the check that said no and the role that said yes. The admin reads one line, makes one change, and asks again before replying. That protects you from fixing access by guesswork, where the quickest guess is to grant more than the job needs. The cost: it explains permissions only, so a missing record or a filtered screen still needs a person to look.

*Measured on ObjectStack 18.6.0, the version a new install gets today, on the open-source CRM example from the release tag, run against the published packages. Every request and response is in [The proof](#the-proof).*

## The ticket, answered

The scene is ordinary. An admin creates an account for a new sales representative. The rep signs in, asks for the customer list, and is refused (we made every request through the platform's programming interface, not a screen): "You do not have permission to perform this action. Contact your administrator if you need access." A ticket follows: *sales says they can't see the customer.*

There are two ways to answer it. One is to open the user's settings, then each role, then each bundle of permissions, then the customer object's sharing rules, and work out in your head what the platform would decide. The other is to ask the platform what it decided, and why.

ObjectStack calls the second one the **explain engine**. You name a person, an object and an action, and it returns one entry per check in the order enforcement runs them, each with a verdict, a sentence, and the names of whatever produced that verdict. Two platform terms appear in its answers. A **permission set** is a named bundle of permissions, such as "CRM Sales User: may read, create and edit customers and deals, may not delete". A **position** is a job role that hands bundles out: in the CRM example, the Sales Representative position hands out CRM Sales User. The example calls customers *accounts* and deals *opportunities*; those are the names in the proof.

We put the ticket, and the questions that usually follow it, to the explain engine on the CRM example, then checked every answer against what enforcement actually did to the same user.

| What the admin asked | What the report answered | What it means for you |
|:--|:--|:--|
| Why can't the new rep open Customers? | **Refused at object permissions.** "No resolved permission set grants read" on customers. The rep held only the two bundles every member gets automatically. Enforcement refused the same read. | The account exists but has no sales role. It is not a sharing rule, a data problem or a bug. |
| After the admin assigns the Sales Representative position, can the rep read customers? | **Allowed.** Object permissions **granted by CRM Sales User, held through the Sales Representative position.** Row filter: none. The rep's customer list then returned all 3 customers. | One change, confirmed by the same question before anyone tells sales it is fixed. |
| Can the rep delete a deal? | **Refused at object permissions:** no bundle grants delete. Row-level security also narrows deletes; asked about one deal, the report shows the condition: only deals the rep created. Enforcement refused the delete. | By the report, adding delete to the sales bundle would not be enough on its own: a member may delete only what they created. We did not grant delete to test it. |
| Can the rep read deals, and which ones? | **Allowed**, granted by CRM Sales User through Sales Representative. Row filter: none, so every deal. Enforcement listed all 12. | The row filter is the one lists and reports apply. On an allowed read, "none" means the whole table. |
| Can the rep export deals? | **Refused at object permissions:** no bundle grants export, although the rep can read every deal. Enforcement refused the export. | Export is its own grant. Asking "can they read?" answers yes and tells you nothing. |
| Who may ask these questions? | The rep about themselves: answered. A help-desk colleague with no admin role, about the rep: **refused**. The same colleague after being made an organization admin: answered. | The access report is itself access-controlled. It says who holds what, so not everyone may read it. |

One request answers each row; the transcripts are in [The proof](#the-proof). We did not time an admin reading them, so we make no claim about minutes.

## Explained by construction

The useful property of this report is not that it is detailed. It is that it cannot disagree with enforcement. ObjectStack's guide says the explain engine ["walks the **same code paths the enforcement middleware runs** … so the report is *explained by construction*, never a parallel re-implementation that can drift."](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/content/docs/permissions/explain.mdx#L7-L13) The schema reference is shorter: the report ["IS enforcement, minus the throw."](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/content/docs/references/security/explain.mdx#L12-L17)

That is the difference from a permissions spreadsheet or a diagram of roles, which describe what someone *meant* to configure. A description can be out of date. This report is not a second description: by design it is the same code path that refused the rep, run without the refusal. We did not audit that design line by line. What we checked is narrower: in our run, each of the five verdicts in the table that enforcement could confirm matched what enforcement then did to the same user, request for request.

Reading one takes three looks:

1. **The verdict.** Allowed or not, for this person, this object, this action.
2. **The check that said no.** One entry is marked as refusing. In every refusal we measured, it was object permissions, the check of whether any bundle the person holds allows this action on this kind of record.
3. **Who said yes.** A granting entry names the bundle and how the person holds it. "CRM Sales User, through position Sales Representative" tells the admin both what to look at and where it came from. A refusal at object permissions names nobody, because nobody granted it. The first entry lists every bundle the person does hold, so the gap is visible.

For a read, the report also carries the **row filter**: the condition the platform adds to every list, search and report that person runs. In the CRM example every customer and deal is shared across the organization, so the filter was empty. In an app where reps see only their own deals, it would show that condition, and that condition is the answer to "why can they see these deals and not that one?"

Ask about an object and the report returns nine checks. Ask about one record and it returns ten: an organization wall comes first, which in our single-organization install answered "does not apply". ObjectStack's two documentation pages give [nine](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/content/docs/permissions/explain.mdx#L20-L23) and [ten](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/content/docs/references/security/explain.mdx#L19-L21) for that reason.

## Who may ask

An access report says which bundles a person holds and how they got them. That is sensitive, so the question is itself governed. On 18.6.0 the runtime's rule is: yourself, always; another user only if you hold the right to manage users, administer an organization that user belongs to, or hold a delegated admin scope that covers them ([source](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/packages/plugins/plugin-security/src/security-plugin-explain-access.ts#L134-L138)). Everyone else is refused.

We measured three askers. The rep asking about themselves was answered. A help-desk colleague, an ordinary member, asking about the rep was refused, and the refusal named the three ways to qualify. After the admin made that colleague an administrator of the organization, the platform gave them the organization administrator bundle, and the same question was answered. So an organization administrator can answer these tickets without holding the platform-wide right to manage users. We did not measure the delegated-scope route, which is the narrower way to let a help desk answer these tickets.

## The case for looking at configuration instead

The explain report is not the only good tool, and for some tickets it is not the best one.

- **Reading the configuration works everywhere and shows the neighbours.** With three roles and one bundle, as in this CRM example, opening the role is as fast as asking, it needs no feature the platform may lack, and it shows everything the role grants, not only the one decision.
- **Logging in as the user shows the screen.** ObjectStack lets an administrator [impersonate a user to verify their access](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/content/docs/permissions/authentication.mdx#L1230-L1233), and many platforms offer something like it. If the complaint is "the button is missing" or "the menu is empty", seeing the screen is faster than reading checks. The report answers why a decision came out as it did; impersonation answers what the person sees.
- **A sweep beats a zoom for policy questions.** "Who can delete deals?" is a question about every role at once. ObjectStack's guide draws that line itself: explain ["is the same evaluation logic pointed at one decision at runtime; the matrix is the build-time sweep across all of them"](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/content/docs/permissions/access-matrix.mdx#L81-L83). We covered the matrix in [How do you catch an AI's silent permission change before it ships?](/en/blog/catch-ai-silent-permission-change-access-matrix-gate/)
- **The settings are where you find the fix and make it.** A refusal tells you what is missing: no bundle the rep holds grants read on customers. It does not tell you which role supplies that. You look that up in the roles and bundles, and the change is made there. On a platform where an AI writes those definitions, the change arrives as a diff someone [reviews](/en/blog/how-to-review-ai-generated-app-changes/).

## What the report does not solve

- **It explains permissions, not data.** A customer that was never created, was merged away, or is hidden by a view's own filter looks the same to the person complaining. The report will say "allowed" and the customer will still be missing. A person has to look.
- **It does not say whether the access is right.** It told us the rep cannot export deals. Whether sales *should* export deals is a policy decision, and so is whether the fix is a position or a narrower bundle.
- **It does not show what else the fix grants.** We asked about reading customers. The position we assigned also lets the rep create and edit customers, contacts, deals, deal product lines, leads and activities. The report confirmed the one decision we asked about. To see everything a role brings, read the role, or use the build-time matrix.
- **Some answers need a second question.** For a delete, the object-level report said row-level security narrows the rows but did not show the condition. Asked about one deal, it did: only deals the rep created. It labelled the rule generically, not by the name the policy carries in the platform's default bundle; the proof shows both.
- **Read the verdict before the row filter.** On a refused read, the report still carried an empty row filter, which on its own would mean "every row". The [schema reference](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/content/docs/references/security/explain.mdx#L110) says the decision is the verdict plus the row-level check, not the filter alone.
- **It needs the security plugin.** The guide says plainly: ["A deployment without `@objectstack/plugin-security` answers 501"](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/content/docs/permissions/explain.mdx#L116), meaning it cannot answer at all.

ObjectStack's guide also says Studio's Access area builds its ["why can this user access?" panel](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/content/docs/permissions/explain.mdx#L120-L121) on this report. We measured the report through its programming interface, not that screen.

## In development

The report's format already reserves room for more than it fills today. The schema reference describes a standing for each person (platform administrator, organization administrator, member, external member) and a marker for which checks belong to the organization wall, as vocabulary ["the β engine + UI will fill"](https://github.com/objectstack-ai/objectstack/blob/958ee03594968c651db1bc40ecb05bfe72f94b2d/content/docs/references/security/explain.mdx#L30-L34). On 18.6.0 both already appear when you ask about one record: every check carried the wall marker, and the rep's standing came back as member. Neither appears on an object-level answer. The reference does not say what else that later engine and screen will add, and we measured nothing beyond these two fields.

## Point your agent at the report

If an AI agent writes your app's roles and bundles, the explain report is how a person checks the result one decision at a time, and how the agent can check its own work before it hands you a diff. [Point your agent at ObjectStack](/en/blog/how-to-point-your-agent-at-objectstack/) and ask it to explain the access it just granted.
