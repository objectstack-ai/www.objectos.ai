**La respuesta.** Declara la base de datos como origen de datos `external`, vincula cada tabla que necesites a un objeto, asigna los nombres de columna antiguos a nombres de negocio, y esas tablas pasan a ser objetos que personas, informes y agentes de AI consultan por las mismas puertas REST y MCP que cualquier otro, con los mismos permisos. No se copia nada. En ObjectStack 18.4.0, la versión que instala hoy `npm create objectstack@latest`, un cambio hecho directamente en la base de datos de origen apareció en la lectura siguiente, y la base de datos propia de ObjectStack contenía **0 de los 2.400 pedidos** que estaba sirviendo. Las escrituras se rechazan hasta que el origen de datos y el objeto lo permitan los dos. Lo llamaré **ontología de lectura directa** (read-through ontology): nombres, relaciones, permisos y herramientas de AI sobre tablas que no son tuyas, con cada lectura entregada al sistema que sí lo es. Abajo va la transcripción y después los cinco sitios donde se detiene.

## Tres maneras de hacer usable una base de datos en marcha

A la mayoría de las empresas a las que se les pide «preparar los datos para la AI» ya tienen los datos, en una base que escribe otro sistema. Hay tres maneras honestas de poner encima una capa de negocio gobernada, y cada una cuesta algo distinto.

| | Reconstruir | Copiar | Leer a través |
|:--|:--|:--|:--|
| Qué se mueve | datos y sistema | datos, según un calendario | nada |
| Frescura | manda el sistema nuevo | la de la última copia | el origen al leer |
| De quién es el esquema | tuyo | tuyo, el de la copia | del sistema de origen |
| Coste del primer día | un proyecto de migración | una canalización que construir y vigilar | un origen de datos y un archivo por tabla |
| Uniones entre orígenes | sí | sí, la razón principal para copiar | dos lecturas, unidas en memoria |
| Carga sobre el origen | ninguna tras el cambio | una por cada copia | cada lectura |

El argumento a favor de copiar es real, no un hombre de paja: una copia se puede indexar, unir con cualquier cosa, buscar y explotar en informes mientras el origen va lento o está caído, y nunca pone las consultas de un panel sobre un sistema de pedidos en producción. Si eso es lo que necesitas, copia. El argumento a favor de leer a través es más estrecho y, donde encaja, más fuerte: el día en que conectas, la capa de negocio es correcta, porque no hay nada que mantener sincronizado. El ADR que especifica el mecanismo enumera entre sus objetivos «Register existing remote tables as ObjectStack objects **without touching the remote schema**» (registrar tablas remotas existentes como objetos de ObjectStack sin tocar el esquema remoto) y «Default to read-only; require **two explicit opt-ins** (datasource level + object level) to enable writes» (solo lectura por defecto; para escribir hacen falta dos permisos explícitos, en el origen de datos y en el objeto).

## El sistema de pedidos que ObjectStack nunca tocó

El origen es un archivo SQLite escrito por un breve script de Python que hace de sistema de pedidos antiguo: una tabla `customers` y una tabla `orders`, cinco clientes y 2.400 pedidos, con los nombres de columna que tienen los sistemas viejos.

```sql
CREATE TABLE customers (
  cust_no      TEXT PRIMARY KEY,
  cust_name    TEXT NOT NULL,
  cust_region  TEXT,
  credit_limit REAL
);
CREATE TABLE orders (
  order_no   TEXT PRIMARY KEY,
  cust_no    TEXT NOT NULL REFERENCES customers(cust_no),
  amount     REAL,
  status     TEXT,
  placed_on  TEXT
);
```

SQLite es el dialecto que un proyecto recién creado puede abrir sin añadir nada. Probé primero con Postgres y el arranque lo dijo sin rodeos: «The database client package `pg` is not installed, so no connection was attempted. It is an OPTIONAL install of @objectstack/driver-sql … `npm install pg` (pnpm add pg / yarn add pg)» (el paquete cliente `pg` no está instalado, así que no se intentó conectar; es una instalación opcional de @objectstack/driver-sql). La guía documenta además Oracle y SQL Server como dialectos solo de federación («ObjectStack reads an existing Oracle schema live … but it never owns one», ObjectStack lee en vivo un esquema Oracle existente, pero nunca es su dueño), y servicios OData v4 como SAP S/4HANA y Dynamics 365 mediante un controlador incluido. No ejecuté ninguno de los tres aquí.

En un proyecto generado con `npm create objectstack@latest` (el paquete se llama `sales`), tres archivos hicieron el trabajo. El origen de datos:

```ts
export const Erp = defineDatasource({
  name: 'erp',
  label: 'Order system (SQLite)',
  driver: 'sqlite',
  schemaMode: 'external',            // ObjectStack never runs DDL here
  config: { filename: '/…/legacy/erp.db' },   // absolute path, trimmed
  external: {
    allowWrites: false,
    validation: { onMismatch: 'fail', checkOnBoot: true },
  },
});
```

Un objeto por tabla, con `external.columnMap` (columna remota → campo local) convirtiendo `cust_no`, `cust_name` y `cust_region` en `id`, `name` y `region`:

```ts
export const Customer = ObjectSchema.create({
  name: 'sales_customer',
  label: 'Customer',
  sharingModel: 'public_read',
  datasource: 'erp',
  external: {
    remoteName: 'customers',
    columnMap: { cust_no: 'id', cust_name: 'name', cust_region: 'region' },
  },
  fields: {
    name: Field.text({ label: 'Name', searchable: true }),
    region: Field.text({ label: 'Region' }),
    credit_limit: Field.currency({ label: 'Credit limit' }),
  },
});
```

`sales_order` tiene la misma forma sobre `orders`, con `cust_no` asignado a un campo de búsqueda `customer`. Y un conjunto de permisos para quienes deben ver a los clientes, pero no cuánto crédito tienen:

```ts
export const SalesReader = definePermissionSet({
  name: 'sales_reader',
  objects: { sales_customer: { allowRead: true } },
  fields: { 'sales_customer.credit_limit': { readable: false, editable: false } },
});
```

No hace falta teclear los objetos a mano. La ruta de administración `GET …/datasources/erp/external/tables` respondió con `customers` (4 columnas) y `orders` (5), y `POST …/external/tables/customers/draft` devolvió un borrador de objeto para la tabla. El borrador conserva los nombres remotos como nombres de campo y empieza con `sharingModel: 'private'`, lo que importa más abajo: renombré con `columnMap` y elegí `public_read` a propósito.

Mi primer borrador de `sales_order` declaraba `placed_on` como campo `date`. El arranque lo rechazó:

```text
✗ Object 'sales_order' does not match its remote table on datasource 'erp':
✗ type_mismatch: orders.placed_on (expected date, actual text)
```

Es `schemaMode: 'external'` haciendo su trabajo; según la guía, «A mature external DB — **DDL forbidden**; a schema mismatch **fails** boot» (una base externa madura: DDL prohibido, y una discrepancia de esquema hace fallar el arranque). ObjectStack no modificó la columna para que encajara. Cambié el campo a `text`, que es lo que guarda el sistema de pedidos.

## Cinco preguntas, respondidas por la aplicación en marcha

Todo lo que sigue es salida real de `objectstack dev` en 18.4.0, recortada solo donde se indica. `$B` es la dirección del servidor de desarrollo, y `sql.py` es un ayudante de Python de tres líneas que ejecuta una sentencia contra el archivo, porque la máquina no tenía el comando `sqlite3`.

### ¿Es en vivo o una copia?

Leer un cliente, cambiarlo en la base de datos propia del sistema de pedidos, volver a leer:

```bash
curl -s -b admin.cookies "$B/api/v1/data/sales_customer/C-1002"
```

```json
{"object":"sales_customer","id":"C-1002","record":{"credit_limit":180000,"id":"C-1002","name":"Borealis GmbH","region":"EU"}}
```

```bash
python3 sql.py erp.db "UPDATE customers SET credit_limit = 95000 WHERE cust_no = 'C-1002'"
curl -s -b admin.cookies "$B/api/v1/data/sales_customer/C-1002"
```

```json
{"object":"sales_customer","id":"C-1002","record":{"credit_limit":95000,"id":"C-1002","name":"Borealis GmbH","region":"EU"}}
```

No corrió ninguna sincronización, porque no la hay. La base de datos propia de ObjectStack tenía en ese momento 84 tablas, y buscar `customer` u `order` en sus nombres no devolvió nada. Los filtros se trasladan al origen, y un campo de búsqueda se expande entre las dos tablas remotas:

```bash
curl -s -b admin.cookies "$B/api/v1/data/sales_order?status=pending&top=2&expand=customer"
```

```json
{"object":"sales_order","records":[
  {"amount":7020.73,"status":"pending","placed_on":"2026-04-04","id":"SO-00003",
   "customer":{"credit_limit":60000,"id":"C-1003","name":"Cyan Pacific","region":"APAC"}},
  … one more row, trimmed …],
 "total":480,"hasMore":true}
```

### ¿Puede algo escribir en él?

Por defecto no, ni siquiera el administrador de la plataforma, y por ninguna puerta:

```bash
curl -s -b admin.cookies -X POST "$B/api/v1/data/sales_customer" \
  -H "content-type: application/json" -d '{"id":"C-9999","name":"Test Co","region":"EU"}'
```

```json
HTTP 403
{"error":"Write 'insert' blocked on object 'sales_customer': datasource 'erp' is external (schemaMode=external). Requires datasource.external.allowWrites=true (got false) AND object.external.writable=true (got false).","code":"EXTERNAL_WRITE_FORBIDDEN","object":"sales_customer"}
```

Un `PATCH` de `C-1002` y un `DELETE` del pedido `SO-00001` respondieron el mismo `403`, nombrando `update` y `delete`. El sistema de pedidos seguía con 5 clientes, 2.400 pedidos y el límite de crédito que él mismo había fijado. El error nombra los dos interruptores, y la guía enuncia la regla: «With either gate off, insert/update/delete on the federated object is rejected» (con cualquiera de las dos compuertas cerrada, se rechaza insertar, actualizar o borrar en el objeto federado).

### ¿Qué ve un miembro?

Mia es una miembro que el administrador creó con `POST /api/v1/auth/admin/create-user`. Sin ninguna concesión, ambos objetos responden `403 PERMISSION_DENIED`: un objeto federado está denegado por defecto como cualquier otro. Después de que el administrador le concede `sales_reader`:

```bash
curl -s -b member.cookies "$B/api/v1/data/sales_customer?region=EU"
```

```json
HTTP 200
{"object":"sales_customer","records":[{"id":"C-1002","name":"Borealis GmbH","region":"EU"},{"id":"C-1004","name":"Delta Freight","region":"EU"}],"total":2,"hasMore":false}
```

`credit_limit` no está en su respuesta. Los pedidos siguen respondiendo `403`. Y no puede sacar la cifra oculta preguntando de lado:

```bash
curl -s -b member.cookies "$B/api/v1/data/sales_customer?credit_limit=95000"
```

```json
HTTP 403
{"error":"[Security] Access denied: query on 'sales_customer' references field(s) not readable by the caller: credit_limit. Filtering, sorting, grouping, or aggregating by a hidden field would leak its values (filter oracle) — remove these predicates or grant field read access.","code":"PERMISSION_DENIED","object":"sales_customer"}
```

Ordenar por ese campo respondió lo mismo. La base de datos de origen no sabe quién es Mia; el permiso se aplica en la capa, en cada lectura, antes de que la fila le llegue.

### ¿Puede un agente de AI saltárselo?

Cada aplicación de ObjectStack es un servidor MCP en `/api/v1/mcp`. Con la sesión de Mia, el `list_objects` de un agente respondió con un solo objeto, `sales_customer`: ni siquiera puede ver que existen pedidos. El resto, recortado a los resultados de las herramientas:

```text
query_records  sales_customer  where {"region":"NA"}  → 2 records: Aurora Labs, Ember Foods (no credit_limit)
query_records  sales_order     limit 1                → {"code":"PERMISSION_DENIED","status":403}
query_records  sales_customer  limit 51               → Too big: expected number to be <=50 at limit
create_record  sales_customer  {"id":"C-9998",…}      → {"code":"EXTERNAL_WRITE_FORBIDDEN","status":403}
```

El agente obtiene exactamente la vista de Mia, como mucho 50 filas por llamada, y ninguna escritura. Ni la edad ni el fabricante de la base de datos cambian eso, porque el agente nunca habla con la base de datos.

### ¿Funcionan los informes entre tablas?

Un dataset es la capa semántica que leen los informes y las preguntas a la AI. Este agrupa los ingresos de pedidos por la región del cliente, una columna que vive en la otra tabla:

```ts
export const OrderRevenue: Dataset = {
  name: 'sales_order_revenue',
  label: 'Order revenue',
  object: 'sales_order',
  include: ['customer'],
  dimensions: [{ name: 'region', label: 'Region', field: 'customer.region', type: 'string' }],
  measures: [
    { name: 'revenue', label: 'Revenue', aggregate: 'sum', field: 'amount' },
    { name: 'orders', label: 'Orders', aggregate: 'count' },
  ],
};
```

Consultado con la herramienta MCP `query_dataset` y contrastado con un `JOIN` ejecutado en el propio sistema de pedidos:

| Región | Ingresos (dataset) | Pedidos |
|:--|--:|--:|
| APAC | 6,127,544.10 | 480 |
| EU | 11,995,588.50 | 960 |
| NA | 12,470,792.17 | 960 |

```text
$ python3 sql.py erp.db "SELECT c.cust_region, round(sum(o.amount),2), count(*) FROM orders o JOIN customers c ON c.cust_no=o.cust_no GROUP BY 1 ORDER BY 1"
('APAC', 6127544.1, 480)
('EU', 11995588.5, 960)
('NA', 12470792.17, 960)
```

La misma respuesta, al céntimo. Cómo llega ahí es el primero de los límites.

## Dónde se detiene la capa de lectura directa

Estos son los bordes que medí, más dos que la documentación fija para controladores que no ejecuté.

**1. Ninguna consulta une orígenes de datos.** El dataset de arriba no fue un único `JOIN` enviado a SQLite. Para un objeto federado, dice el propio comentario del compilador de analítica, el dataset se sirve por «the ObjectQL FK-expand path (two reads, joined in memory)» (la ruta de expansión de claves foráneas de ObjectQL: dos lecturas, unidas en memoria). Lo mismo ocurre cuando la relación cruza de la base de datos de ObjectStack al sistema de pedidos: un objeto nativo `sales_visit` con un campo de búsqueda a `sales_customer` expandió el cliente (`?expand=customer`) y filtró por su región con la forma anidada `{"customer":{"region":"EU"}}`. Ambas funcionan como lecturas separadas. Lo que no existe es una sentencia que abarque dos bases de datos. Los no objetivos del ADR del runtime lo dicen: «cross-datasource JOINs in one query (federated objects are queried per-datasource)» (JOIN entre orígenes en una sola consulta; los objetos federados se consultan por origen de datos). Dos rechazos que encontré no son límites de la federación, y los nombro para que nadie culpe a la capa equivocada: un filtro con ruta de puntos como `?customer.region=EU` y `aggregate_records` agrupado por `customer.region` respondieron `400 INVALID_FIELD` en el nativo `sales_visit` exactamente igual que en `sales_order`.

**2. El tope de filas es de los controladores de plugin, no de SQL.** Sobre el controlador SQLite integrado no hay tope: `?top=5000` en pedidos devolvió las 2.400 filas. Poner un tope en ese origen de datos se rechaza al validar:

```text
✗ external.rowCap: `external.rowCap` caps the rows the engine reads from a plugin driver, which it holds behind its correctness floor; the 'sqlite' driver is built in, runs the whole query itself and is never capped, so the key would do nothing here. Remove `rowCap`.
```

Sobre un controlador de plugin, OData incluido, la guía fija el tope: «A read that matches more rows than the datasource's row cap is refused with `422 EXTERNAL_ROW_CAP_EXCEEDED` rather than answered from a partial set» (una lectura que coincide con más filas que el tope del origen se rechaza con 422 en lugar de responder con una parte), «The default is 1000 rows» (por defecto, 1000 filas), como mucho 10.000. No lo ejecuté aquí.

**3. El uso compartido controlado por el padre depende del controlador.** En un controlador de plugin, «A read whose scope composes a `ReadableIds` leaf, such as an object `controlled_by_parent`, is refused» (se rechaza una lectura cuyo alcance incluye una hoja `ReadableIds`, como un objeto `controlled_by_parent`). En SQL medí lo contrario: con `sales_order` en `controlled_by_parent` mediante un `master_detail` a clientes, Mia leyó pedidos, y cuando el registro padre dejó de ser visible para ella, los hijos desaparecieron con él (punto siguiente).

**4. El uso compartido por propietario necesita una columna de propietario.** Con `sales_customer` en `private`, el valor por defecto del borrador, sobre una tabla sin columna de propietario, la respuesta de Mia fue `{"records":[],"total":0}` para clientes y para los pedidos controlados por el padre, mientras el administrador seguía leyendo los 5 y los 2.400. La guía lo advierte: «only an `owner_id` declared in `fields`, or named by an `external.columnMap` entry, counts as one. Without it a member reads no row» (solo cuenta como propietario un `owner_id` declarado en `fields` o nombrado por una entrada de `external.columnMap`; sin él, un miembro no lee ninguna fila). Asigna la columna de propietario del origen, o elige `public_read` y acota con conjuntos de permisos, como arriba.

**5. El rendimiento es el del origen.** Cada lectura se ejecuta en ese momento sobre el sistema de pedidos: una página de lista lee las filas y el total, y un panel que alguien deja abierto es una consulta contra tu base de producción. La capa no añade índices que el origen no tenga, y el cambio de arriba apareció en la lectura siguiente porque nada en medio guardaba la fila vieja. Si el origen no aguanta la carga, apunta el origen de datos a una réplica que ya operes, o copia los datos.

## Cuándo una copia es la mejor herramienta

La guía de ObjectStack sobre objetos virtuales traza la línea en una frase: «Make the object virtual when a copy would be **wrong**, and real when a copy is merely **convenient**» (haz el objeto virtual cuando una copia sería un error, y real cuando una copia solo es cómoda). Una copia es un error cuando el remoto calcula la respuesta al pedirla, cuando los datos no deben aterrizar (residencia, licencia, auditoría) o cuando cambian más rápido de lo que cualquier sincronización puede seguir. Una copia es cómoda para datos de referencia que cambian despacio y para informes que unen muchos orígenes. Lo primero, léelo a través; lo segundo, cópialo. Para un sistema ya apagado solo queda una exportación, y [un mapeo de importación con su ensayo en seco](/es/blog/how-to-import-a-spreadsheet-from-an-old-system/) es como ese archivo llega al modelo sin sus códigos antiguos.

## En desarrollo: copiar desde una base de datos

Copiar filas de una tabla federada a un objeto normal de ObjectStack según un calendario («sync-in») está diseñado, pero no está en 18.4.0. Su documento, el ADR-0153, está en estado Proposed y dice de sí mismo: «This record declares; it implements nothing» (este documento declara; no implementa nada). Lo que describe: «A remote table or API collection becomes an ordinary object whose rows were **copied** by a pull» (una tabla remota o una colección de API se convierte en un objeto normal cuyas filas se copiaron con una extracción), y su regla práctica asigna «Reports, analysis, AI question answering, joins across sources; a slow or fragile legacy system» (informes, análisis, preguntas a la AI, uniones entre orígenes; un sistema heredado lento o frágil) al sync-in y «Live data, one table at a time; the legacy system must not be touched; data that must not land» (datos en vivo, una tabla cada vez; no se puede tocar el sistema heredado; datos que no deben aterrizar) a la federación. Nada de esta sección se midió.

## Qué leer en el diff

Si un agente escribe el vínculo, la revisión es corta, porque cada decisión es una línea:

| Línea del diff | Qué decide |
|:--|:--|
| `schemaMode: 'external'` | ObjectStack nunca altera el origen; una deriva hace fallar el arranque |
| `allowWrites` / `writable` | ambos deben ser `true` para que una escritura llegue al origen |
| `columnMap` | con qué nombres de negocio aparecen las columnas del origen |
| `sharingModel` | `private` necesita una columna de propietario asignada, o los miembros no leen nada |
| `fields` del conjunto de permisos | qué columnas del origen un miembro nunca ve ni usa para filtrar |
| `rowCap` | solo para controladores de plugin; rechazado en un controlador SQL integrado |

La [ontología](/en/glossary/ontology/) es la capa que pone nombre a tu negocio: objetos, relaciones, permisos, acciones. La federación significa que puede nombrar una base de datos que tú no construiste, desde el primer día, sin un proyecto de migración por delante y con el [modelo de permisos](/en/glossary/permission-model/) aplicado a cada lector, sea persona o agente.

## Apunta tu agente hacia aquí

Dale a tu agente de código el vínculo como regla, no este artículo: un origen de datos `external`, un objeto por tabla con `remoteName` y `columnMap`, un `sharingModel` escrito a propósito, los dos interruptores de escritura apagados y un conjunto de permisos por público. [Cómo configurar el agente de código](/en/blog/how-to-point-your-agent-at-objectstack/) cubre el archivo de reglas, el endpoint MCP que expone la aplicación en marcha y la especificación; la [guía de orígenes de datos externos](https://objectstack.ai/docs/data-modeling/external-datasources) es la referencia que debe leer el agente. `npm create objectstack@latest` instala la 18.4.0, la versión en la que corrieron todas las transcripciones de arriba.
