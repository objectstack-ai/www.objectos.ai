**Lesen Sie das Quellsystem live, wenn die Daten sekundengenau aktuell sein müssen oder nirgendwo sonst gespeichert werden dürfen. Kopieren Sie sie herein, wenn Menschen, Berichte und KI sie mit voller Geschwindigkeit verknüpfen, filtern und befragen sollen.** Beides hat seinen Preis. Live-Lesen wartet jedes Mal auf das Quellsystem und kann zwei Datenbanken nicht in einer Abfrage verbinden. Eine Kopie ist nur so frisch wie ihre letzte geplante Aktualisierung. Wenn Sie kopieren, gilt die Regel **ein Schreiber pro Zeile**: Nur die geplante Aktualisierung schreibt die Kopie. Niemand bearbeitet sie, auch kein Administrator. Eine Änderung wird in der Quelle vorgenommen, über eine eigens dafür gebaute Aktion, und die nächste Aktualisierung übernimmt sie. In meinem Test las eine Aktualisierung nur 3 der 7 Zeilen der Quelle, und eine Änderung an der Kopie wurde einem Mitglied ebenso verweigert wie einem Administrator.

*Gemessen auf ObjectStack 18.5.0, der am 2026-11-16 veröffentlichten aktuellen Version. Alle Protokolle stehen im letzten Abschnitt, „Der Beweis“.*

## Live lesen oder hereinkopieren?

**Föderation** lässt die Zeilen, wo sie sind, und leitet jede Abfrage an die Quelle weiter. **Sync-in** kopiert sie nach Zeitplan in eine gewöhnliche Tabelle, die der Plattform gehört. Eine **Connector-Aktion** ruft das andere System über eine Schaltfläche oder eine Automatisierung auf und speichert keine seiner Zeilen. ObjectStacks Entwurfsdokument zur Synchronisation, ADR-0153, beim Tag 18.5.0 noch im Status „Vorgeschlagen“, wählt so zwischen ihnen:

| Ihre Lage | Wahl |
|:--|:--|
| Live-Daten, eine Tabelle nach der anderen; das Altsystem darf nicht angefasst werden; Daten, die nicht außerhalb der Quelle gespeichert werden dürfen | **Live lesen** (Föderation) |
| Berichte, Analysen, KI-Fragen, Verknüpfungen über Quellen hinweg; ein langsames oder fragiles Altsystem; die Ergebnisse eines Data Warehouse | **Hereinkopieren** (Sync-in) |
| Etwas im anderen System auslösen; es werden keine Zeilen gespeichert | **Keins von beiden**: eine Connector-Aktion |

Für das Live-Lesen spricht viel. Eine föderierte Tabelle ist immer aktuell: Zwischen einer Änderung an der Quelle und dem, was ein Mitglied sieht, gibt es keine Verzögerung. Nichts wird dupliziert, also gibt es keine zweite Kopie personenbezogener Daten, die zu sichern, aufzubewahren oder zu löschen wäre. Und die Quelle bleibt der einzige Ort, an dem Daten geschrieben werden. Ein [Begleitartikel](/de/blog/ai-business-layer-over-an-existing-database/) geht die Föderation nach ihrer eigenen Logik durch, und die Seite [Bestehende Systeme anbinden](/de/connect-existing-systems/) stellt alle drei nebeneinander. Wenn Sie genau diese Eigenschaften brauchen, hören Sie hier auf: Eine Kopie ist das falsche Werkzeug.

Eine Kopie ist die bessere Wahl, wenn das Live-Lesen an seine Grenzen stößt. Die Plattform kann zwei Datenbanken nicht in einer einzigen Abfrage verbinden (sie liest jede und führt die Zeilen im Speicher zusammen), jeder Lesezugriff wartet auf das entfernte System, und Lesezugriffe über einen zusätzlich installierten Datenbank-Connector sind auf eine Höchstzahl von Zeilen begrenzt. In den Worten des Entwurfsdokuments: „Werden die Zeilen in ein gewöhnliches Objekt kopiert, entfallen diese Grenzen: Dann gehören der Plattform die Indizes, die Abfrageoperatoren, die Berechtigungen und die Verfügbarkeit.“ Einmal kopiert, ist es eine weitere Tabelle, die bestehende Berechtigungen, Berichte und KI-Werkzeuge unverändert lesen.

## Die Regel, die eine Kopie ehrlich hält: ein Schreiber pro Zeile

Das Risiko jeder Kopie ist, dass sie zu einem zweiten führenden System wird: Jemand korrigiert einen Preis in der Kopie, die Quelle erfährt nie davon, und die beiden widersprechen sich. Die Regel „ein Schreiber pro Zeile“ verhindert das mit vier Regeln, die die Laufzeit durchsetzt:

1. **Der Pull schreibt die Zeilen.** Der Pull ist die geplante Aktualisierung: ein Job, der die Quelle liest und die Kopie schreibt, unter der eigenen Identität der Plattform, nicht unter der eines Benutzers, und der nur liest, was sich seit seinem letzten Lauf geändert hat. Diese Zeilen findet er über ein *Watermark*: eine Spalte „zuletzt geändert“ in der Quelle.
2. **Sonst schreibt niemand.** Die Kopie ist als *synced-Objekt* deklariert: eine Tabelle, deren Zeilen nur der Pull schreiben darf. Bearbeiten, Einfügen oder Löschen durch ein Mitglied, einen Administrator oder einen API-Aufrufer wird abgewiesen, gleich welche Berechtigungen sie haben.
3. **Eine Änderung geht an die Quelle, über eine deklarierte Aktion.** Eine *deklarierte Aktion* ist eine in der App definierte Schaltfläche mit eigener Berechtigungsprüfung, die die API der Quelle aufruft. Sie fasst die Kopie nicht an; der nächste Pull aktualisiert sie.
4. **Es gibt keine andere Richtung.** Keine Zwei-Wege-Synchronisation und kein Zusammenführen widersprüchlicher Änderungen.

Regel 4 ist der Kern. Eine Zwei-Wege-Synchronisation hat zwei Schreiber pro Zeile und braucht deshalb eine Regel für die Zeile, die beide Seiten geändert haben: Der letzte Schreiber gewinnt, Zusammenführen auf Feldebene, eine Warteschlange von Konflikten, die ein Mensch auflösen muss. Jede davon verwirft entweder die Änderung einer Seite oder braucht einen Menschen als Schiedsrichter. Mit einem Schreiber gibt es keine solche Zeile und kein Zusammenführen, das schiefgehen kann.

## Was ich getestet habe und was es für Sie bedeutet

Ich habe eine frische ObjectStack-App mit einem Stellvertreter für ein „altes ERP“ verbunden, einer kleinen Datenbank mit sechs Teilen, und einem Mitglied, Mia, Lese- und absichtlich auch Bearbeitungsrechte auf der Kopie gegeben, um zu sehen, ob eine Berechtigung die Regel umgehen kann. Der Pull lief in diesem Test alle 30 Sekunden; Ihr Zeitplan bestimmt die Verzögerung. Zeiten in UTC am 2026-11-16.

| Was ich getan habe | Was das System antwortete | Was es für Sie bedeutet |
|:--|:--|:--|
| Die App gebaut, nachdem die Markierung „synced“ an der Kopie entfernt war | Der Build schlug fehl und nannte die fehlende Markierung | Wenn der Build durchläuft, ist der Schutz aktiv |
| Den Pull einmal laufen lassen, um 02:31:21, dann Mia die Kopie auflisten lassen | 6 Zeilen gelesen, 6 angelegt, abgeschlossen, ein Laufprotokoll hinterlassen; Mia sah die 6 Zeilen | Jede Aktualisierung ist protokolliert, und Mitglieder lesen die Kopie wie jede andere Tabelle |
| Mia, die Bearbeitungsrechte hat, änderte den Preis von P-2001; ein Administrator versuchte dasselbe | Für beide abgewiesen; die Meldung sagt, was stattdessen zu tun ist | Weder ein Mitglied mit Bearbeitungsrechten noch ein Administrator kann die Kopie über die App oder ihre API bearbeiten |
| P-1003 direkt im ERP geändert und P-3002 hinzugefügt | Nächster Lauf, 02:31:51: 3 der 7 Zeilen gelesen, 1 angelegt, 2 aktualisiert | Eine Aktualisierung liest, was sich geändert hat, nicht die ganze Tabelle |
| Mia führte auf P-2001 die Aktion „Change price in ERP“ aus und las dann die Zeile | Erlaubt; die API des ERP protokollierte eine Änderung. Die Kopie zeigte weiter 3.8 | Die Aktion hat die Quelle geändert, nicht die Kopie |
| Auf den nächsten Lauf gewartet, 02:32:21 | 3 gelesen, 3 aktualisiert; P-2001 zeigt jetzt 4.1 | Die Kopie zeigt immer nur, was das ERP enthält |

Zwei Details. Eine der 2 „aktualisierten“ Zeilen des zweiten Laufs, P-3001, hatte sich nicht geändert: Ein Lauf liest die Zeilen an der Stelle, an der der letzte aufhörte, erneut. Lesen Sie die Zahl also als „geschriebene Zeilen“, nicht als „geänderte Zeilen“. Und geplante Jobs sind standardmäßig aus: Eine Installation muss sie einschalten, sonst läuft nie ein Pull.

## Was die Kopie nicht erbt

- **Die Berechtigungen der Quelle.** Wer eine Zeile im ERP lesen darf, wird nicht mitkopiert: Berechtigungen auf der Kopie beginnen ohne jeden Zugriff, und ein Mitglied liest sie nur über eine Freigabe. Mia las die Kopie über ihr Berechtigungsset und wurde an der Quelltabelle abgewiesen, für die sie keine Freigabe hat: genau die Einrichtung, die Sie anstreben sollten. Eine kopierte Zeile hat keinen Eigentümer; machen Sie die Kopie also für alle Mitglieder lesbar, oder halten Sie sie privat und geben Sie Lesezugriff über eine Freigaberegel.
- **Die Laufhistorie, für Mitglieder.** Mia wurde abgewiesen, als sie sie las: Wie jede Tabelle braucht sie eine Freigabe.
- **Löschungen.** Eine in der Quelle gelöschte Zeile bleibt auf 18.5.0 in der Kopie (der Job-Leitfaden: „Die Lösch-Schlüssel ändern noch nichts“; das habe ich nicht ausgeführt). Solche Zeilen zu markieren ist in Entwicklung, siehe unten.
- **Eine Organisation, in einer Installation mit mehreren Organisationen.** Die Plattform rät nicht. Im isolierten Mehr-Organisationen-Modus verweigerte dieselbe App den Start, bis die Quelle ihren Organisationsbereich angab, und plante den Pull dann nicht ein, bis der Job seine Organisation nannte: ein Job pro Organisation.
- **Eine Pipeline.** Die Kopie ist eine Quelltabelle, ein Mapping, ein Ziel. Das Entwurfsdokument: „ObjectStack baut keine Pipelines oder Transformationen. Verknüpfen, Bereinigen und Aggregieren über Quellen hinweg ist Sache des Data Warehouse oder des ETL-Anbieters; ObjectStack synchronisiert das Ergebnis herein.“ Sie brauchen eine bereinigte, verknüpfte Sicht? Bauen Sie sie im Data Warehouse und ziehen Sie das Ergebnis herein.

- In der Quelle gelöschte Zeilen: Der Entwurf markiert sie als gelöscht und entfernt sie nie.
- Eine Herkunftsangabe an jeder Zeile: woher sie kam und welcher Lauf sie schrieb.
- Ein Sync-Assistent in Studio, mit der Laufhistorie auf dem Bildschirm.
- Data Warehouses (Snowflake, BigQuery) als Quellen, über zusätzlich installierte Connectoren.
- Der Sync-Leitfaden und die Agent-Skills.

## So prüfen Sie es, wenn ein Agent es schreibt

Die Synchronisation eines Agenten besteht aus fünf Deklarationen, plus einer Aktion und einem Flow, wenn Rückschreiben dazugehört. Prüfen Sie vier Dinge:

1. **Die Kopie ist als synced markiert** (`managedBy: 'synced'` am Ziel). Ohne das weist der Build die Synchronisation ab; wenn der Build durchläuft, ist es also da.
2. **Wer die Kopie lesen darf**: ihr Freigabemodell und ihre Berechtigungssets, die ohne jeden Zugriff beginnen.
3. **Die Spalte „zuletzt geändert“ der Quelle und ihr Schlüssel.** Eine solche Spalte, die nicht bei jedem Schreibvorgang geändert wird, verliert Änderungen still, und der Schlüssel muss eindeutig und nie leer sein. Der Pull kann beides nicht prüfen; die Quelle muss es garantieren.
4. **Die Rückschreib-Aktion und ihr Flow**, falls vorhanden: der einzige Weg zurück zur Quelle. Prüfen Sie sie wie jeden ausgehenden Aufruf: was sie sendet, an wen, und wer sie ausführen darf.

Vergleichen Sie dann die gelesenen Zeilen im ersten Laufprotokoll mit der Zeilenzahl der Quelle.

## Richten Sie Ihren Agenten darauf aus

Geben Sie Ihrem Coding-Agenten den Job-Leitfaden (`objectstack.ai/docs/automation/jobs`, „Pulling a mapping“) und die Mapping-Referenz, und geben Sie ihm die Regel in einer Zeile: in ein `managedBy: 'synced'`-Objekt kopieren, über ein `mapping` mit einer `datasourceSource` und einen `job`, dessen `pull` es nennt; die Kopie nie schreiben; die Quelle über eine deklarierte Aktion ändern. Der [Leitfaden zum Konfigurieren eines Coding-Agenten für ObjectStack](/en/blog/how-to-point-your-agent-at-objectstack/) behandelt die Regeldatei und den MCP-Endpunkt, die diese Regel transportieren. Das Mapping nutzt dieselben `fieldMapping` und `upsertKey`, mit denen Sie [eine Tabelle aus einem Altsystem importieren](/de/blog/how-to-import-a-spreadsheet-from-an-old-system/) würden: Ein Pull ist dieser Import, von einem Job gegen eine Live-Quelle ausgeführt, und die Kopie ist ein weiteres Objekt in der [Ontologie](/de/glossary/ontology/). Der Sync-Kernel ist Open Source unter Apache-2.0, wie die Föderation.

## Der Beweis

Alles hier lief auf `@objectstack/cli` 18.5.0, der Version, die `npm view @objectstack/cli dist-tags` am 2026-11-16 als `latest` meldete, in einem frischen `npm create objectstack@latest`-Gerüst.

### Die fünf Deklarationen

Das „alte ERP“ ist eine SQLite-Datei, die der App nicht gehört, mit einer Tabelle, `PARTS`, die sechs Teile und eine Spalte `UPDATED_AT` enthält.

```ts
// 1. The ERP's database: external, so no DDL ever runs there.
export const Erp = defineDatasource({
  name: 'erp', driver: 'sqlite', schemaMode: 'external',
  config: { filename: './legacy/erp.db' },
  external: { allowWrites: false, validation: { onMismatch: 'fail', checkOnBoot: true } },
});

// 2. The PARTS table, federated. PART_NO is mapped onto `id`: that is the source key.
export const ErpPart = ObjectSchema.create({
  name: 'syncdemo_erp_part', datasource: 'erp', sharingModel: 'private',
  external: {
    remoteName: 'PARTS',
    columnMap: { PART_NO: 'id', DESCRIPTION: 'description', UNIT_PRICE: 'unit_price', UPDATED_AT: 'updated_at' },
  },
  fields: {
    description: Field.text({ label: 'Description' }),
    unit_price: Field.number({ label: 'Unit price', scale: 2 }),
    updated_at: Field.datetime({ label: 'Updated at (ERP)' }),
  },
});

// 3. The local copy: an ordinary object that only the pull writes.
export const Part = ObjectSchema.create({
  name: 'syncdemo_part', managedBy: 'synced', sharingModel: 'public_read',
  fields: {
    part_no: Field.text({ label: 'Part no', required: true }),
    description: Field.text({ label: 'Description' }),
    unit_price: Field.number({ label: 'Unit price', scale: 2 }),
    source_updated_at: Field.datetime({ label: 'Updated at (ERP)' }),
  },
});

// 4. The sync, defined on its target: where rows come from, how they map, how one matches.
export const ErpPartsPull = defineMapping({
  name: 'erp_parts_pull', targetObject: 'syncdemo_part',
  mode: 'upsert', upsertKey: ['part_no'],
  fieldMapping: [
    { source: 'id', target: 'part_no' },
    { source: 'description', target: 'description' },
    { source: 'unit_price', target: 'unit_price' },
    { source: 'updated_at', target: 'source_updated_at' },
  ],
  datasourceSource: { object: 'syncdemo_erp_part', watermark: { field: 'updated_at', start: '2026-01-01' } },
});

// 5. When. No code: `pull` names the mapping.
export const ErpPartsPullJob = defineJob({
  name: 'erp_parts_pull_job',
  schedule: { type: 'interval', intervalMs: 30000 },
  pull: { mapping: 'erp_parts_pull' },
});
```

Der `job` führt das Mapping nach Zeitplan aus und schreibt über den Import-Runner als System. Der Spec-Changelog listet, was `managedBy: 'synced'` einschaltet: „Der Schreibschutz der Engine weist den generischen Schreibzugriff eines Mitglieds ab (403), der `apiMethods`-Abgleich entfernt jede Schreibmethode, die `/me/permissions`-Klammer meldet die geschlossene Zeile“.

### Die Abweisung beim Build

`objectstack validate` ließ es durch. Mit entferntem `managedBy: 'synced'` am Ziel endete derselbe Befehl mit Exit-Code 1:

```text
✗ Mapping 'erp_parts_pull' pulls rows into object 'syncdemo_part' through its datasourceSource,
  but that object is not managedBy: 'synced' (it is unset). A pulled copy is read-only to members,
  so a member's edit is never kept or lost silently by the next pull; declare managedBy: 'synced'
  on the target object (ADR-0153 D4).
```

Der Changelog listet die weiteren Abweisungen, die beim Build und noch einmal vor dem ersten Lesen laufen: Ein Mapping mit Quelle muss `mode: 'upsert'` mit einem `upsertKey` sein, die Quelle muss ein föderiertes Objekt sein, dessen `columnMap` eine Spalte auf `id` abbildet (`source_key_missing`), das Watermark muss ein `datetime`-, `date`- oder Ganzzahlfeld sein, und ein `fieldMapping`-Eintrag muss es unverändert ins Ziel kopieren (`watermark_field_unmapped`).

### Der Lauf

Die Jobs eines Pakets werden nur dort eingeplant, wo die Variable `OS_AUTOMATION_SCHEDULED_WORK_ENABLED` auf `true` steht, ein Schalter, der laut Job-Leitfaden „**in jeder Mandanten-Ausprägung und jedem Kernel standardmäßig aus**“ ist. Ich startete `objectstack dev --fresh` mit eingeschaltetem Schalter und legte ein Mitglied (Mia) an, mit einem Berechtigungsset, das Lesen und absichtlich auch Bearbeiten auf `syncdemo_part` gewährt. Der erste Tick lief um 02:31:21; Mias Auflistung von `syncdemo_part` antwortete `200` mit 6 Zeilen.

**Das Laufprotokoll.** Jeder Pull hinterlässt eine `sys_sync_run`-Zeile in der Organisation des Jobs. Die erste, gekürzt auf die Felder, die zählen:

```json
{ "mapping": "erp_parts_pull", "mapping_package": "com.example.syncdemo",
  "target_object": "syncdemo_part", "source_kind": "datasource", "source": "syncdemo_erp_part",
  "datasource": "erp", "read_path": "builtin", "trigger": "schedule", "status": "completed",
  "read_count": 6, "created_count": 6, "updated_count": 0, "refused_count": 0,
  "watermark_field": "updated_at",
  "watermark_from": "2026-01-01T00:00:00.000Z",
  "watermark_committed": "2026-11-09T16:05:00.000Z",
  "holds_position": true, "job_run_id": "run_0b31fc19-…", "failure_reason": null }
```

`watermark_committed` ist der neueste `UPDATED_AT`, den der Lauf geschrieben hat, und `holds_position: true` markiert diese Zeile als die, an der der nächste Lauf beginnt. Die Verbindung zum Job-Journal ist `job_run_id`, die `sys_job_run`-Zeile des auslösenden Ticks. Der Service-Changelog legt die Aufbewahrung fest: Die Zeilen sind „Telemetrie, 30 Tage aufbewahrt, das Fenster des Job-Journals, außer der einen Zeile pro Mapping (Paket und Name) und Organisation, die die Leseposition hält“.

**Die abgewiesene Änderung.** Mia hat `allowEdit: true` auf dem Objekt. Ihr `PATCH` des Preises von P-2001:

```json
HTTP 403
{ "error": "[Security] Access denied: 'syncdemo_part' is synced (managedBy:'synced', ADR-0153) — direct update via the data API is disabled. Its rows are copied from their source by a pull, which would keep or overwrite the change; change the source through a declared action instead, and the next pull brings it home.",
  "code": "PERMISSION_DENIED", "object": "syncdemo_part" }
```

Der `PATCH` des Admins bekam denselben Body. Mias `POST` und `DELETE` antworteten `403` mit „direct insert“ und „direct delete“ im selben Satz. Zu sagen, was stattdessen zu tun ist, ist genau das, was Sie wollen, wenn ein Agent den Aufruf macht.

**Der inkrementelle Lauf, 3 von 7.** Ich änderte das ERP direkt, wie seine eigenen Benutzer es täten: den Preis von P-1003 von 0.05 auf 0.06 und ein neues Teil, P-3002, beide mit Zeitstempel `2026-11-16T02:31:22.383Z`. Der nächste Tick, um 02:31:51:

```json
{ "read_count": 3, "created_count": 1, "updated_count": 2,
  "watermark_from": "2026-11-09T16:05:00.000Z",
  "watermark_committed": "2026-11-16T02:31:22.383Z", "status": "completed" }
```

Drei Zeilen gelesen von den sieben, die das ERP da hatte: P-1003, P-3002 und P-3001, das die Position teilt, die der letzte Lauf festgeschrieben hat. Der Job-Leitfaden beschreibt dieses erneute Lesen: Ein Lauf „liest nur seither geschriebene Zeilen plus jene, die diese letzte Position teilen, die der Upsert harmlos erneut schreibt“.

**Rückschreiben.** Die Aktion ist eine `type: 'flow'`-Aktion auf `syncdemo_part`. Ihr Flow hat einen arbeitenden Knoten, eine `connector_action`, die einen `rest`-Connector aufruft, der auf die eigene HTTP-API des ERP zeigt (hier ein 20-zeiliger Stellvertreter, der `PARTS` aktualisiert und `UPDATED_AT` setzt):

```ts
{ id: 'patch_erp', type: 'connector_action',
  connectorConfig: {
    connectorId: 'erp_api', actionId: 'request',
    input: {
      method: 'PATCH',
      path: { dialect: 'cel', source: "'/parts/' + record.part_no" },
      body: { dialect: 'cel', source: '{ "unit_price": new_price }' },
    },
  },
}
```

Mia rief sie über REST auf, denselben Einstiegspunkt, den die Schaltfläche auf der Datensatzseite nutzt („die Console-Schaltfläche und der API-Aufruf durchlaufen dieselbe Prüfung und denselben Handler“):

```bash
curl -s -b mia.cookies -X POST http://localhost:49921/api/v1/actions/syncdemo_part/syncdemo_send_price \
  -H 'content-type: application/json' \
  -d '{"recordId":"6b7fe890-…","params":{"new_price":4.1}}'
```

```text
HTTP 200  { "success": true, "data": { "success": true, "flowLabel": "Send price to ERP", … } }
ERP API:  2026-11-16T02:31:52.833Z PATCH /parts/P-2001 {"unit_price":4.1} -> changes=1
```

Unmittelbar danach gelesen, zeigte die Kopie noch `"unit_price": 3.8`, weil das Rückschreiben das ERP geändert hat und sonst nichts. Dreißig Sekunden später, um 02:32:21, las der nächste Lauf 3 Zeilen (P-1003 und P-3002 an der geteilten Position, dazu P-2001), aktualisierte 3, schrieb `2026-11-16T02:31:52.833Z` fest, und P-2001 zeigte `"unit_price": 4.1, "source_updated_at": "2026-11-16T02:31:52.833Z"`. Hätte das ERP den Wert abgelehnt oder gerundet, würde die Kopie das zeigen (aus der Schleife gefolgert; hier nicht getestet).

### Die Grenzen, gemessen

- **Berechtigungen.** Dieselbe Sitzung, in der Mia die Kopie las, bekam `403` auf dem föderierten Quellobjekt `syncdemo_erp_part`, für das sie keine Freigabe hat. Die kopierten Zeilen tragen kein `owner_id`, daher lautet der Lint-Rat des Spec-Changelogs für ein synced-Objekt „`sharingModel: 'public_read'` … oder `'private'` mit einer Freigaberegel, die Lesen gewährt“.
- **Laufhistorie.** `sys_sync_run` ist für die Daten-API offen, aber Mias Lesezugriff darauf antwortete `403`.
- **Organisationen.** Mit `OS_TENANCY_POSTURE=isolated` gestartet, verweigerte dieselbe App den Start, bis die föderierte Quelle ihren Organisationsbereich angab („Stating nothing: 'syncdemo_erp_part'“). Mit der Quelle als geteilt deklariert, protokollierte der Start auf Stufe `error`: „NOT SCHEDULED — job 'erp_parts_pull_job' declares no `organization`“ (danach hielt er bei einer unabhängigen Einstellung der abgeschotteten Ausprägung an, der Mitgliedschaftsrichtlinie, die eine echte Installation mit mehreren Organisationen ohnehin deklariert). Die Lösung ist `organization` am Job, ein Job pro Organisation. Der Changelog nennt die Abweisungen, mit denen ein Pull selbst in dieser Ausprägung antwortet: `source_organization_scope_unstated` und `job_organization_missing`.

### Was Entwurfsdokument und Leitfäden sagen

Die Abschnitte oben geben diese Quellen sinngemäß wieder; hier sind die Zeilen selbst.

- **Warum kopieren.** „Berichte, Analysen, KI-Fragen und Verknüpfungen über Quellen hinweg stoßen zuerst an diese Grenzen. Werden die Zeilen in ein gewöhnliches Objekt kopiert, entfallen sie: Dann gehören der Plattform die Indizes, die Abfrageoperatoren, die Berechtigungen und die Verfügbarkeit.“
- **Verknüpfungen über Datenbanken.** Der Quellkommentar des Analytics-Compilers in 18.5.0: Ein Dataset mit einem föderierten Objekt „wird über den FK-Expand-Pfad von ObjectQL bedient (zwei Lesezugriffe, im Speicher verknüpft) – der Datenquellen konstruktionsbedingt überschreitet“.
- **Die Zeilenobergrenze (hier nicht ausgeführt).** Der Leitfaden zu virtuellen Objekten in 18.5.0: „Ein Lesezugriff, der mehr Zeilen trifft als die Zeilenobergrenze der Datenquelle, wird mit `422 EXTERNAL_ROW_CAP_EXCEEDED` abgewiesen, statt aus einer Teilmenge beantwortet zu werden. Die Obergrenze gilt nur für Plugin-Treiber, OData eingeschlossen“. „Der Standard ist 1000 Zeilen“, das Plattformmaximum 10,000.
- **Regel 3, Rückschreiben.** ADR-0153 D5: „Eine Änderung an Quelldaten wird in der Quelle vorgenommen, über eine deklarierte Aktion … Das Rückschreiben bearbeitet die lokale Zeile nicht; **der nächste Pull gleicht sie ab**.“
- **Regel 4, eine Richtung.** „Keine bidirektionale Synchronisation, kein Konfliktabgleich, keine Bearbeitungsschicht im Stil von Writeback-Datasets“.
- **Berechtigungen.** „Objektberechtigungen werden lokal von null an konfiguriert … ein Mitglied liest synchronisierte Zeilen nur über eine Freigabe.“
- **Watermark und Schlüssel.** Zu `watermark.field`: „Jeder Schreibvorgang an der Quelle setzt das Watermark der Zeile auf einen Wert, der mindestens so hoch ist wie jeder Wert, den die Quelle bereits enthält“. Zur auf `id` abgebildeten Spalte: eindeutig und nie NULL, „eine Anforderung an die Quelle … die der Pull nicht prüfen kann“.
- **Löschungen.** Der Job-Leitfaden von 18.5.0: „Die Lösch-Schlüssel ändern noch nichts, und `os validate` sagt das.“
- **Lizenz.** ADR-0153 D9: Der Sync-Kernel „wird in diesem Repository unter Apache-2.0 ausgeliefert, wie die Föderation“.
