**답:** 데이터베이스를 복사하지도, 다시 만들지도 마십시오. 플랫폼이 읽기만 하고 절대 바꾸지 않는 원본으로 연결하고, 각 테이블에 업무 이름을 붙이고, 누가 무엇을 볼 수 있는지 정하십시오. 그러면 사람, 보고서, AI 에이전트가 하나의 통제된 입구로 실시간 데이터를 읽고, 각 사람의 권한이 모든 답에 적용됩니다. 에이전트가 받는 답도 마찬가지입니다. 대가는 모든 읽기가 원본 데이터베이스에서 실행된다는 점입니다. 아무것도 복사하지 않으므로 오래된 데이터도 생기지 않습니다. 기존 시스템에서 바꾼 값이 다음 읽기에 바로 보였습니다. 두 곳에서 쓰기를 켜기 전까지는 아무것도 되돌려 쓰지 않습니다.

*ObjectStack 18.5.0(현재 릴리스)에서, 고객 5명과 주문 2,400건을 가진 모의 주문 시스템을 대상으로 실측했습니다. 모든 기록은 마지막 절 '증거'에 있습니다.*

저는 이것을 **리드스루 온톨로지**라고 부르겠습니다. 내 소유가 아닌 테이블 위에 업무 이름, 관계, 권한, AI 도구를 얹고, 모든 읽기를 그 테이블의 실제 주인인 시스템으로 넘기는 방식입니다. 숫자 하나로 말하면, 주문 2,400건을 모두 제공하는 동안 ObjectStack 자체 데이터베이스가 가진 주문은 **0건**이었습니다.

## 운영 중인 데이터베이스를 쓸 수 있게 만드는 세 가지 길

"데이터를 AI에 쓸 수 있게 만들라"는 요청을 받는 회사 대부분은 이미 데이터를 갖고 있습니다. 다른 시스템이 쓰는 데이터베이스 안에 말입니다. 그 위에 통제된 업무 계층을 올리는 정직한 방법은 세 가지이고, 각각 치르는 비용이 다릅니다.

| | 다시 만들기 | 복사하기 | 통과해서 읽기 |
|:--|:--|:--|:--|
| 움직이는 것 | 데이터와 시스템 | 데이터(일정에 따라) | 없음 |
| 신선도 | 새 시스템이 기준 | 마지막 동기화 시점 | 읽는 순간의 원본 |
| 스키마 소유자 | 당신 | 당신(복사본에 대해) | 원본 시스템 |
| 첫날 비용 | 마이그레이션 프로젝트 | 만들고 지켜봐야 하는 파이프라인 | 연결 파일 하나와 테이블마다 파일 하나 |
| 원본을 넘나드는 조인 | 가능 | 가능(복사하는 주된 이유) | 두 번 읽어 메모리에서 결합 |
| 원본의 부하 | 전환 후 없음 | 한 번에 동기화 하나 | 읽을 때마다 |

복사를 택할 이유는 진짜입니다. 복사본은 인덱스를 걸 수 있고, 무엇과도 조인할 수 있고, 검색할 수 있으며, 원본이 느리거나 멈춰도 보고서를 낼 수 있습니다. 운영 중인 주문 시스템에 대시보드 쿼리를 올리지도 않습니다. 그게 필요하다면 복사하십시오. 통과해서 읽을 이유는 더 좁지만, 맞는 자리에서는 더 강합니다. 연결한 날부터 업무 계층이 최신 상태입니다. 뒤처질 복사본이 없기 때문입니다.

![테스트 구성. 멤버, 그 멤버로 로그인한 AI 에이전트, 관리자가 ObjectStack 계층을 호출합니다. 이 계층은 두 테이블의 업무 이름, 신용 한도와 주문을 숨기는 열람 역할, 꺼진 쓰기 스위치를 갖고 있습니다. 모든 읽기는 주문 시스템 자체 데이터베이스(고객 5명, 주문 2,400건)에서 실시간으로 실행됩니다. 멤버에게는 신용 한도가 없는 고객 두 명이 보이고, 에이전트에게는 주문이 보이지 않으며, 모든 쓰기는 거부되고, ObjectStack 자체 데이터베이스에는 고객이나 주문 행이 하나도 없습니다.](./read-through-en.svg)

## 무엇을 연결했고, 무엇이 돌아왔나

원본은 기존 주문 시스템을 흉내 내는 짧은 Python 스크립트가 쓴 SQLite 파일입니다. 고객 테이블과 주문 테이블이 있고, 열 이름은 오래된 시스템에 흔한 알아보기 힘든 약어입니다. 일은 짧은 파일 세 개가 했습니다. **데이터 소스**는 데이터베이스가 어디에 있고 플랫폼이 거기서 무엇을 해도 되는지 선언합니다. 이 데이터 소스는 스키마가 원본의 것이므로 ObjectStack이 절대 바꾸지 않으며, 쓰기는 꺼져 있다고 말합니다.

```ts
export const Erp = defineDatasource({
  name: 'erp',
  label: 'Order system (SQLite)',
  driver: 'sqlite',
  schemaMode: 'external',            // ObjectStack never runs DDL here
  config: { filename: '/…/legacy/erp.db' },   // absolute path, trimmed
  external: {
    allowWrites: false,
    validation: { onMismatch: 'fail', checkOnBoot: true },
  },
});
```

**객체**는 테이블마다 하나씩 있으며, 사람과 보고서와 에이전트가 이름으로 찾는 업무 레코드입니다. 각 객체는 옛 열을 알기 쉬운 이름에 대응시킵니다. 예를 들어 `cust_no`는 `id`가 됩니다. 플랫폼은 원본의 테이블을 나열하고 이 객체들의 초안을 대신 만들어 줄 수 있습니다. **권한 세트**는 사람에게 부여하는, 이름이 붙은 권한 묶음입니다. 이 권한 세트는 열람자에게 고객은 보여 주지만 신용 한도는 보여 주지 않고, 주문에 대해서는 아무것도 허용하지 않습니다.

그런 다음, 승인하기 전에 당신이 물을 질문을 실행 중인 앱에 던졌습니다. 관리자로, Mia라는 멤버로, 그리고 **MCP**를 통해 Mia로 로그인한 AI 에이전트로 말입니다. MCP는 AI 에이전트가 애플리케이션의 도구를 호출할 때 쓰는 개방형 프로토콜입니다.

| 한 일 | 시스템의 답 | 당신에게 주는 의미 |
|:--|:--|:--|
| 주문 시스템에서 직접 신용 한도를 바꾸고 ObjectStack을 통해 읽었다 | 바로 다음 읽기에서 180,000이 아닌 95,000. 동기화는 한 번도 돌지 않았고, ObjectStack 자체 데이터베이스의 테이블 85개 중 고객이나 주문 테이블은 없었다 | 읽는 것은 원본이지, 오래될 수 있는 복사본이 아니다 |
| 대기 중인 주문을 고객과 함께 요청했다 | 주문 480건. 원본에서 걸러졌고, 각각 다른 테이블의 고객이 붙어 있었다 | 내 소유가 아닌 테이블에서도 필터와 관계가 동작한다 |
| 주문 날짜를 날짜 타입으로 선언했다(원본은 텍스트로 저장) | 앱이 시작을 거부하고 그 열을 지목했다 | 이 계층은 자신에게 맞추려고 스키마를 바꾸지 않는다 |
| 관리자로 생성, 수정, 삭제했다 | 모두 거부되었고 두 쓰기 스위치가 지목되었다. 원본은 여전히 고객 5명, 주문 2,400건 | 두 스위치를 열기 전에는 누구도 원본에 쓸 수 없다 |
| 열람용 권한 세트를 부여하기 전과 후에 Mia로 읽었다 | 전: 두 테이블 모두 거부. 후: EU 고객 두 명, 신용 한도 없음. 주문은 계속 거부 | 부여 전까지 닫혀 있다. 플랫폼이 만들지 않은 데이터베이스에서도 열 숨김이 동작한다 |
| Mia가 신용 한도로 필터링하고, 이어서 정렬했다 | 둘 다 거부. 답이 값을 노출하기 때문 | 숨겨진 수치로 필터링하거나 정렬하면 거부되므로, 그런 식으로는 추측할 수 없다 |
| Mia로 로그인한 에이전트가 객체를 나열하고, 고객을 읽고, 51행을 요청하고, 쓰기를 시도했다 | 고객과 동료 디렉터리, 주문은 없음. NA 고객 두 명, 신용 한도 없음. 50행 초과 요청 거부. 쓰기 거부 | 에이전트가 얻는 것은 Mia의 뷰를 넘지 않으며, 호출당 최대 50행, 읽기 전용이다 |
| **데이터셋**(이름이 붙은 보고서 수치 묶음)에 고객 지역별 매출을 요청했다 | APAC 6,127,544.10, EU 11,995,588.50, NA 12,470,792.17. 주문 시스템 자체 쿼리와 소수점 둘째 자리까지 정확히 일치 | 보고서가 두 테이블을 넘나들며 동작한다(한계 1 참고) |

원본 데이터베이스는 Mia가 누구인지 모릅니다. 권한은 읽을 때마다 이 계층이 집행하고, 에이전트는 데이터베이스와 직접 대화하지 않습니다.

## 리드스루 계층이 멈추는 곳

아래는 제가 실측한 경계와, 제가 실행하지 않은 드라이버에 대해 문서가 밝혀 둔 두 가지입니다. 쓰기 스위치는 한 번도 켜지 않았으므로, 둘 다 열었을 때 쓰기가 어떻게 되는지는 여기서 측정하지 않았습니다.

**1. 두 데이터베이스를 조인하는 단일 쿼리는 없습니다.** 매출 보고서는 SQLite에 보낸 하나의 조인이 아니었습니다. 페더레이션 객체, 즉 외부 테이블에 연결된 객체에 대해 분석 컴파일러 자체 주석은 데이터셋이 "the ObjectQL FK-expand path (two reads, joined in memory)"(ObjectQL 외래 키 확장 경로: 두 번 읽고 메모리에서 결합)로 처리된다고 말합니다. ObjectStack 자체 데이터베이스와 주문 시스템 사이에서도 마찬가지입니다. 고객을 가리키는 조회 필드가 있는 네이티브 방문 객체는 고객을 펼치고 그 지역으로 필터링할 수 있었지만, 모두 별개의 읽기였습니다. 없는 것은 두 데이터베이스에 걸친 하나의 문장입니다. 런타임의 설계 기록(ADR)은 이를 비목표로 적어 두었습니다. "cross-datasource JOINs in one query (federated objects are queried per-datasource)"(한 쿼리 안의 데이터 소스 간 JOIN. 페더레이션 객체는 데이터 소스별로 조회한다).

**2. 대량 읽기 상한은 추가 커넥터에 있고, 내장 SQL 데이터베이스에는 없습니다.** 내장 SQLite 드라이버에는 상한이 없습니다. 주문 5,000건을 요청하자 2,400건이 모두 돌아왔고, 이 데이터 소스에 상한을 두면 아무 효과가 없다는 이유로 검증 단계에서 거부됩니다. 추가 커넥터(ObjectStack의 용어로는 플러그인 드라이버)는 따로 설치하는 것이며 OData도 여기에 속합니다. 그 위에서는 가이드가 상한을 정합니다. "A read that matches more rows than the datasource's row cap is refused with `422 EXTERNAL_ROW_CAP_EXCEEDED` rather than answered from a partial set"(데이터 소스의 행 상한보다 많은 행에 일치하는 읽기는 일부만으로 답하지 않고 거부된다), "The default is 1000 rows"(기본값은 1000행), 최대 10,000. 여기서는 실행하지 않았습니다.

**3. '부모가 보이면 보인다'는 SQL에서는 동작하고, 추가 커넥터에서는 거부됩니다.** 부모가 통제하는 공유란, 주문이 그 고객을 볼 수 있는 사람에게 보인다는 뜻입니다. 추가 커넥터에서는 이런 읽기가 거부된다고 가이드는 말합니다('증거'에 원문 인용). SQL에서는 반대 결과를 측정했습니다. Mia는 고객을 통해 주문을 읽을 수 있었고, 고객이 그녀에게 보이지 않게 되자 주문도 함께 사라졌습니다(다음 항목).

**4. 소유자 기준 공유에는 소유자 열이 필요합니다.** 고객을 비공개(초안으로 만든 객체의 기본값)로 두고 테이블에 소유자 열이 없으면, Mia는 아무것도 읽지 못했습니다. 고객도, 그 주문도 보이지 않았고, 관리자는 여전히 5명과 2,400건을 모두 읽었습니다. 가이드는 이렇게 경고합니다. "only an `owner_id` declared in `fields`, or named by an `external.columnMap` entry, counts as one. Without it a member reads no row."(`fields`에 선언되었거나 `external.columnMap` 항목이 지목한 `owner_id`만 소유자로 인정된다. 그것이 없으면 멤버는 한 행도 읽지 못한다.) 원본의 소유자 열을 대응시키거나, 위에서처럼 테이블을 열람 가능하게 연 뒤 권한 세트로 좁히십시오.

**5. 성능은 원본의 성능입니다.** 모든 읽기는 그 순간의 주문 시스템에서 실행됩니다. 목록 페이지는 행과 총수를 읽고, 누군가 열어 둔 대시보드는 운영 데이터베이스에 대한 쿼리입니다. 이 계층은 원본에 없는 인덱스를 추가하지 않습니다. 원본이 부하를 감당하지 못한다면, 이미 운영 중인 복제본으로 데이터 소스를 돌리거나 데이터를 복사하십시오.

## 복사가 더 나은 도구일 때

ObjectStack의 가상 객체 가이드는 규칙을 한 문장으로 밝힙니다. "Make the object virtual when a copy would be **wrong**, and real when a copy is merely **convenient**"(복사가 틀린 경우에는 객체를 가상으로, 복사가 그저 편한 경우에는 실제 객체로). 원격이 요청 시점에 답을 계산할 때, 데이터를 원본 밖에 저장해서는 안 될 때(데이터 상주, 라이선스, 감사), 또는 어떤 동기화보다 빨리 바뀔 때 복사는 틀립니다. 느리게 바뀌는 참조 데이터나 여러 원본을 조인하는 보고서에서는 복사가 편할 뿐입니다. 앞의 경우는 통과해서 읽고, 뒤의 경우는 복사하십시오. 이미 꺼진 시스템에는 내보낸 파일만 남습니다. 그 파일을 옛 코드 없이 들여오는 방법이 [가져오기 매핑과 그 시험 실행](/ko/blog/how-to-import-a-spreadsheet-from-an-old-system/)입니다.

복사해 들여오는 것이 다른 길이고, 그 핵심은 18.5.0에 들어 있습니다. 예약된 작업이 페더레이션 객체를 동기화된 복사본으로 옮기며, 멤버는 그것을 읽을 수 있지만 쓸 수는 없습니다. 이 글을 위해 측정하지는 않았습니다. ADR-0153의 지침은 "Reports, analysis, AI question answering, joins across sources; a slow or fragile legacy system"(보고서, 분석, AI 질의응답, 원본 간 조인. 느리거나 취약한 레거시 시스템)을 복사해 들여오기를 가리키는 sync-in에, "Live data, one table at a time; the legacy system must not be touched; data that must not land"(실시간 데이터, 한 번에 한 테이블. 레거시 시스템을 건드려서는 안 됨. 내려앉아서는 안 되는 데이터)를 이 리드스루 연결을 가리키는 페더레이션에 배정합니다. [Connect existing systems](/en/connect-existing-systems/)는 세 길을 나란히 보여 줍니다. 실시간으로 읽기, 복사해 들여오기, 선언된 액션으로 원본 바꾸기입니다.

## 개발 중: sync-in의 나머지

18.5.0에 아직 없는 것: 원본이 삭제한 행 표시(작업 가이드: "The delete keys change nothing yet", 삭제 키는 아직 아무것도 바꾸지 않는다), 커넥터 원본의 페이지 처리(키는 선언할 수 있지만 "nothing reads it yet", 아직 아무것도 읽지 않는다), 그리고 sync-in 가이드와 스킬. 이 절의 내용은 아무것도 측정하지 않았습니다.

## diff에서 읽을 곳

에이전트가 연결을 작성했다면, 각 결정은 diff의 한 줄입니다.

| diff의 줄 | 그 줄이 정하는 것 |
|:--|:--|
| `schemaMode: 'external'` | ObjectStack은 원본을 절대 바꾸지 않는다. 어긋나면 시작에 실패한다 |
| `allowWrites` / `writable` | 둘 다 `true`여야 쓰기가 원본에 닿는다 |
| `columnMap` | 원본의 열이 어떤 업무 이름으로 나타나는가 |
| `sharingModel` | `private`에는 대응된 소유자 열이 필요하다. 없으면 멤버는 아무것도 읽지 못한다 |
| 권한 세트의 `fields` | 멤버가 절대 보지 못하고 필터에도 쓸 수 없는 원본 열 |
| `rowCap` | 플러그인 드라이버 전용. 내장 SQL 드라이버에서는 거부된다 |

페더레이션 덕분에 [온톨로지](/ko/glossary/ontology/)는 내가 만들지 않은 데이터베이스에도 이름을 붙일 수 있고, [권한 모델](/en/glossary/permission-model/)은 사람이든 에이전트든 모든 읽는 이에게 적용됩니다.

## 에이전트에게 맡기기

코딩 에이전트에게 건넬 것은 이 글이 아니라 규칙입니다. `external` 데이터 소스 하나, `remoteName`과 `columnMap`을 가진 테이블별 객체, 명시적으로 적은 `sharingModel`, 꺼 둔 두 쓰기 스위치, 그리고 대상별 권한 세트. [코딩 에이전트 설정 방법](/en/blog/how-to-point-your-agent-at-objectstack/)은 규칙 파일, 실행 중인 앱이 노출하는 MCP 엔드포인트, 사양을 다룹니다. 에이전트가 읽어야 할 참고 자료는 [외부 데이터 소스 가이드](https://objectstack.ai/docs/data-modeling/external-datasources)입니다.

## 증거

아래는 모두 `npm create objectstack@latest`로 만든 프로젝트를 18.5.0의 `objectstack dev`로 실행한 실제 출력이며, 표시한 곳만 줄였습니다. `$B`는 개발 서버 주소이고, `sql.py`는 파일에 문장 하나를 실행하는 세 줄짜리 Python 도우미입니다. 그 머신에 `sqlite3` 명령이 없었기 때문입니다.

### 원본과 방언

고객 5명과 주문 2,400건, 스키마는 다음과 같습니다.

```sql
CREATE TABLE customers (
  cust_no      TEXT PRIMARY KEY,
  cust_name    TEXT NOT NULL,
  cust_region  TEXT,
  credit_limit REAL
);
CREATE TABLE orders (
  order_no   TEXT PRIMARY KEY,
  cust_no    TEXT NOT NULL REFERENCES customers(cust_no),
  amount     REAL,
  status     TEXT,
  placed_on  TEXT
);
```

처음에는 Postgres를 시도했고, 시작 단계에서 분명하게 알려 주었습니다. "The database client package `pg` is not installed, so no connection was attempted. It is an OPTIONAL install of @objectstack/driver-sql … `npm install pg` (pnpm add pg / yarn add pg)"(데이터베이스 클라이언트 패키지 `pg`가 설치되지 않아 연결을 시도하지 않았다. 이것은 @objectstack/driver-sql의 선택적 설치다). 가이드는 Oracle과 SQL Server도 페더레이션 전용 방언으로 문서화하고 있으며("ObjectStack reads an existing Oracle schema live … but it never owns one", ObjectStack은 기존 Oracle 스키마를 실시간으로 읽지만 결코 소유하지 않는다), SAP S/4HANA나 Dynamics 365 같은 OData v4 서비스도 함께 제공되는 드라이버로 다룹니다. 이 세 가지는 여기서 실행하지 않았습니다.

### 연결

`sales` 프로젝트에서는 위의 데이터 소스 옆에서 고객 객체가 `external.columnMap`(원격 열 → 로컬 필드)으로 `cust_no`, `cust_name`, `cust_region`을 `id`, `name`, `region`으로 바꿉니다.

```ts
export const Customer = ObjectSchema.create({
  name: 'sales_customer',
  label: 'Customer',
  sharingModel: 'public_read',
  datasource: 'erp',
  external: {
    remoteName: 'customers',
    columnMap: { cust_no: 'id', cust_name: 'name', cust_region: 'region' },
  },
  fields: {
    name: Field.text({ label: 'Name', searchable: true }),
    region: Field.text({ label: 'Region' }),
    credit_limit: Field.currency({ label: 'Credit limit' }),
  },
});
```

`sales_order`는 `orders` 위에 같은 형태로 만들었고, `cust_no`를 `customer` 조회 필드에 대응시켰습니다. 권한 세트는 다음과 같습니다.

```ts
export const SalesReader = definePermissionSet({
  name: 'sales_reader',
  objects: { sales_customer: { allowRead: true } },
  fields: { 'sales_customer.credit_limit': { readable: false, editable: false } },
});
```

관리용 경로 `GET …/datasources/erp/external/tables`는 `customers`(4열)와 `orders`(5열)를 돌려주었고, `POST …/external/tables/customers/draft`는 그 테이블의 객체 초안을 돌려주었습니다. 초안은 원격 이름을 그대로 필드 이름으로 쓰고 `sharingModel: 'private'`로 시작하므로(한계 4), 저는 `columnMap`으로 이름을 바꾸고 `public_read`를 골랐습니다.

`placed_on`을 `date` 필드로 선언하자 시작에 실패했습니다.

```text
✗ Object 'sales_order' does not match its remote table on datasource 'erp':
✗ type_mismatch: orders.placed_on (expected date, actual text)
```

이것이 설계대로 동작하는 `schemaMode: 'external'`입니다. 가이드의 표현으로는 "A mature external DB — **DDL forbidden**; a schema mismatch **fails** boot."(성숙한 외부 DB: DDL 금지, 스키마 불일치는 시작을 실패시킨다.) 저는 필드를 주문 시스템이 실제로 저장하는 `text`로 바꿨습니다.

### 실시간인가, 복사본인가?

읽고, 주문 시스템에서 바꾸고, 다시 읽습니다.

```bash
curl -s -b admin.cookies "$B/api/v1/data/sales_customer/C-1002"
```

```json
{"object":"sales_customer","id":"C-1002","record":{"credit_limit":180000,"id":"C-1002","name":"Borealis GmbH","region":"EU"}}
```

```bash
python3 sql.py erp.db "UPDATE customers SET credit_limit = 95000 WHERE cust_no = 'C-1002'"
curl -s -b admin.cookies "$B/api/v1/data/sales_customer/C-1002"
```

```json
{"object":"sales_customer","id":"C-1002","record":{"credit_limit":95000,"id":"C-1002","name":"Borealis GmbH","region":"EU"}}
```

동기화는 돌지 않았습니다. 애초에 동기화가 없기 때문입니다. 그 시점에 ObjectStack 자체 데이터베이스에는 테이블이 85개 있었고, 이름을 `customer`나 `order`로 검색해도 아무것도 나오지 않았습니다. 필터는 원본으로 내려가고, 조회 필드는 두 원격 테이블을 넘나들며 펼쳐집니다.


```json

  {"amount":7020.73,"status":"pending","placed_on":"2026-04-04","id":"SO-00003",
```

### 무언가가 쓸 수 있나?

플랫폼 관리자로:

```bash
curl -s -b admin.cookies -X POST "$B/api/v1/data/sales_customer" \
  -H "content-type: application/json" -d '{"id":"C-9999","name":"Test Co","region":"EU"}'
```

```json
HTTP 403
{"error":"Write 'insert' blocked on object 'sales_customer': datasource 'erp' is external (schemaMode=external). Requires datasource.external.allowWrites=true (got false) AND object.external.writable=true (got false).","code":"EXTERNAL_WRITE_FORBIDDEN","object":"sales_customer"}
```

`C-1002`에 대한 `PATCH`와 주문 `SO-00001`의 `DELETE`도 같은 `403`을 돌려주었고, 각각 `update`와 `delete`를 지목했습니다. 주문 시스템은 여전히 고객 5명, 주문 2,400건이었고, 신용 한도도 스스로 정한 값 그대로였습니다. 가이드: "With either gate off, insert/update/delete on the federated object is rejected."(어느 한 게이트라도 닫혀 있으면 페더레이션 객체에 대한 삽입, 수정, 삭제는 거부된다.) 이 메커니즘을 정한 설계 기록(ADR)은 목표로 "Register existing remote tables as ObjectStack objects **without touching the remote schema**"(기존 원격 테이블을 원격 스키마를 건드리지 않고 ObjectStack 객체로 등록한다)와 "Default to read-only; require **two explicit opt-ins** (datasource level + object level) to enable writes."(기본은 읽기 전용. 쓰기를 켜려면 데이터 소스와 객체 두 수준에서 명시적으로 켜야 한다)를 듭니다.

### 멤버에게는 무엇이 보이나?

Mia는 관리자가 `POST /api/v1/auth/admin/create-user`로 만든 멤버입니다. 부여된 권한이 없을 때는 두 객체 모두 `403 PERMISSION_DENIED`를 돌려줍니다. 페더레이션 객체도 다른 객체처럼 기본적으로 거부됩니다. 관리자가 그녀에게 `sales_reader`를 부여한 뒤:

```bash
curl -s -b member.cookies "$B/api/v1/data/sales_customer?region=EU"
```

```json
HTTP 200
{"object":"sales_customer","records":[{"id":"C-1002","name":"Borealis GmbH","region":"EU"},{"id":"C-1004","name":"Delta Freight","region":"EU"}],"total":2,"hasMore":false}
```

`credit_limit`은 없습니다. 주문은 계속 `403`입니다. 간접적으로 물으면:

```bash
curl -s -b member.cookies "$B/api/v1/data/sales_customer?credit_limit=95000"
```

```json
HTTP 403
{"error":"[Security] Access denied: query on 'sales_customer' references field(s) not readable by the caller: credit_limit. Filtering, sorting, grouping, or aggregating by a hidden field would leak its values (filter oracle) — remove these predicates or grant field read access.","code":"PERMISSION_DENIED","object":"sales_customer"}
```

그 필드로 정렬해도 같은 답이었습니다.

### AI 에이전트라면 빠져나갈 수 있나?

모든 ObjectStack 앱은 `/api/v1/mcp`에 있는 MCP 서버입니다. Mia로 로그인한 에이전트의 `list_objects`는 `sys_user`(18.5.0은 에이전트가 사람 필드에 넣을 동료를 찾을 수 있도록 이것을 열어 둡니다)와 `sales_customer`를 돌려주었습니다. 이후 결과를 도구 결과만 남겨 줄이면 다음과 같습니다.

```text
query_records  sales_customer  where {"region":"NA"}  → 2 records: Aurora Labs, Ember Foods (no credit_limit)
query_records  sales_order     limit 1                → {"code":"PERMISSION_DENIED","status":403}
query_records  sales_customer  limit 51               → Too big: expected number to be <=50 at limit
create_record  sales_customer  {"id":"C-9998",…}      → {"code":"EXTERNAL_WRITE_FORBIDDEN","status":403}
```

### 보고서는 테이블을 넘나들며 동작하나?

이 데이터셋은 주문 매출을 다른 테이블의 열로 묶습니다.

```ts
export const OrderRevenue: Dataset = {
  name: 'sales_order_revenue',
  label: 'Order revenue',
  object: 'sales_order',
  include: ['customer'],
  dimensions: [{ name: 'region', label: 'Region', field: 'customer.region', type: 'string' }],
  measures: [
    { name: 'revenue', label: 'Revenue', aggregate: 'sum', field: 'amount' },
    { name: 'orders', label: 'Orders', aggregate: 'count' },
  ],
};
```

MCP `query_dataset` 도구로 조회하고, 주문 시스템 자체에서 실행한 `JOIN`과 대조했습니다.

| 지역 | 매출(데이터셋) | 주문 수 |
|:--|--:|--:|
| APAC | 6,127,544.10 | 480 |
| EU | 11,995,588.50 | 960 |
| NA | 12,470,792.17 | 960 |

```text
('APAC', 6127544.1, 480)
```

### 실측한 한계

데이터 소스를 넘나들 때(한계 1): 네이티브 `sales_visit`은 `sales_customer`를 가리키는 조회 필드를 갖고 있으며, `?expand=customer`와 중첩 필터 `{"customer":{"region":"EU"}}`를 받아들였습니다. `?customer.region=EU` 같은 점 경로 필터와 `customer.region`으로 묶은 `aggregate_records`는 네이티브 `sales_visit`에서도 `sales_order`에서와 똑같이 `400 INVALID_FIELD`를 돌려주었습니다. 따라서 이 두 거부는 페더레이션의 한계가 아닙니다.

행 상한(한계 2): 주문에 대한 `?top=5000`은 2,400행을 모두 돌려주었습니다. SQLite 데이터 소스에 `rowCap`을 두면 검증 단계에서 이렇게 됩니다.

```text
✗ external.rowCap: `external.rowCap` caps the rows the engine reads from a plugin driver, which it holds behind its correctness floor; the 'sqlite' driver is built in, runs the whole query itself and is never capped, so the key would do nothing here. Remove `rowCap`.
```

부모 통제(한계 3): `sales_order`를 `controlled_by_parent`로 두고 `master_detail`로 고객에 연결했습니다. Mia는 주문을 읽었습니다. 플러그인 드라이버에 대한 가이드의 설명: "A read whose scope composes a `ReadableIds` leaf, such as an object `controlled_by_parent`, is refused"(범위에 `ReadableIds` 잎을 포함하는 읽기, 예컨대 `controlled_by_parent` 객체는 거부된다).

소유자 열(한계 4): `sales_customer`를 `private`로 두자, Mia가 받은 답은 고객에 대해서도 부모가 통제하는 주문에 대해서도 `{"records":[],"total":0}`였습니다. 관리자는 여전히 5명과 2,400건을 모두 읽었습니다.

복사해 들여오기, 이름으로(18.5.0에 포함, 여기서는 측정하지 않음): `pull`이 `datasourceSource`를 가진 `mapping`을 가리키는 `job`은 페더레이션 객체를 구간 단위로 읽어 `managedBy: 'synced'`로 선언된 객체에 upsert합니다. 멤버는 그것을 읽을 수 있지만, 쓰기는 엔진이 `403`으로 거부합니다. 실행할 때마다 무엇을 읽었고 어디까지 갔는지를 기록한 `sys_sync_run` 행이 남고, 다음 실행은 거기서부터 이어 읽습니다. 릴리스 노트: "A mapping's `datasourceSource` now does what it declares"(매핑의 `datasourceSource`가 이제 선언한 대로 동작한다). 앱에 선언한 작업은 `OS_AUTOMATION_SCHEDULED_WORK_ENABLED`를 `true`로 설정한 배포에서만 실행되며, 기본값은 꺼짐입니다.
