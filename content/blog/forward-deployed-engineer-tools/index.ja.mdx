**要約：** フォワードデプロイドエンジニア(FDE)はエンタープライズ AI で最も成長している職種です — 報道によれば採用は前年比約 1,000% 増、OpenAI は 2026 年 5 月、専門のデプロイメント会社に 40 億ドルをコミットしました。実際に機能するプレイブックは Palantir のもの、すなわち**オントロジー優先** — AI アプリケーションを出荷する前に顧客のビジネスをモデル化することです。このプレイブックが未解決のまま残しているのは結末です。すべてのエンゲージメントは引き継ぎで終わりますが、今日オントロジーは通常、顧客が永久に借り続けるプラットフォームの中に閉じ込められます。次世代 FDE を定義する問いは、私たちが**オントロジーの引き継ぎ（the ontology handover）**と呼ぶものだと考えます：顧客のオントロジーは、*顧客自身の*リポジトリの型付きオープンファイルとして引き継がれるのか — それとも誰かの更新交渉の切り札になるのか？

## エンタープライズ AI を飲み込んだ職種

今年報じられた数字：FDE の求人は 2025 年 1〜9 月で 800% 以上増加し、2026 年初頭には前年比 1,000% を超えました（[Perspective AI](https://getperspective.ai/blog/2026-fde-hiring-trends-what-1000-job-posts-reveal)、[TechTarget](https://www.techtarget.com/searchenterpriseai/feature/The-rise-of-the-AI-forward-deployed-engineer)）。2026 年 5 月、OpenAI は **40 億ドルのコミット資本**と約 150 名の FDE を擁するデプロイメント会社を発表しました。理由は構造的です：モデルは十分に良くなり、ボトルネックはモデリングからデプロイメントへ移りました — どの企業もデータ、ワークフロー、コンプライアンス制約が固有であり、誰かがその中に入り込んで AI を適合させなければなりません。

## 機能するプレイブックはオントロジー優先

この言葉が流行するずっと前に、Palantir はそれを制度化していました：同社の AI FDE は **LLM ベースのアプリケーションを出荷する前に顧客専用のオントロジーを先行構築し**、週の 30〜40% をディスカバリーに充てます（[Palantir AI FDE ガイド](https://www.palantir.com/docs/foundry/ai-fde/overview)）。この洞察は色あせません：汎用モデルは汎用の答えしか返さない。エンタープライズの価値は顧客自身の名詞と動詞 — オブジェクト、関係、権限、承認経路 — に接地することを要求します。それはエンジニアリングであり、プロンプトではありません。

ここまではもう議論の余地がありません。ほとんど語られないのは、終わりに何が起きるかです。

## 未解決の部分：引き継ぎ

すべてのフォワードデプロイドのエンゲージメントは終わります。FDE は撤収し、彼らが構築したオントロジー — エンゲージメント全体で最も価値ある成果物、このビジネスが実際にどう動くかの符号化された知識 — は二つの場所のどちらかに落ち着きます：

- **ベンダーのプラットフォームの中。** 顧客は使えますが、プラットフォーム経由でのみ、シート課金で、変更はプラットフォーム訓練を受けた専門家頼み。オントロジーは更新交渉の切り札と化しています。
- **顧客のリポジトリの中。** 型付きでバージョン管理されたオープンなファイル。顧客自身のチームと — 顧客自身の AI エージェントが — 誰の許可もなく読み、動かし、変更し続けられます。

今日のデフォルトは前者であり、これこそ企業顧客が「成功したパイロット」を恐れるようになった理由です：オントロジーが良いほどロックインは深い。後者の結末は、定義層そのものがオープンフォーマットである場合にのみ可能です。

## オープンな FDE スタックの姿

これこそ [ObjectStack](https://github.com/objectstack-ai/objectstack)（Apache-2.0）が設計されたワークフローです。ディスカバリーのメモが型付きメタデータになります — コーディングエージェントが書き、検証ゲートが静かに壊れるものを拒否します：

```ts
export const Ticket = ObjectSchema.create({
  name: 'support_ticket',
  label: 'Ticket',
  sharingModel: 'private',        // デフォルトは保守的 — ゲートが要求する
  fields: {
    subject:  Field.text({ label: 'Subject', required: true }),
    status:   Field.select({ label: 'Status', options: [/* 顧客の実際の状態 */] }),
    approver: Field.lookup('sys_user'),
  },
});
```

この定義からランタイムがデータベース、REST API、管理 Console、MCP ツールを導出し、すべての呼び出しに権限と監査を強制します — あなたが去った後も。アプリ全体はレビュー可能なまま：完全な CRM は **1,792 行、約 16k トークン**です — 自分で数えてください：

```bash
find examples/app-crm/src -name '*.ts' -not -name '*.test.ts' | xargs cat | wc -l
```

このサイズこそが引き継ぎを誠実にします。顧客のセキュリティチームはプラットフォームの境界を信頼する代わりに実際の diff を読み、顧客の将来のエージェントはシステム全体をコンテキストに載せ、丸ごとリファクタリングします。

## このスタックが解決しないこと

境界をはっきりさせておきます：**超大規模なデータフェデレーションと分析パイプライン**は Foundry のホームグラウンドであり、オープンなアプリケーション層はそれを置き換えません。**組織のチェンジマネジメント** — 人に実際に使ってもらうこと — は、どんなスタックでも直せない人間の仕事のままです。すでに閉じたプラットフォームに全面標準化した顧客が留まるのも合理的でしょう。主張はより狭いものです：フォワードデプロイド業務のアプリケーション層 — ビジネスをモデル化し、その上で統制されたアプリを出荷すること — においては、オントロジーはもう人質に取られず、引き継げるということです。

## FDE チェックリスト

1. どんな UI の話よりも先に、顧客の名詞と動詞をオブジェクトとフローにモデル化する。
2. 定義全体をコンテキストサイズに保ち、エージェントが丸ごとリファクタリングできるようにする。
3. 権限はデフォルトで保守的に。権限の変更はすべて diff で明示する。
4. 引き継ぐのはリポジトリ、コンパイル済み成果物、レビューチェックリスト — 自社テナントのログインではない。
5. MCP を有効にしたまま渡し、顧客自身の AI がその権限内でアプリを操作できるようにする。

## ループを回してみる

コーディングエージェントをオープンスタックに向けてください — スキャフォールドには `AGENTS.md` とスキルバンドルが同梱されています：

```bash
npm create objectstack@latest client-app && cd client-app
npx os dev --ui   # アプリは動いています — 次のオブジェクトをエージェントとモデル化
```

プラットフォームの運用ごと任せたい顧客には — ブラウザの AI Builder、クラウドまたはセルフマネージド — 同じオープンな定義の上で動く商用ランタイム [ObjectOS](https://www.objectos.ai) があります。
