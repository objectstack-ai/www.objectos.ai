**TL;DR:** Wenn Sie Retool für KI-App-Entwicklung mit Governance bewerten, besteht seine Zugriffsschicht die Prüfung, und Sie sollten nicht so tun, als wäre es anders. Retool hat RBAC über Berechtigungsgruppen, rollenbasierte Kontrolle darüber, wer seinen KI-Builder nutzen darf, Audit-Logs, die jede Query-Ausführung protokollieren, SSO, Self-Hosting und (seit Oktober 2026, als Public Beta für Postgres) Ressourcen-Zugriffsrichtlinien, denen sich keine Query entziehen kann. Seit Juni 2026 wendet es diese Kontrollen auch auf Apps an, die in Lovable, Cursor oder Claude Code gebaut wurden. Was es Ihnen nicht gibt, ist geschäftliche **Autorität** als deklarierter Fakt. „Darf diese Person eine Rückerstattung über 12.000 $ ausstellen?" lebt weiterhin meist in JavaScript, verteilt über Komponenteneigenschaften und Query-Logik, und eine KI schreibt diese Ausdrücke schneller, als irgendein Pull Request sie prüfen kann. Die Lücke ist nicht die grundlegende Sicherheit. Sie besteht darin, dass Autorität *Code* ist und keine Regel, die ein Prüfer an einem Ort lesen kann.

Stellen Sie sich die gewöhnlichste Retool-App der Welt vor: eine Rückerstattungs-Konsole. Ein Entwickler baut sie an einem Nachmittag — eine Tabelle mit Bestellungen, ein „Rückerstattung"-Button, ein paar Queries. Der Support nutzt sie. Sie ist großartig. Das ist Retool in seiner besten Form, und Retool ist darin wirklich das Beste der Kategorie.

Jetzt sind sechs Monate vergangen. Der Entwickler, der sie gebaut hat, ist in ein anderes Team gewechselt. Die Sicherheitsabteilung führt eine Zugriffsprüfung durch und stellt dem neuen Verantwortlichen eine Ein-Satz-Frage: **„Welche Rollen können eine Rückerstattung über 10.000 $ ausstellen, und wo genau wird das durchgesetzt?"**

Beobachten Sie, was der neue Verantwortliche tun muss, um zu antworten. Es gibt keinen einzigen Ort, an dem man nachschauen kann. Er öffnet die App und beginnt, JavaScript zu lesen.

## Der grep-Test

So sieht „wo wird es durchgesetzt" in einer echten Retool-App tatsächlich aus. Die Autorität, eine große Rückerstattung auszustellen, verteilt sich auf mindestens drei unabhängige Ausdrücke, jeder handgeschrieben, jeder von anderer Form:

```js
// 1. refundButton → "Hidden"-Eigenschaft
{{ current_user.groups.map(g => g.name).includes('admin') ||
   (current_user.groups.map(g => g.name).includes('support_lead') && refundAmount.value <= 10000) }}

// 2. refundAmount input → "disabled"-Eigenschaft
{{ !current_user.groups.map(g => g.name).includes('support_lead') }}

// 3. issueRefund query → transformer (das ist der Teil, der tatsächlich schreibt)
if (refundAmount.value > 10000 && !current_user.groups.map(g => g.name).includes('finance')) {
  throw new Error('Refunds over $10k require finance');
}
```

Drei Stellen. Drei sich subtil unterscheidende Bedingungen. Der Button blendet sich für manche Nutzer aus; das Eingabefeld deaktiviert sich für andere; die Query wirft einen Fehler für eine dritte Gruppe. Sie *sollen* sich zu einer kohärenten Regel summieren — „Support-Leads bis 10.000 $, Finance darüber" — aber nichts garantiert, dass sie es tun. Blenden Sie einen Button aus, und die zugrunde liegende Query läuft trotzdem, wenn jemand sie auf andere Weise auslöst. Fügen Sie nächstes Quartal einen zweiten Schreibpfad hinzu und vergessen Sie die `finance`-Prüfung, und Sie haben ein Leck, das kein Screen aufdeckt.

Nennen Sie das **den grep-Test**: Um „wer darf X tun" zu beantworten, lesen Sie *eine deklarierte Regel*, oder müssen Sie die App `grep`en? Wenn es grep ist, wird die App nicht auf der Autoritätsschicht regiert — sie ist lediglich *codiert*, und die Zugriffs-Governance (die Retool perfekt beherrscht) sitzt eine Schicht über dem, was Ihnen tatsächlich schaden kann.

Zum Kontrast hier dieselbe Autorität als deklarierter Fakt — eine Regel, die die Laufzeitumgebung auf *jedem* Pfad durchsetzt, ganz gleich, über welchen Button oder welche Query Sie gekommen sind:

```yaml
action: issue_refund
  who_can_run:
    - role: SupportLead   when: amount <= 10000
    - role: Finance       when: amount  > 10000
  requires_approval:      when: amount > 10000      # ein präventives Gate, kein geworfener Fehler
  audit: always
```

Ein Ort zum Lesen. Ein Ort zum Ändern. Eine Sache, über die ein Prüfer — oder eine KI — nachdenken muss. Der Unterschied zwischen drei handgepflegten Ausdrücken und einer deklarierten Regel ist der ganze Unterschied zwischen „die App ist codiert" und „die Autorität der App wird regiert".

## Retool RBAC und Audit-Logs: Was jede Kontrolle tatsächlich abdeckt

Der grep-Test ist nur fair, wenn die Kontrollen, die Retool *tatsächlich* hat, exakt benannt werden. Hier sind sie, im November 2026 an Retools eigener Dokumentation geprüft:

| Kontrolle | Was sie regelt | Wo sie aufhört |
| --- | --- | --- |
| **Berechtigungsgruppen (RBAC)** | Gruppen „vergeben Rollen und steuern den Zugriff auf Apps, Ressourcen, Workflows und Agents" ([Retool-Leitfäden zu Berechtigungen](https://docs.retool.com/permissions/guides)) | Wer öffnen, bearbeiten oder abfragen darf, nicht, was eine bestimmte Aktion tun darf, sobald jemand drin ist |
| **Assist RBAC** (Feb. 2026, Business und Enterprise) | Pro Rolle: Ask- und Build-Modus, nur Ask-Modus oder kein Zugriff auf den KI-Builder ([Changelog](https://docs.retool.com/changelog/assist-rbac)) | Wer Änderungen *generieren* darf, nicht, was eine generierte Änderung gewährt |
| **Audit-Logs** | Nutzeraktionen „wie Query-Ausführungen und Passwort-Resets", mit exakter Query, Parametern, IP-Adresse und Antwortzeit; ein Jahr Aufbewahrung in der Cloud, CSV-Export in Business und Enterprise, Streaming zu Datadog oder Splunk in Enterprise ([Audit-Logs](https://docs.retool.com/org-users/guides/audit-logs)) | Detektivisch: Sie protokollieren, was lief, nachdem es lief |
| **`current_user`-Zeilenfilter** | Werte, die „serverseitig aus der authentifizierten Sitzung berechnet" und in jede Query eingefügt werden ([Sicherheit auf Zeilenebene](https://docs.retool.com/docs/user-permissions)) | Pro Query, von Hand: „Eine Query, die den Filter weglässt, liefert ungefilterte Daten." |
| **Ressourcen-Zugriffsrichtlinien** | Tabellen-, Spalten- und Zeilenzugriff auf eine Ressource, durchgesetzt bei jeder Query aus Apps, der Query Library, rohem SQL und Agents ([Zugriffsrichtlinien](https://docs.retool.com/data-sources/concepts/access-policies)) | Nur PostgreSQL, [Public Beta seit Oktober 2026](https://community.retool.com/t/new-public-beta-data-access-enforcement-for-postgres-resources/67615); Zeilenfilter „validieren weder die Zeilen, die ein Nutzer anlegt, noch die Werte, die ein Nutzer schreibt" |
| **Governance für KI-codierte Apps** (Juni 2026) | Apps, die in Lovable, Replit, Cursor oder Claude Code gebaut wurden, „erben bestehende Berechtigungen und Audit-Trails"; „Berechtigungen hängen an Datenquellen" ([Retool-Newsroom](https://retool.com/newsroom/retool-extends-enterprise-governance-to-vibe-coded-apps)) | Dieselbe Schicht: Datenquellen-Berechtigungen, keine Geschäftsregeln auf Aktionsebene |

Zwei dieser Zeilen zählen mehr als der Rest, denn in ihnen bewegt sich Retool genau in die Richtung, für die dieser Artikel argumentiert.

**Zugriffsrichtlinien sind eine deklarierte Regel, nicht drei Ausdrücke.** Eine Richtlinie auf der Ressource gilt für jede Query, „sodass sich keine Query entziehen kann" — das Gegenteil des `current_user`-Filters pro Query. Für *Daten*-Autorität — welche Zeilen ein Support-Lead lesen oder löschen darf — erledigt das auf Postgres den Großteil des grep-Tests. Das ehrliche Update gegenüber der Juni-Fassung dieses Beitrags: Retool hat für diese Schicht jetzt eine echte Antwort.

**Was Richtlinien nicht ausdrücken, ist die Rückerstattungsregel.** Die Dokumentation zu Zugriffsrichtlinien beschreibt Lese-, Schreib- und Löschzugriff auf Tabellen, Spalten und Zeilen. Sie beschreibt keine Betragsschwellen, keine Genehmigungs-Gates und keine Bedingungen an den geschriebenen Wert; und Zeilenfilter prüfen ausdrücklich nicht, was ein Nutzer schreibt. „Support-Leads bis 10.000 $, Finance darüber, Genehmigung oberhalb der Grenze" ist eine Regel über eine *Aktion und ihre Argumente*, also lebt sie weiterhin im Button, im Eingabefeld und im Transformer von oben. Richtlinien holen Daten-Autorität an einen Ort. Geschäftliche Autorität bleibt in JavaScript.

Lesen Sie die Tabelle als Scorecard, und Retool besteht jede Frage zur Zugriffs-Governance, die ein Security-Review stellen wird. Die Frage, die es nicht von einem Ort aus beantworten kann, ist die vom Anfang dieses Beitrags: Welche Rollen können eine Rückerstattung über 10.000 $ ausstellen, und wo wird das durchgesetzt?

## Warum Versionskontrolle das nicht schließt

Der Einwand des versierten Retool-Entwicklers ist fair, und Sie müssen ihn präzise beantworten: *„Wir haben Git-gestützte Versionskontrolle, Audit-Logs und RBAC. Änderungen werden in PRs geprüft. Der Zugriff wird regiert. Was fehlt?"*

Drei Dinge, konkret.

Erstens ist ein PR auf einer Retool-App eine Prüfung von **JavaScript und Bindungen, die über Komponenten verstreut sind** — Sie führen ein Code-Review durch, was bedeutet, dass (a) es einen Entwickler erfordert und (b) es keine strukturierte Repräsentation davon gibt, *„diese Änderung hat verändert, wer eine große Rückerstattung ausstellen kann."* Der Prüfer muss *bemerken*, dass eine Anpassung an einem `Hidden`-Ausdruck drei Komponenten weiter eine Autoritätsgrenze verschoben hat. Diffs verstreuter Logik verbergen genau das, was Sie am dringendsten sehen müssen.

Zweitens prüft Versionskontrolle **Code, nicht Autorität als Fakt.** „Hat dieser PR verändert, wer >10.000 $ rückerstatten darf?" ist keine Frage, die ein Git-Diff direkt beantwortet; es ist eine Frage, die Sie beantworten, indem Sie den Code in Ihrem Kopf nachverfolgen. Die deklarierte Regel oben macht diesen Diff trivial: `who_can_run` hat sich geändert, oder eben nicht.

Drittens — und das ist der Punkt, der für die Richtung der Branche am wichtigsten ist — die ganze Prämisse von Low-Code ist, dass **Nicht-Entwickler und KI** die App ändern, oft im visuellen Editor, oft ganz ohne PR. Die Governance, auf die Sie zählen (PR-Review), existiert nicht für die Änderungen, *für die* Low-Code da ist. Audit-Logs sagen Ihnen, dass sich eine `Hidden`-Eigenschaft geändert hat, im Nachhinein — detektivisch, nicht präventiv — aber niemand hat geprüft, *welche Autorität sie gewährte*, bevor sie ausgeliefert wurde.

## KI bricht das nicht. Sie multipliziert es.

Jahrelang war der grep-Test überlebbar, weil ein Mensch das JavaScript schrieb und ein anderer Mensch das Wissen darüber trug, wo jede Regel lebte. Verstreute Logik ist navigierbar, wenn ein Mensch sie gebaut hat und sich an sie erinnert.

Richten Sie eine KI auf dieselbe App, und die Ökonomie kehrt sich in beide Richtungen um. Die KI kann fünfzig Bindungen und ein Dutzend Transformer in einer Minute erzeugen — sie produziert *Autoritätsentscheidungen* schneller, als irgendein Prüfer sie nachverfolgen kann. Und um zu prüfen, was sie produziert hat, sind Sie wieder beim Lesen von JavaScript über Screens hinweg, denn es gibt immer noch keine einzige strukturierte Repräsentation von Autorität, gegen die man diffen könnte. „Retool AI" und Agents (2025) sind real und nützlich, aber sie automatisieren *auf demselben handgebauten Substrat*: Der Agent wird regiert (Retool kann eingrenzen, was er aufruft), aber die **App, die der Agent bearbeitet, ist es nicht** — nicht autoritäts-regiert in irgendeiner Form, die eine KI — oder ein Mensch — als Fakt statt als Code prüfen kann.

Das, was KI am schnellsten produziert, ist genau das, was Retool am schwersten zu prüfen macht.

## Retool vs. Lovable für Enterprise-Apps

Der andere Vergleich, den viele anstellen, ist Retool gegen Lovable, meist gerahmt als „Builder für interne Tools vs. KI-App-Generator". Für eine Enterprise-App ist die nützlichere Rahmung: *Wessen Nutzer regelt die jeweilige Kontrolle?*

| | Retool | Lovable |
| --- | --- | --- |
| **Was die KI erzeugt** | Eine App auf Retools Komponenten-Laufzeit, verdrahtet mit Ihren bestehenden Ressourcen | Full-Stack-Projektcode; standardmäßig „liegt er in Lovables verwalteter Infrastruktur", mit Synchronisierung zu GitHub, GitLab oder Bitbucket ([Lovable for Enterprise](https://docs.lovable.dev/introduction/lovable-for-enterprise)) |
| **Rollen** | Berechtigungsgruppen steuern den Zugriff auf die App und auf die Ressourcen, Workflows und Agents dahinter | Owner, Admin, Editor, Viewer und externe Mitarbeiter regeln den *Workspace*, der die App baut ([dieselbe Seite](https://docs.lovable.dev/introduction/lovable-for-enterprise)) |
| **Datenzugriff der Endnutzer** | Datenquellen-Berechtigungen, `current_user`-Filter, Zugriffsrichtlinien | Sicherheit auf Zeilenebene im integrierten Backend „für nutzerbezogene Daten", Teil des generierten Projekts; ein Quick Scan „läuft bei jeder Veröffentlichung und prüft die Datenbank-Zugriffsregeln" |
| **Audit** | Audit-Log auf Query-Ebene, ein Jahr in der Cloud | Workspace-Audit-Log, „13 Wochen aufbewahrt", mit geplantem Export in ein SIEM oder einen Storage-Bucket |
| **Self-Hosting** | Von Retool verwaltete oder selbst verwaltete Self-Hosted-Instanzen ([Self-Hosted Retool](https://docs.retool.com/self-hosted)) | Backend und Datenbank können auf Infrastruktur umziehen, die Sie betreiben, „einschließlich selbst gehostetem Supabase"; der Builder selbst bleibt SaaS |

Die Unterscheidung in der zweiten und dritten Zeile ist diejenige, die über die Enterprise-Tauglichkeit entscheidet. Lovables Rollen und Audit-Log regeln die Menschen, die die App *bauen*; die Menschen, die sie *nutzen*, werden durch die Zugriffsregeln im eigenen Backend des generierten Projekts geschützt, die ein Scan bei jeder Veröffentlichung prüft. Retool regelt die Menschen, die die App nutzen, weil die App in Retool läuft. Deshalb besteht Retools Schritt vom Juni 2026 darin, in Lovable und ähnlichen Tools gebaute Apps unter seinen eigenen Datenquellen-Berechtigungen zu *hosten*, statt mit ihnen bei der Generierung zu konkurrieren.

Das realistische Enterprise-Muster ist also nicht „Retool oder Lovable", sondern „überall generieren, an einem regierten Ort betreiben". Keines von beiden ändert den grep-Test: Die Rückerstattungsschwelle einer Lovable-App lebt in ihrem generierten Code, die einer Retool-App in ihren Bindungen und Transformern, und in beiden Fällen rekonstruiert ein Prüfer geschäftliche Autorität, indem er Code liest.

## Wo Retool die richtige Wahl ist — und wo das Metadaten-Modell Sie etwas kostet

Seien Sie in beide Richtungen ehrlich, denn ein einseitiger Text ist für jemanden, der wirklich eine Entscheidung trifft, wertlos.

Retools Zugriffs-Governance ist wirklich erstklassig, und für eine große Menge von Apps wird der grep-Test nie akut: ein internes Tool, das von vertrauenswürdigem Personal bedient wird, hinter SSO, gepflegt von denselben Entwicklern, die es geschrieben haben, wo „Support-Leads können bis zu 10.000 $ rückerstatten" an drei Stellen durchgesetzt wird, die zufällig übereinstimmen und sich selten ändern. Dafür — und für die Freiheit, jederzeit in SQL und beliebiges JavaScript abzutauchen, wenn eine Anforderung schräg ist — ist Retool exzellent und für schnell verdrahtete interne Tools sehr stark.

Und das Modell deklarierter Metadaten hat einen echten Preis in die andere Richtung: Sie tauschen rohe Flexibilität gegen Lesbarkeit. Sie können nicht einfach beliebiges JavaScript in eine Eigenschaft einfügen, wenn das Modell keinen Platz dafür hat; genuin ungewöhnliche Logik als deklarierte Regeln auszudrücken ist eingeschränkter als `{{ }}` überall. Für ein Wegwerf-Tool ist diese Einschränkung reiner Overhead. Das Modell zahlt sich erst aus, wenn „wer darf was" etwas ist, dessen *Nachweis von Ihnen verlangt wird* — von einem Auditor, einer Aufsichtsbehörde oder dem nächsten Verantwortlichen — und wenn eine KI, nicht der ursprüngliche Autor, die Änderungen vornimmt.

Das ist die Trennlinie. Darunter gewinnt Retool nach Verdienst. Darüber ist der grep-Test das, woran Sie sechs Monate später scheitern, vor jemandem mit einem Klemmbrett.

## ObjectStacks Position

ObjectStack behält das, was Retool richtig macht — starke Zugriffskontrolle, Self-Hosting, Ihre eigene Infrastruktur — und verschiebt *Autorität* hinunter in dieselbe regierte Schicht. Die Logik der App ist **offene, lesbare Metadaten**: Eine Aktion wie `issue_refund` trägt ihr eigenes `who_can_run`, ihr eigenes Genehmigungs-Gate, ihre eigene Audit-Anforderung, einmal deklariert und von der Laufzeitumgebung auf jedem Pfad durchgesetzt. Eine KI-Änderung ist ein **Diff gegen diese deklarierte Autorität** — „diese Änderung erlaubt SupportLead, bis zu 25.000 $ rückzuerstatten" ist eine Zeile, die ein Nicht-Entwickler lesen und genehmigen kann, bevor sie ausgeliefert wird — kein `Hidden`-Ausdruck, den Sie später durch Grepen entdecken.

Wir werden Retool nicht bei „in JavaScript abtauchen und bis zum Mittagessen ein Tool ausliefern" übertreffen. Der Anspruch ist enger und zählt nur oberhalb der Linie: Wenn die KI Ihre interne Software schreibt, sollte *wer-darf-was* ein Fakt sein, den Sie an einem Ort lesen und als Diff prüfen können — keine emergente Eigenschaft dreier Ausdrücke, die übereinstimmen müssen, und es meist auch tun, bis zu dem Quartal, in dem sie es nicht tun.
